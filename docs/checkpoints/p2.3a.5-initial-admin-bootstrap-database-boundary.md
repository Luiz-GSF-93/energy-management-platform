# P2.3a.5 — Initial Admin Bootstrap Database Boundary

## Status

IMPLEMENTED AND LOCALLY VALIDATED — migration not yet executed.

Phase 2 — Administration remains active.

P2.3 — User Management remains active.

P2.3a remains open pending bootstrap and positive production read validation.

P2.3b remains blocked.

## Objective

Establish the database-atomic boundary required by the published P2.3a.5
Initial Organization Administrator Bootstrap Decision and Implementation
Contract.

This checkpoint implements only:

- dedicated Platform Administration bootstrap permission catalog entry;
- assignment of that permission to `admin_platform`;
- atomic first-admin membership RPC;
- per-Organization concurrency serialization;
- service-role-only RPC execution boundary;
- migration preflight and postflight integrity assertions.

No NestJS bootstrap endpoint is implemented by this checkpoint.

The migration has not been executed in production.

## Verified production schema

The migration was reconciled against the live production catalog before
execution.

Verified types include:

- `permissions.id` — text;
- `organizations.id` — text;
- `roles.id` — text;
- `roles.organization_id` — text;
- `roles.permissions` — jsonb;
- `organization_members.id` — text;
- `organization_members.organization_id` — text;
- `organization_members.role_id` — text;
- `organization_members.user_id` — uuid.

The existing membership uniqueness constraint is:

`UNIQUE (user_id, organization_id)`

That constraint prevents duplicate membership for the same User and
Organization.

It does not serialize two different Users concurrently attempting to become
the first Organization administrator.

## Permission catalog

The migration introduces:

`platform.organizations.bootstrap_admin`

using the verified Platform Organizations catalog convention:

- module: `gestao`;
- resource: `organizations`;
- action: `bootstrap_admin`.

The generated permission identifier is intentionally not reproduced in this
checkpoint.

The migration assigns the permission only to the existing global
`admin_platform` role.

A postflight assertion rejects permission leakage to any other role.

## RPC contract

The migration introduces:

`public.bootstrap_initial_organization_admin(text, uuid)`

Arguments:

- target Organization ID — text;
- target User ID — uuid.

The RPC does not accept a role identifier.

The destination role is resolved internally as exactly one organization-scoped
`admin_org` role belonging to the target Organization.

## Concurrency boundary

Bootstrap attempts are serialized per Organization with a transaction-scoped
PostgreSQL advisory lock.

The lock key is derived from the target Organization identifier through:

`hashtextextended(text, bigint)`

and acquired through:

`pg_advisory_xact_lock(bigint)`.

Both PostgreSQL primitives were confirmed in the live production catalog
before migration execution.

The lock is per Organization rather than global.

## Eligibility checks

After acquiring the advisory lock, the RPC re-evaluates bootstrap eligibility.

It proves:

1. the target Organization exists and is not soft-deleted;
2. exactly one organization-scoped `admin_org` role exists;
3. no active `admin_org` membership exists;
4. no active `gestor` membership exists;
5. the target User has no existing membership in the target Organization.

Only after those checks pass may membership creation occur.

## Membership mutation

The RPC creates exactly one membership with:

- target Organization;
- target User;
- internally resolved `admin_org` role;
- status `active`.

The returned state is checked against the requested Organization, requested
User, resolved role and expected status.

A failed confirmation aborts the database transaction.

## Conflict contract

The RPC exposes distinct database error contracts for:

- invalid argument;
- Organization not found;
- Organization integrity failure;
- `admin_org` integrity failure;
- membership confirmation failure;
- existing active Organization administrator;
- existing target membership;
- concurrent membership uniqueness conflict.

Expected bootstrap domain conflicts are not represented by a synthetic
`23505`.

A real `unique_violation` from the existing membership uniqueness constraint
is mapped to the dedicated concurrent bootstrap conflict.

## Privileged execution boundary

The RPC is:

`SECURITY DEFINER`

with fixed:

`search_path=pg_catalog`.

All application tables are explicitly schema-qualified.

Execution is revoked from:

- PUBLIC;
- anon;
- authenticated.

Execution is granted to:

- service_role.

The browser must never call this RPC directly.

## Privilege postflight

The migration verifies the effective function security state through the
PostgreSQL catalog.

Postflight verifies:

- the function exists with the expected `(text, uuid)` identity arguments;
- the function is `SECURITY DEFINER`;
- `search_path` is fixed to `pg_catalog`;
- PUBLIC cannot execute;
- anon cannot execute;
- authenticated cannot execute;
- service_role can execute.

This follows the existing repository pattern for privileged database helpers.

## Production catalog discovery

Before finalizing the migration, read-only production discovery confirmed:

- the real permission schema;
- the real Organization, Role and Membership identifier types;
- `roles.permissions` as a JSONB array;
- the existing membership uniqueness constraint;
- availability of `hashtextextended(text, bigint)`;
- availability of `pg_advisory_xact_lock(bigint)`;
- service_role RLS bypass capability.

No production mutation was performed by that discovery.

## Migration policy

The migration is additive.

It does not:

- delete application data;
- alter existing User Management permissions;
- alter `consulta`;
- alter `operacional`;
- add Platform Admin bypass to organization User Management;
- hard-delete memberships;
- expose the RPC to browser-authenticated roles.

Migration source is versioned before database execution.

Migration execution requires a separate controlled checkpoint.

## Nest boundary

No NestJS bootstrap implementation is included here.

The next implementation slice must add:

- backend permission constant;
- Platform-scoped bootstrap endpoint;
- request DTO;
- identity/profile resolution;
- RPC invocation and error mapping;
- persistent bootstrap audit;
- guarded audit-failure compensation;
- focused tests.

Normal `/api/v1/admin/users` remains organization-scoped.

## Audit relationship

The existing AuditService remains the persistent audit authority.

The repository already supports persistent audit records containing actor,
Organization, resource, before/after state, IP address and user-agent.

The future Nest bootstrap implementation must persist bootstrap audit only
after successful RPC membership creation.

Audit failure must trigger guarded compensation of the membership created by
that bootstrap execution.

## Scope boundary

This checkpoint does not authorize:

- execution of the migration before its publication;
- direct invocation of the RPC from a browser;
- manual mutation of the validation User;
- changing `consulta` permissions;
- changing `operacional` permissions;
- permanent Platform Admin User Management bypass;
- P2.3b implementation;
- P2.4 or later Phase 2 work.

## Decision

The P2.3a.5 database boundary is implemented and locally validated.

The atomic first-admin decision belongs to the database RPC.

Identity and profile provisioning remain a NestJS responsibility.

The migration must be published before controlled database execution.

P2.3a remains open.

P2.3b remains blocked.

## Publication state

This checkpoint and its migration are pending commit and publication.

The migration must not be executed until both are published to `origin/main`.
