# F1.4 — Pre-DDL Catalog Guard Design

## 1. Status

Design checkpoint. No migration is executed by this checkpoint.

The authoritative runtime database already contains `public.licenses`.
F1.4 SHALL reuse that domain and SHALL NOT create a competing license table.

The migration MUST inspect authoritative PostgreSQL catalog state before DDL.
The guard MUST fail closed.
Unknown or incompatible state MUST abort before mutation.

Migration creation and migration execution MUST NOT occur in the same checkpoint.

## 2. Catalog and type guards

The guard MUST prove that the target relation is exactly `public.licenses`.
The guard MUST also prove that `public.organizations` exists.

The guard MUST inspect authoritative PostgreSQL types for:
- licenses.id
- licenses.organization_id
- organizations.id
- licenses.status
- licenses.active
- licenses.start_date
- licenses.end_date
- licenses.renewal_date

`licenses.organization_id` and `organizations.id` MUST be type-compatible.
Type mismatch MUST abort before DDL.

The guard MUST confirm the existing primary key for licenses.id.
Unexpected primary-key shape MUST abort.

## 3. Foreign keys, uniqueness and indexes

The guard MUST enumerate current licenses foreign keys.
It MUST inspect local columns, referenced schema/table/columns, actions and validation state.

Desired ownership semantics are:
licenses.organization_id -> public.organizations.id

An equivalent compatible foreign key MUST be reused.
A conflicting foreign key MUST abort.
No destructive foreign-key replacement is authorized.

The guard MUST enumerate current unique constraints.
Historical license coexistence is an architectural requirement.
A plain global UNIQUE(organization_id) is therefore not the intended invariant.
Unexpected uniqueness affecting license history MUST abort for review.

The guard MUST enumerate current indexes, including uniqueness and predicates.
Equivalent indexes MUST be reused based on semantics, not names.
Duplicate indexes MUST NOT be created merely because names differ.

## 4. Check constraints, lifecycle and existing data

The guard MUST enumerate current check constraints and validation state.
It MUST inspect constraints affecting status, active, quotas and dates.

The OpenAPI default `ACTIVE` does not prove the accepted status vocabulary.
Conflicting lifecycle constraints MUST abort for review.

F1.4 normalizes lifecycle semantics around active, suspended, expired and cancelled.
The existing persistence contract contains both status and active.
Existing values MUST NOT be bulk rewritten merely to normalize case or vocabulary.

### Existing data gate

The migration MUST NOT assume that licenses is still empty at execution time.
Before adding constraints it MUST validate relevant existing data.
This includes orphan organization_id values and conflicting cardinality.
It also includes incompatible lifecycle, quota and date values.

If existing data violates a proposed integrity rule, the migration MUST abort.
It MUST NOT delete or rewrite license rows automatically to make DDL succeed.

Foundation requires at most one effective active license per organization.
Historical licenses MUST remain compatible with that invariant.
Application-only read-then-write checks are insufficient under concurrency.
Database-backed enforcement is required before concurrency-sensitive create is released.
The exact database predicate MUST NOT be guessed before catalog and data classification.

## 5. RLS, policies, triggers and defaults

The guard MUST inspect whether row-level security is enabled and forced.
RLS state MUST NOT be inferred from Supabase or PostgREST availability.
Backend tenant enforcement remains mandatory regardless of RLS state.

The guard MUST enumerate current RLS policies for `public.licenses`.
It MUST inspect policy command, roles, mode, USING and WITH CHECK semantics.
Existing policies MUST NOT be dropped or replaced implicitly.
Unknown or conflicting policy semantics require explicit review.

Relevant non-internal triggers SHOULD be enumerated.
Existing trigger behavior MUST NOT be duplicated or silently bypassed.

Authoritative defaults and nullability MUST be inspected.
Existing defaults MUST NOT be silently replaced.

Schema objects MUST be compared by semantics rather than names alone.
Equivalent compatible objects MUST be reused.
Conflicting semantics MUST abort before mutation.

## 6. Fail-closed and additive-only boundary

The migration MUST abort before mutation when required state cannot be safely classified.
This includes missing relations, missing compatibility columns and incompatible ownership types.
It also includes unexpected primary keys, conflicting FKs and conflicting uniqueness.
Incompatible lifecycle constraints or existing data MUST also abort.
Best-effort schema guessing is prohibited.

After all guards pass, only minimum reviewed additive evolution is permitted.

The migration MUST NOT drop or destructively recreate `public.licenses`.
The migration MUST NOT delete license rows or drop compatibility columns.
The migration MUST NOT drop constraints or indexes merely to replace their names.
The migration MUST NOT disable RLS or remove policies as a shortcut.

Equivalent approved objects SHOULD be treated as satisfied.
Conflicting objects MUST cause an abort.
Idempotency MUST NOT conceal incompatible schema drift.

No dynamic destructive DDL may be generated from discovered object names.

Migration diagnostics MUST NOT expose database URLs, passwords, service keys or JWT secrets.
Errors SHOULD identify schema objects and failed invariants only.

## 7. Catalog sources, audit and execution gate

The guard may use PostgreSQL-native metadata sources including:
- pg_class
- pg_namespace
- pg_attribute
- pg_type
- pg_constraint
- pg_index
- pg_policy
- pg_trigger
- pg_get_constraintdef
- pg_get_indexdef
- pg_get_expr
- information_schema where appropriate

Before DDL is authorized, the migration MUST classify:
- relation identity and type
- required compatibility columns
- relevant PostgreSQL types
- nullability and defaults
- primary key
- current licenses foreign keys
- current unique constraints
- current check constraints
- current indexes
- existing-data compatibility
- RLS enabled and forced state
- current RLS policies
- relevant non-internal triggers

An unresolved required category means DDL is not authorized.

The schema guard does not replace runtime application audit.
License create, update and lifecycle mutations still require persistent audit.

Required implementation sequence:
1. write migration source
2. inspect complete migration source
3. run static checks
4. prove catalog guards precede DDL
5. prove no unrelated schema mutation
6. inspect fail-closed paths
7. approve the migration source
8. execute only in a later controlled checkpoint

F1.4 will not install tooling or create an RPC merely to bypass missing local catalog clients.
Authoritative pre-DDL inspection will be embedded in the reviewed PostgreSQL migration.
Equivalent compatible objects will be reused and conflicting state will fail closed.
Existing data and compatibility boundaries will be preserved.

Only after the guard succeeds may the minimum reviewed additive license schema evolution execute.
