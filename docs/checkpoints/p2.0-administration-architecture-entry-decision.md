# P2.0 — Administration Architecture & Entry Decision

## Status

APPROVED FOR PHASE 2 ENTRY — architecture and scope only.

Phase 1 — Foundation remains closed and validated.

Phase 2 — Administration is authorized to begin incrementally under the
constraints defined by this decision.

No functional Phase 2 implementation is performed by this checkpoint.

## Objective

Define the architecture, data-model authority, module map, permission
boundary, flows, dependencies, integration strategy, migration policy,
test strategy and risks required before implementation of Phase 2 —
Administration.

The approved Administration scope is:

- organizations;
- user management;
- licenses;
- settings;
- administrative dashboard.

The existing Foundation must be extended, not rewritten.

## 1. Proposed architecture

Phase 2 will use the following dependency direction:

Foundation security and tenant boundary
→ existing and incremental Administration backend APIs
→ typed frontend API layer
→ authenticated organization context
→ Backoffice application shell
→ reusable Design System
→ Administration modules.

The Foundation security boundary remains authoritative.

Frontend visibility is not authorization.

All protected operations continue to require backend enforcement through
the established authentication, TenantContext, RBAC, membership, RLS and
audit boundaries.

Phase 2 must not weaken or bypass:

- authenticated identity resolution;
- active organization membership;
- contextual organization role;
- backend permission enforcement;
- Foundation RLS;
- persistent audit requirements;
- license entitlement enforcement.

## 2. Authoritative data model

Phase 2 adopts the validated Foundation runtime model as authoritative.

### Identity and organization authority

`organization_members` is the organization-membership authority.

`organization_members.role_id` is the contextual organization-role
authority.

`user_profiles` stores profile information, affiliation information and
the active-organization pointer where applicable.

`user_profiles.organization_id` must not be treated as organization-access
authority.

### Permission authority

`roles.permissions` JSONB remains the effective runtime permission-grant
authority.

The historical `user_roles` / `role_permissions` model documented in
`docs/supabase-schema.sql` must not be assumed to represent the current
runtime authorization model.

### Organization data

The active organizations service currently operates against the live
`organizations` contract used by the Foundation.

Any Phase 2 requirement for additional organization fields must first be
reconciled against the live database catalog and existing runtime behavior.

The historical schema document may be used as reference material but must
not independently authorize a migration.

### User data

Administration user views are composed from organization-scoped
`organization_members` plus bounded `user_profiles` data.

Existing user-management behavior includes:

- organization-scoped list;
- organization-scoped detail;
- invite;
- membership deactivation;
- contextual role update;
- affiliation update.

Affiliation does not grant organization access.

### License data

The existing `licenses` Foundation model remains authoritative for the
Administration license module.

Its current contract includes:

- license type;
- document limit;
- renewal date;
- start date;
- optional end date;
- optional consumer-unit limit;
- document-management capability;
- advanced-analytics capability;
- report-generation capability;
- free-market-management capability;
- lifecycle status.

License access remains organization-scoped.

### Historical schema boundary

`docs/supabase-schema.sql` contains legacy or superseded identity and
authorization structures.

Where that document conflicts with validated Foundation migrations,
runtime code or published Foundation decisions, the validated Foundation
model takes precedence.

No Phase 2 migration may be created solely from the historical schema
document.

## 3. Module map

### P2.1 — Backoffice Foundation

Build the reusable frontend foundation required by all Administration
modules:

- Design System primitives;
- visual tokens and global styles;
- typed API client;
- authentication/session integration;
- organization-context integration;
- permission-aware navigation;
- Backoffice shell;
- loading, empty and error states.

The current provisional frontend is not the target architecture.

### P2.2 — Organizations

Reuse the existing organizations backend module.

Build the Administration organization experience over the existing API
contract.

Backend or database expansion is permitted only when a documented Phase 2
requirement is not satisfied by the live contract.

### P2.3 — User Management

Reuse the existing Administration users module for current supported
operations.

Additional requirements such as password reset, new invitation link,
last-access information or access counters must be separately reconciled
against Supabase Auth and the live data model before implementation.

### P2.4 — Licenses

Reuse the existing License Foundation service, permission model,
entitlement semantics and audit behavior.

Build Administration workflows over those existing contracts rather than
introducing a parallel license model.

### P2.5 — Settings

Settings is currently an unimplemented Administration domain.

Its persistence model and permission model require a separate design
checkpoint before schema or implementation changes.

### P2.6 — Administrative Dashboard

The dashboard must use real backend data.

Static placeholder metrics must not be presented as production
Administration data.

Dashboard aggregation contracts must be designed before implementation and
must preserve tenant and permission boundaries.

### P2.7 — Phase 2 Regression and Closeout

Run consolidated Administration regression and reconcile all Phase 2
requirements before formal closeout.

## 4. Permission map

Phase 2 must preserve backend authorization as the enforcement authority.

Frontend permission checks may control presentation and navigation but must
never replace backend authorization.

### Organizations

Organization Administration must reuse the existing organization permission
contract.

Any new organization operation requires explicit backend permission review
before implementation.

### User management

User Administration must preserve the existing granular permission model for:

- reading organization users;
- inviting users;
- deactivating memberships;
- changing contextual organization roles;
- changing affiliation where authorized.

A user's affiliation type must never independently grant organization access.

Organization access continues to depend on active membership.

### Licenses

The existing License Foundation permission model remains authoritative.

Phase 2 must reuse the validated license permission assignment rather than
introducing UI-specific authorization rules.

### Settings

No Settings permission contract is currently approved.

P2.5 must define its resources, actions, role assignments and tenant scope
before implementation.

### Administrative dashboard

Dashboard access must be permission-aware.

Aggregate endpoints must enforce authorization and tenant boundaries on the
backend before returning data.

Dashboard cards and navigation visibility are presentation concerns only.

## 5. Principal flows

### Authentication and Administration entry

The Administration entry flow is:

authenticated identity
→ validated application token
→ active organization context
→ contextual organization membership
→ contextual role and permissions
→ Backoffice shell
→ permitted Administration modules.

The current provisional localStorage-based frontend protection is not the
target security architecture.

P2.1 must design the browser session boundary without weakening the existing
backend authentication contract.

### Organization flow

authorized administrator
→ organization API
→ backend permission validation
→ organization operation
→ persistent audit where required
→ response
→ Administration UI state refresh.

### User-management flow

authorized administrator
→ active organization context
→ organization-scoped user operation
→ backend permission validation
→ membership/profile/auth operation as applicable
→ persistent audit for mutating Foundation operations
→ response
→ Administration UI state refresh.

Membership remains the organization-access authority.

### License flow

authorized administrator
→ active organization context
→ license permission validation
→ organization-scoped license operation
→ entitlement/audit invariants
→ response
→ Administration UI state refresh.

### Settings flow

Settings flow remains intentionally undefined until P2.5 design establishes:

- ownership;
- persistence;
- scope;
- permissions;
- audit requirements;
- inheritance/default behavior.

### Dashboard flow

authorized administrator
→ dashboard query/filter request
→ backend permission and tenant validation
→ real aggregate queries
→ bounded aggregate response
→ dashboard visualization.

The UI must not manufacture production metrics.

## 6. Dependencies and reuse policy

Phase 2 must reuse the validated Foundation before adding dependencies.

Existing runtime contracts to preserve include:

- NestJS backend;
- Supabase integration;
- Next.js frontend;
- React;
- TypeScript;
- Lucide icon dependency;
- existing authentication;
- TenantContext;
- RoleGuard / permission enforcement;
- Foundation RLS;
- Foundation audit service;
- existing organizations module;
- existing users Administration module;
- existing licenses module.

New runtime dependencies require an explicit need, security review and
compatibility validation.

A UI dependency must not be introduced merely to avoid creating reusable
Design System primitives already required by the architecture.

## 7. Integration strategy

The frontend must communicate with Administration through explicit backend
contracts.

P2.1 must introduce a centralized typed API boundary rather than distributing
raw fetch calls throughout pages and components.

The frontend must have a single integration strategy for:

- API base URL;
- authentication;
- error normalization;
- organization context;
- permission context;
- request lifecycle;
- loading state;
- unauthorized/forbidden handling.

Existing backend DTO and response contracts should be reused where suitable.

Where a frontend requirement is not represented by an existing backend
contract, the backend contract must be designed and tested before the UI
depends on it.

## 8. Migration strategy

No database migration is authorized by P2.0.

Before any Phase 2 migration:

1. identify the requirement that cannot be satisfied by the live model;
2. inspect the live Supabase catalog;
3. reconcile the change with Foundation migrations and decisions;
4. define tenant, RBAC, RLS and audit impact;
5. define forward migration;
6. define validation and rollback/compensation strategy;
7. review the migration before execution;
8. validate the resulting live state.

`docs/supabase-schema.sql` is not independently authoritative where it
conflicts with the validated Foundation runtime model.

Phase 2 must not restore superseded identity or authorization authority such
as organization access derived solely from `user_profiles.organization_id`.

## 9. Test strategy

Every Phase 2 checkpoint follows the incremental delivery rule:

develop
→ test
→ validate
→ correct
→ run regression
→ document
→ version
→ proceed.

### Backend

Backend changes require, as applicable:

- unit tests;
- service tests;
- controller tests;
- permission-denial tests;
- tenant-isolation tests;
- audit tests;
- migration diagnostics;
- full backend regression before checkpoint closeout.

Existing Foundation regression must remain passing.

### Frontend

P2.1 must establish the sustainable frontend validation baseline for the
new architecture.

At minimum each frontend checkpoint must preserve:

- TypeScript validation;
- production build;
- dependency-security validation;
- route/navigation integrity;
- explicit loading, empty and error states.

The final lint architecture must be established as part of the rebuilt
frontend rather than restoring the removed obsolete `next lint` command.

### Security regression

Administration mutations must verify that:

- unauthorized roles are denied;
- foreign-organization access is denied;
- inactive membership does not grant access;
- frontend visibility cannot bypass backend authorization;
- audit requirements remain satisfied.

## 10. Risks and controls

### Risk — rewriting validated Foundation behavior

Control:

Reuse existing modules and extend contracts only where a documented Phase 2
requirement demonstrates a gap.

### Risk — historical schema drift

Control:

Use live catalog evidence, Foundation migrations and current runtime contracts
before designing schema changes.

### Risk — frontend-only authorization

Control:

Treat frontend permission checks as presentation only and preserve backend
authorization as mandatory.

### Risk — provisional frontend becoming permanent architecture

Control:

P2.1 establishes the Backoffice shell, typed integration boundary and Design
System before Administration feature pages are expanded.

### Risk — fabricated dashboard information

Control:

Administrative dashboard metrics must originate from real authorized backend
queries. Placeholder values must be explicitly identified as development-only
or omitted.

### Risk — Settings becoming an unbounded configuration store

Control:

P2.5 requires a separate domain design before persistence or generic settings
APIs are introduced.

### Risk — Phase 2 weakening Foundation RLS or tenant isolation

Control:

Every new organization-scoped table or query requires explicit tenant and RLS
review.

## Entry conditions

Phase 2 entry conditions are satisfied by:

- formally closed and published Phase 1 Foundation;
- clean synchronized repository baseline;
- passing final Foundation regression;
- validated Foundation security invariants;
- authoritative Administration scope supplied by the Master Prompt;
- completed Administration implementation inventory;
- reconciled Foundation data-authority model;
- documented Phase 2 architecture and incremental module sequence.

## Decision

Phase 2 — Administration is authorized to begin after publication of this
P2.0 decision.

The first implementation checkpoint is P2.1 — Backoffice Foundation.

P2.1 is limited to the reusable Administration frontend foundation and its
required integration contracts.

P2.1 must not prematurely implement Organizations, User Management, Licenses,
Settings or Dashboard business functionality.

Each later Phase 2 module requires its own scoped checkpoint and regression
gate.

This decision does not authorize Phase 3 or any later phase.

## Publication state

P2.0 is pending review and publication.

Until this decision is committed and published to `origin/main`, no Phase 2
functional implementation is authorized.
