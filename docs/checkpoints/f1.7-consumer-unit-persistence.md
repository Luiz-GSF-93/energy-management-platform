# F1.7 — Cadastro de unidades consumidoras

O serviço enviava propriedades camelCase como se fossem colunas PostgreSQL e
não recebia distributor/tariff_group, obrigatórios no schema. A criação não
verificava o tenant do cliente referenciado, apesar de usar service_role.

A API mantém customerId/name/code e os campos opcionais existentes. Criação
passa a exigir distributor e tariffGroup: não há default correto para esses
dados. Campos são mapeados explicitamente; code corresponde a
consumer_unit_number e voltageClass a voltage. A resposta continua com os
nomes snake_case do banco, como antes.

A migração adiciona cinco colunas opcionais para preservar metadados já aceitos
pela API: name, address, city, state e installed_capacity. Capacidade instalada
não é convertida em demanda contratada; contractedDemand é um campo separado.
Não há backfill, modificação de registros existentes ou reabertura de grants.

O serviço verifica customer_id + organization_id e exclui clientes com
deleted_at. Updates não permitem trocar cliente/tenant. Leituras, updates e
deletes de ID ausente ou externo retornam 404; duplicidade retorna 409; erros
inesperados não expõem mensagens internas do banco.

Exemplo de POST /api/v1/consumer-units (com autenticação e contexto de organização):

```json
{
  "customerId": "00000000-0000-4000-8000-000000000001",
  "name": "Unidade industrial",
  "code": "UC-001",
  "distributor": "Distribuidora",
  "tariffGroup": "A4",
  "tariffModality": "GREEN",
  "contractedDemand": 80,
  "installedCapacity": 100
}
```

Validação local: 41 suítes / 393 testes, build NestJS; 20 verificações executando
o serviço compilado contra PostgreSQL via PGlite, com duas organizações fictícias,
constraints, defaults, mapeamento, duplicidade e tentativas de acesso cruzado.
O adaptador de teste executa SQL real, mas não simula a autenticação ou transporte
HTTP do Supabase. Não substitui testes completos com usuários reais.

Ordem de implantação: testar no PostgreSQL 17.6; aplicar a migração aditiva antes
do backend; publicar PR; verificar deploy Railway e disponibilidade. Reverter o
backend não exige remover as novas colunas. Contratos e documentos permanecem
para etapas seguintes. Nenhuma interface nova foi adicionada nesta etapa.
