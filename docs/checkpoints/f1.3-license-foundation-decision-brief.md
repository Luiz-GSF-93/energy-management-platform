# F1.3 — License Foundation Decision Brief

## Status

Decision checkpoint for the Foundation license architecture.

This checkpoint defines the architecture only.

It does not:

- create or alter database schema;
- implement license APIs;
- implement frontend license management;
- alter authentication;
- alter tenant resolution;
- alter organization membership;
- alter RBAC;
- implement commercial billing;
- implement plan catalogs;
- implement feature-specific quotas.

---

## 1. Context

Foundation discovery confirmed that the authorization catalog already contains:

- `ORGANIZATION_LICENSES_VIEW`
- `ORGANIZATION_LICENSES_CREATE`
- `ORGANIZATION_LICENSES_UPDATE`

No `ORGANIZATION_LICENSES_DELETE` permission exists.

The existing license permissions currently have no implementation usage outside
the permission catalog.

No authoritative license, subscription, entitlement, or plan domain has yet
been implemented.

Therefore F1.3 defines the minimum license architecture required before F1.4
implements the License Foundation.

---

## 2. Architectural boundary

License management MUST NOT become part of identity resolution, tenant
resolution, organization membership, or RBAC authority.

The authorization sequence is:

1. authenticated identity;
2. validated organization membership / platform context;
3. validated RBAC permission;
4. organization license;
5. applicable entitlement or limit;
6. business operation.

Conceptually:

`Identity -> Membership/Tenant -> RBAC -> License -> Entitlement -> Resource`

RBAC answers:

> Is this actor authorized to perform this class of operation?

License enforcement answers:

> Is this organization entitled to use this licensed capability?

These responsibilities MUST remain separate.

---

## 3. License ownership

A license belongs to an organization.

The organization is the tenant boundary.

License ownership MUST therefore be represented by an explicit
`organization_id`.

A license MUST NOT be owned by:

- `user_profiles`;
- `organization_members`;
- `roles`;
- `user_roles`;
- individual users.

User access to license administration continues to be controlled through the
existing tenant context and RBAC pipeline.

---

## 4. Persistence decision

License state MUST be persisted in a dedicated license domain.

License fields MUST NOT be embedded directly into the `organizations` table as
the primary persistence model.

Rationale:

- preserves separation between tenant identity and commercial entitlement;
- permits lifecycle history;
- permits future plan and entitlement evolution;
- avoids expanding the organization aggregate for unrelated commercial state;
- supports auditability;
- supports future versioning without changing tenant identity.

The exact physical schema is deferred to F1.4 after authoritative database
schema verification.

---

## 5. Foundation cardinality

F1 Foundation adopts:

> At most one effective active license per organization at a time.

Historical licenses MAY coexist with the current license.

The persistence model MUST prevent ambiguous simultaneous effective licenses
for the same organization.

The exact database constraint or transaction strategy will be decided during
F1.4 after inspection of the authoritative Supabase schema and supported
constraint mechanisms.

---

## 6. License lifecycle

Foundation lifecycle states:

- `active`
- `suspended`
- `expired`
- `cancelled`

### active

The organization has a currently effective license.

### suspended

The license exists but licensed capabilities are temporarily unavailable.

Suspension is reversible through an authorized administrative operation.

### expired

The license validity period has ended.

Expiration MUST be enforced from persisted validity dates and MUST NOT depend
only on a manually maintained boolean.

### cancelled

The license has been administratively terminated.

Cancellation is a historical business event.

Cancelled license records MUST NOT be hard-deleted.

---

## 7. Validity period

The license model MUST support an explicit validity interval.

At minimum the persistence design must represent:

- start of validity;
- optional end of validity;
- lifecycle status.

Effective license evaluation MUST consider both lifecycle state and validity
dates.

The backend is authoritative for effective-license evaluation.

Frontend state MUST NOT be considered authoritative.

---

## 8. Fail-closed behavior

License enforcement MUST fail closed.

If a protected licensed capability requires a valid license and the backend
cannot establish exactly one valid effective license for the current
organization, the protected capability MUST NOT be granted.

Examples include:

- missing license;
- malformed license;
- ambiguous effective license state;
- database lookup failure;
- invalid lifecycle state;
- expired validity;
- tenant/license ownership mismatch.

Infrastructure failures MUST NOT silently convert into licensed access.

---

## 9. Tenant isolation

Every organization-scoped license operation MUST use the validated organization
context supplied by the backend authorization pipeline.

For organization-scoped endpoints:

- organization authority MUST NOT come from an arbitrary request body;
- organization authority MUST NOT come from an unvalidated query parameter;
- organization authority MUST NOT be inferred from `user_profiles` alone;
- cross-organization license access MUST be rejected.

Platform-scoped administration, if introduced later, MUST use explicit
platform scope and explicit target-organization validation.

It MUST NOT impersonate organization tenant context.

---

## 10. RBAC contract

Existing license permissions remain the authorization vocabulary:

- `ORGANIZATION_LICENSES_VIEW`
- `ORGANIZATION_LICENSES_CREATE`
- `ORGANIZATION_LICENSES_UPDATE`

F1 does not introduce a generic license delete permission.

License history is retained.

Lifecycle termination is represented through controlled state transition, not
hard deletion.

Permission possession alone does not grant licensed business functionality.

Likewise, an active license does not grant a user an RBAC permission.

Both checks are independent.

---

## 11. Create semantics

Creating a license is an explicit administrative mutation.

Creation MUST:

- operate inside validated organization authority;
- validate input;
- reject ownership mismatch;
- preserve single-effective-license integrity;
- persist the license;
- create persistent audit evidence.

Creation MUST NOT:

- alter membership;
- alter user roles;
- alter active organization context;
- silently grant RBAC permissions.

---

## 12. Update semantics

License updates are controlled lifecycle/configuration mutations.

Updates MUST use optimistic or equivalent integrity protection where necessary
to prevent lost updates or invalid concurrent lifecycle transitions.

Updates MUST NOT overwrite historical license records in a way that destroys
material audit history.

The exact concurrency mechanism is deferred to F1.4 implementation design.

---

## 13. No hard delete

F1 License Foundation will not implement hard deletion of license records.

This matches the absence of an existing
`ORGANIZATION_LICENSES_DELETE` permission and preserves commercial/audit
history.

Termination is represented through lifecycle state.

---

## 14. Audit requirements

License mutations are critical administrative operations.

Persistent audit MUST capture, as applicable:

- authenticated actor;
- organization;
- license record;
- action;
- timestamp;
- previous state;
- resulting state;
- IP address when available;
- user agent / request origin when available;
- success/failure semantics consistent with the existing audit architecture.

At minimum the Foundation implementation must audit:

- license creation;
- lifecycle/status changes;
- validity changes;
- other material license configuration changes.

Audit records MUST NOT contain secrets.

---

## 15. Entitlements and limits

F1.3 distinguishes the license record from feature-specific entitlement logic.

The Foundation license establishes organization-level licensing infrastructure.

F1.4 MUST NOT prematurely introduce a large commercial plan catalog or generic
billing engine without a proven product requirement.

Future modules MAY extend the license domain with:

- feature entitlements;
- usage limits;
- quotas;
- product tiers;
- plan catalogs;
- commercial subscription integration.

Those extensions MUST preserve the architectural boundary established here.

---

## 16. Billing boundary

License Foundation is not a billing system.

F1 does not implement:

- payment processing;
- invoices for SaaS subscription billing;
- payment-provider integration;
- automatic renewals;
- pricing catalogs;
- discounts;
- taxes;
- payment delinquency workflows.

Future billing integration may drive license lifecycle changes through explicit,
audited application services.

Billing providers MUST NOT become tenant or RBAC authorities.

---

## 17. Frontend boundary

Frontend license state is presentation only.

The frontend MAY later:

- display license state;
- display validity;
- display licensed capabilities;
- hide or disable unavailable UI.

However, UI visibility is never an authorization or entitlement boundary.

Every protected operation remains enforced by the backend.

---

## 18. Existing organization model

F1.3 does not modify the organization aggregate.

Existing organization create/update behavior remains unchanged.

License creation is a separate operation from organization creation.

Automatic default-license provisioning is NOT introduced by this decision.

If product requirements later require automatic provisioning, it must be an
explicit audited workflow.

---

## 19. Schema authority warning

The repository documentation contains historical schema snapshots that do not
fully represent the current identity and membership architecture.

Therefore F1.4 MUST verify the authoritative Supabase schema before creating a
license migration.

Historical `docs/supabase-schema.sql` is documentation evidence only and MUST
NOT be treated as sufficient authority for migration design.

---

## 20. Compatibility requirements

F1.4 implementation MUST preserve:

- current authentication behavior;
- ADR 009 identity/membership architecture;
- active organization switching;
- Platform Admin behavior;
- organization CRUD;
- existing user lifecycle endpoints;
- current permission IDs;
- existing API contracts unrelated to licenses;
- existing database data.

No unrelated refactor is authorized.

---

## 21. Security requirements

License Foundation MUST preserve the project security priority:

1. security;
2. integrity;
3. compatibility;
4. scalability;
5. performance;
6. UX.

Specifically:

- backend enforcement is mandatory;
- tenant ownership is mandatory;
- ambiguous state fails closed;
- client-supplied tenant authority is forbidden;
- cross-tenant license access is forbidden;
- hard deletion is forbidden;
- audit is mandatory for mutations;
- license state cannot substitute RBAC;
- RBAC cannot substitute license state.

---

## 22. F1.4 implementation scope

F1.4 may implement only the minimum License Foundation necessary to realize
this decision.

Expected implementation areas:

1. authoritative schema discovery;
2. additive license migration;
3. license persistence model;
4. organization-scoped license read;
5. controlled license creation;
6. controlled license update/lifecycle transition;
7. persistent audit;
8. backend effective-license evaluation primitive;
9. focused tests;
10. broad regression;
11. implementation closeout.

Feature-specific commercial entitlements are not automatically part of F1.4.

---

## 23. Out of scope

F1.3/F1.4 do not authorize:

- identity redesign;
- membership redesign;
- generic role administration;
- generic permission administration;
- billing provider integration;
- payment processing;
- plan marketplace;
- frontend redesign;
- automatic tenant creation;
- automatic role grants;
- hard deletion of licenses;
- cross-tenant license management through organization-scoped routes;
- unrelated database cleanup;
- unrelated refactoring.

---

## 24. Decision

F1 adopts a dedicated organization-owned License Foundation.

The license domain is separate from identity, membership, RBAC, and the
organization aggregate.

The backend evaluates effective license state after authentication, tenant
resolution, and RBAC authorization.

License enforcement is organization-scoped and fail closed.

Foundation supports one effective active license per organization, lifecycle
state, validity dates, persistent audit, historical retention, and future
extension to entitlements and limits.

F1.4 will implement the minimum additive foundation required by this decision
after authoritative Supabase schema verification.
