# P2.2b — Organization Create

## Status

IMPLEMENTED AND LOCALLY VALIDATED — pending publication and controlled
production validation.

Phase 2 — Administration remains active.

P2.2 — Organizations remains open.

This checkpoint implements Organization creation only.

Organization update and deletion remain outside this checkpoint.

P2.3 — User Management remains unauthorized.

## Objective

Add the Organization creation experience to the existing Administration
Organizations module while preserving the architecture established by P2.1
and the read foundation established by P2.2a.

The implementation reuses the existing platform-scoped backend mutation
contract.

No backend expansion is included.

No database migration is included.

## Existing backend contract

The existing backend exposes:

`POST /api/v1/admin/organizations`

The controller is platform-scoped.

The operation requires:

`PLATFORM_ORGANIZATIONS_CREATE`

The request contract accepts:

- `name`: required string;
- `description`: optional string.

The service:

- rejects an absent or blank organization name;
- trims the organization name;
- trims the optional description;
- normalizes an empty description to `null`;
- generates the organization identifier;
- establishes creation and update timestamps;
- creates the organization;
- records persistent creation audit information.

If persistent audit fails after creation, the service attempts to compensate
by removing only the state created by that operation.

The backend remains the mutation authorization authority.

## Frontend API contract

The centralized Organizations API now exposes:

- `CreateOrganizationRequest`;
- `createOrganization()`.

`createOrganization()` delegates to the existing centralized `apiRequest`
boundary.

The component does not call `fetch` directly.

The request uses:

- method `POST`;
- path `/api/v1/admin/organizations`;
- JSON request serialization owned by the centralized API client;
- Bearer authentication owned by the centralized API client.

The response is represented by the existing `Organization` frontend type.

## Permission boundary

The frontend platform permission registry now includes:

`ORGANIZATIONS_CREATE`

with the existing backend permission identifier.

The Organizations page evaluates the permission through the existing
`hasPermission()` auth-provider boundary.

The Create interface is rendered only when the current global access context
contains the Organization create permission.

This frontend visibility rule is presentation authorization only.

Backend authorization remains authoritative.

## Create interface

The existing `/backoffice/organizations` route now includes a create form for
authorized users.

The form contains:

- Organization name;
- optional description;
- submit action;
- submitting state;
- mutation error state;
- mutation success state.

The Organization name is required by the frontend before submission.

The submitted name and description are normalized before the API request.

After successful creation:

- form fields are cleared;
- a success state is presented;
- the Organizations collection is reloaded from the backend.

The backend response remains authoritative for the resulting collection.

## Production validation boundary

Organization creation is a real persistent and audited mutation.

Production validation must therefore be controlled and explicit.

No production Organization creation is performed by this implementation
checkpoint before publication.

After deployment, production validation must use an intentionally selected
test Organization and must verify the resulting state without exposing
credentials or access tokens.

The validation record must not be represented as disposable unless a
separately authorized cleanup operation is performed.

check.

No credential is introduced into source control.
