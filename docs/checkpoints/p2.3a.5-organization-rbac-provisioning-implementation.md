## Objective

Implement the published P2.3a.5 Organization RBAC provisioning contract so
that Organization creation and its canonical four-role RBAC baseline become
one database-atomic lifecycle boundary.

The same canonical permission authority must support controlled remediation of
an eligible existing Organization.

## 1. What was developed

The implementation adds:

1. one canonical Organization RBAC resolver;
2. one atomic Organization + canonical RBAC Create primitive;
3. one guarded existing-Organization RBAC backfill primitive;
4. one read-only PostgreSQL catalog compatibility guard;
5. NestJS Organization Create integration through the atomic RPC;
6. fail-closed RPC result validation;
7. persistent-audit sequencing after confirmed RBAC provisioning;
8. guarded Create compensation behavior;
9. focused Create/RBAC regression coverage.

The canonical Organization roles remain:

- `admin_org`;
- `gestor`;
- `operacional`;
- `consulta`.

Their canonical permission counts are:

- `admin_org` — 53;
- `gestor` — 39;
- `operacional` — 26;
- `consulta` — 12.

The canonical mapping contains 130 role-permission mappings.

## 2. Database changes

The new migration is:

`backend/src/database/migrations/20260923_p2_3a_5_organization_rbac_provisioning.sql`

It installs three database functions:

- `resolve_canonical_organization_rbac()`;
- `create_organization_with_canonical_rbac(...)`;
- `backfill_canonical_organization_rbac(...)`.

The migration is installation-only.

It does not execute production RBAC backfill.

It does not execute initial administrator bootstrap.

The Create primitive creates the Organization and all four canonical
organization-scoped roles within one database function execution.

The Create and Backfill primitives both validate the persisted role state
against the shared canonical resolver before returning success.

The new diagnostic is:

`backend/src/database/diagnostics/20260923_p2_3a_5_organization_rbac_catalog_guard.sql`

The diagnostic is read-only by contract:

- begins a transaction;
- performs catalog introspection only;
- contains no persistent DML or DDL;
- ends with `ROLLBACK`.

Its live execution remains pending.

## 5. Permissions implemented

Canonical Organization RBAC provisioning remains backend/database controlled.

The resolver has no direct execution authority for:

- `PUBLIC`;
- `anon`;
- `authenticated`;
- `service_role`.

The Organization Create RPC is executable only by `service_role`.

The controlled Backfill RPC is executable only by `service_role`.

All three privileged functions use:

`SECURITY DEFINER`

with fixed:

`search_path=pg_catalog`

The migration includes postflight validation of function security
configuration and effective execution privileges.

## 8. Problems found

The implementation process identified the following issues before publication:

1. the temporary migration generator initially constructed SQL but did not
   materialize the migration;
2. the initial generated Create/Backfill integrity check confirmed role count,
   names and scope but did not re-confirm persisted permission sets against the
   canonical resolver;
3. the historical `docs/supabase-schema.sql` is not authoritative for the
   current production schema;
4. the current Codespace cannot establish TCP connectivity to the PostgreSQL
   endpoint;
5. the published implementation contract still contains stale prose saying
   that the contract is pending publication, although Git proves that the
   contract exists in `origin/main`.

## 9. Problems corrected

The migration materialization step was completed.

Create and Backfill were strengthened to compare persisted canonical role
permissions against the same shared resolver used for provisioning.

The NestJS Create path was changed from a direct Organization insert to the
atomic RBAC provisioning RPC.

Fail-closed RPC result validation and domain error handling were added.

Focused and full backend regression coverage were executed successfully.

A dedicated catalog guard was created rather than treating historical schema
documentation as current database authority.

The catalog guard was corrected so that verified production types remain
strict while unverified operational column types are classified by compatible
type instead of assumed nullability.

## 11. Risks

The Create audit compensation currently deletes the just-created Organization
using guarded `id`, `updated_at` and active-state predicates.

The implementation must not rely on that deletion as complete Organization +
RBAC compensation until the live catalog guard proves the current role foreign
key uses `ON DELETE CASCADE`.

Therefore deployment remains blocked on live catalog validation.

Production RBAC backfill remains an exceptional controlled operation and must
not be coupled to migration installation.

The previous failed initial administrator bootstrap request is not reusable
authorization for another bootstrap attempt.
