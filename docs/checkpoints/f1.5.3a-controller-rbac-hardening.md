# F1.5.3a — Controller RBAC Hardening

## Status

Technically validated and ready for publication.

This checkpoint is a partial authorization-hardening checkpoint inside F1.5.
It does not close F1.5.3 or Foundation Phase 1.

## Objective

Close controller-level RBAC gaps where the existing authoritative permission
catalog already provides an unambiguous permission mapping.

No new permission identifiers were introduced.

## Changes

### ContractsController

Added explicit permission enforcement:

- POST /contracts
  - ORGANIZATION_CONTRACTS_CREATE
- GET /contracts
  - ORGANIZATION_CONTRACTS_VIEW
- GET /contracts/:id
  - ORGANIZATION_CONTRACTS_VIEW
- PUT /contracts/:id
  - ORGANIZATION_CONTRACTS_UPDATE
- DELETE /contracts/:id
  - ORGANIZATION_CONTRACTS_DELETE

Tenant isolation remains based on the validated organization context and
organization_id filtering already present in the service layer.

### DocumentsController

Added explicit permission enforcement where the existing permission semantics
are unambiguous:

- POST /documents
  - DOCUMENTS_UPLOAD
- GET /documents
  - DOCUMENTS_VIEW
- GET /documents/:id
  - DOCUMENTS_VIEW
- DELETE /documents/:id
  - DOCUMENTS_DELETE

Document license entitlement enforcement remains independent from RBAC.
The DocumentsService continues to require the document_management entitlement.

## Deliberately unresolved

### PUT /documents/:id

No DOCUMENTS_UPDATE permission exists in the current authoritative application
permission catalog.

This checkpoint does not map update to DOCUMENTS_UPLOAD or
DOCUMENTS_ARCHIVE_MANAGE because that would invent authorization semantics.

The endpoint remains an open F1.5.3 authorization gap pending an explicit
permission-model decision.

### Consumer Units

ConsumerUnitsController has tenant isolation through organization context and
organization_id filtering, but no authoritative consumer-unit CRUD permission
set was found in the current application permission catalog.

No permission was invented or borrowed from another domain.

This remains an open F1.5.3 authorization gap.

### Customers permission model

CustomersController currently uses ORGANIZATION_CONTRACTS_* permissions and
the application exposes CUSTOMERS_PERMISSIONS as aliases of those permissions.

This checkpoint preserves that existing behavior and does not reinterpret or
replace it without an explicit permission-model decision.

## Security model

This checkpoint preserves the layered authorization model:

Identity
→ Tenant / Membership Context
→ RBAC Permission
→ License Entitlement where applicable
→ Resource scoped by organization_id

License entitlement is not treated as a replacement for RBAC.

F1.5.3 remains open.

At minimum, remaining decisions include:
