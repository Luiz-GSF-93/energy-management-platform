# P2.3a — User Management Read Foundation

## Status

IMPLEMENTED AND LOCALLY VALIDATED — pending publication and controlled
production validation.

Phase 2 — Administration remains active.

P2.3 — User Management is active.

This checkpoint implements the organization-scoped User Management read
foundation only.

User Invite, Role Update, Affiliation Update and Membership Deactivation
remain outside this checkpoint.

P2.4 and later Phase 2 modules remain unauthorized.

## Objective

Establish the first User Management frontend slice over the existing
organization-scoped backend Users contract.

The implementation provides:

- typed User list API integration;
- typed User detail API integration;
- centralized organization Users View permission;
- organization-scoped Administration navigation;
- Users Administration route;
- loading, empty and error states;
- role presentation;
- affiliation presentation;
- membership status presentation.

No backend expansion is included.

No database migration is included.

## Existing backend read contract

The existing backend exposes organization-scoped User Management reads.

The read endpoints are:

`GET /api/v1/admin/users`

and:

`GET /api/v1/admin/users/:userId`

Both routes require:

`ORGANIZATION_USERS_VIEW`

The controller resolves the organization through the authenticated tenant
context.

The frontend therefore does not supply or select an organization identifier
for the read request.

## Safe User response

The existing backend composes the administrative User response from the
organization membership and user profile contracts.

The frontend typed representation preserves:

- `userId`;
- `email`;
- nullable `name`;
- `affiliationType`;
- `membershipStatus`;
- role identifier;
- role name;
- nullable invitation timestamp;
- nullable acceptance timestamp.

The frontend does not reconstruct role or membership integrity.

## Backend integrity boundary

The backend read contract validates membership, profile and role integrity
before composing a User view.

The backend fails closed for invalid conditions including:

- missing target membership;
- duplicate target membership;
- target membership mismatch;
- missing user profile;
- duplicate user profile;
- target profile mismatch;
- invalid organization membership;
- invalid organization role;
- invalid invitation timestamp;
- invalid acceptance timestamp;
- invalid user profile;
- invalid affiliation.

These integrity rules remain backend responsibilities.

## Membership status

Administrative User reads expose membership status.

The frontend does not filter the response to active memberships only.

Known lifecycle values include:

- `active`;
- `inactive`.

The read UI presents the membership status returned by the backend.

Unknown status values are not silently converted to another lifecycle state.

## Affiliation

The existing affiliation contract supports:

- `internal`;
- `external`.

The read UI presents these values as administrative labels.

This checkpoint does not modify affiliation.

Affiliation mutation remains deferred to a separately scoped P2.3 slice.

## Role

The backend returns an organization-scoped role containing:

- role identifier;
- role name.

The read UI presents the role name returned by the backend.

The frontend does not infer role from permission membership.

The frontend does not resolve role directly from the database.

## Permission boundary

The organization permission registry now contains:

`USERS_VIEW`

mapped to the existing backend:

`ORGANIZATION_USERS_VIEW`

The Users route evaluates visibility through the existing `hasPermission()`
boundary.

This is presentation authorization only.

Backend authorization remains authoritative.

## Navigation scope

User Management is organization-scoped.

The backoffice navigation model now supports explicit navigation scope.

The Users navigation entry declares:

`scope: 'organization'`

The Sidebar passes the current authentication scope into the navigation
filter.

As a result:

- organization-scoped actors may see Users when they hold Users View;
- global Platform Admin context does not receive the organization-scoped Users
  navigation item merely because it is globally authenticated.

No artificial organization membership is created for a global actor.

## Users interface

The Administration Users route is:

`/backoffice/users`

The page requires an organization authentication context before loading User
Management data.

The page provides:

- loading state;
- empty state;
- API error state;
- missing organization-context state;
- missing permission state;
- manual refresh.

Each rendered User card presents:

- name when available;
- email;
- role;
- affiliation;
- membership status.

Inactive memberships are not hidden by the frontend.

## Initial loading behavior

Initial User loading is synchronized with the current authorization state.

The effect performs the asynchronous Users request directly and uses
cancellation state to avoid applying stale results after cleanup.

The manual refresh path reuses the explicit `loadUsers()` action.

The implementation does not suppress or disable the React Hooks lint rule.

## Production validation boundary

P2.3a must be published and deployed before production validation.

Production validation must remain read-only.

The production gate must verify an organization-scoped actor with
`ORGANIZATION_USERS_VIEW`.

The gate must confirm:

- organization-context authentication succeeds;
- Users View permission is present;
- Users list returns HTTP 200;
- list response follows the safe User response contract;
- a controlled list item can be read through the detail endpoint;
- detail returns HTTP 200;
- detail response follows the same safe User response contract.

Production validation must not:

- invite a User;
- change a role;
- change affiliation;
- deactivate a membership;
- reactivate a membership.

## Security boundary

Frontend Users View is presentation authorization only.

Backend permission enforcement remains authoritative.

Organization membership remains the access boundary.

Profile, role, affiliation and membership integrity remain backend
responsibilities.

No database authority is moved to the frontend.

No credential is introduced by this checkpoint.
