# F1.2.4 — Organization User Invite Decision Brief

## Status

APPROVED FOR DESIGN — implementation not yet authorized.

## Objective

Add an organization-scoped administrative invite workflow without weakening
the established identity, membership, tenant, role, or audit boundaries.

## Endpoint contract

Planned endpoint:

`POST /admin/users/invite`

Required permission:

`ORGANIZATION_USERS_INVITE`

Planned input:

- `email`
- `name`
- `roleId`
- `affiliationType`

The organization ID must never be accepted from the request body.

Actor user ID and organization ID come from validated tenant context.
IP address and user-agent come from the request when available.

## Authorities

The lifecycle model remains:

- Supabase Auth is the identity authority.
- `user_profiles` stores profile data and active-organization pointer data.
- `organization_members` is the organization-access authority.
- `organization_members.role_id` is the organization-role authority.
- `user_roles` is not used for organization membership provisioning.
- persistent audit is mandatory for successful invite provisioning.

Creating or finding an identity does not itself grant organization access.

## Role validation

Before granting organization membership, the requested role must:

- exist exactly once;
- match the requested `roleId`;
- belong to the actor's validated current organization;
- have `scope = organization`.

Global roles and roles from another organization are rejected.

## Affiliation validation

`affiliationType` must use the existing supported contract:

- `internal`
- `external`

Affiliation does not grant organization access.

## State machine

### Existing active membership

If the resolved identity already has an `active` membership in the actor's
current organization, the invite performs no mutation.

The operation must return an explicit conflict/idempotent result according to
the implementation design, without modifying role, profile, or membership.

Invite must not be used as an implicit role-update operation.

### Existing inactive membership

Invite does not reactivate an inactive membership.

Reactivation is a distinct lifecycle transition and requires its own explicit
authorization, audit, concurrency, and compensation contract.

### Existing identity without membership in current organization

Reuse the existing identity.

Do not create a duplicate authentication identity.

If its profile is valid, create only the organization membership required for
the current organization.

Do not modify memberships belonging to other organizations.

### Existing identity with missing profile

Fail closed.

The first invite implementation must not silently reconstruct a missing profile
and grant organization access in the same operation.

This state is treated as incomplete provisioning/data integrity requiring a
separately designed recovery path.

### New identity

The implementation may use the supported Supabase administrative invitation
capability to create/invite a new identity.

After identity creation is confirmed, the workflow must provision the required
profile and organization membership explicitly unless a proven runtime
mechanism guarantees that provisioning.

No such automatic provisioning mechanism is assumed by this decision.

## Membership creation

A newly created membership must be scoped to:

- resolved target user ID;
- actor's validated current organization;
- validated organization role.

The implementation must not write a global role assignment.

The exact initial membership status and invited/accepted timestamp semantics
must be fixed by the implementation design before writes are authorized.

## Active organization pointer

`user_profiles.organization_id` is not organization-access authority.

For an existing multi-organization user, invite must not freely replace the
user's current active-organization pointer.

Organization switching remains governed by the existing validated switching
flow.

For a newly provisioned user with no active organization pointer, initial
pointer semantics must be explicitly defined by the implementation design.

## Identity lookup

The installed Supabase SDK exposes administrative user listing and
get-user-by-ID capabilities but no discovered dedicated get-user-by-email
operation.

Email lookup therefore must not be treated as an atomic SDK primitive.

The implementation design must define bounded lookup, normalization,
pagination, duplicate handling, and fail-closed behavior before identity writes
are authorized.

## Email normalization

Email comparison must use a single documented normalization rule.

At minimum, surrounding whitespace and case comparison must be handled
consistently.

The system must not implement provider-specific transformations such as
removing dots or plus-addressing unless separately justified.

## Compensation principle

There is no assumed distributed transaction spanning Supabase Auth and the
application tables.

Compensation is therefore ownership-aware.

A failed invite operation may compensate only resources proven to have been
created by that same operation.

It must never delete or overwrite a pre-existing identity, profile, membership,
role assignment, or organization pointer as generic rollback behavior.

## Failure model

Examples:

- role validation failure: no identity/profile/membership write;
- identity lookup ambiguity: fail closed, no write;
- existing inactive membership: no write;
- new identity creation failure: no application-table write;
- profile creation failure after new identity creation: compensate only the
  newly created identity when ownership can be proven;
- membership creation failure after new identity/profile creation: compensate
  only resources created by the current operation, in reverse order;
- audit failure after successful provisioning: execute the separately specified
  guarded compensation sequence;
- any unconfirmed compensation: CRITICAL integrity failure requiring
  administrative intervention.

## Persistent audit

Successful invite provisioning requires a dedicated persistent audit primitive.

The audit must identify:

- actor user ID;
- organization ID;
- target user ID;
- normalized target email or an appropriately minimized representation;
- resulting membership ID;
- role ID;
- affiliation type;
- provisioning path, such as new identity or existing identity;
- IP address when available;
- user-agent when available;
- status and timestamp.

Sensitive authentication material must never be recorded.

## Public register compatibility

The existing public `/auth/register` flow remains unchanged in F1.2.4.

Administrative invite must not be implemented by changing public registration
semantics as an unrelated side effect.

## Schema position

The repository's legacy schema document is not treated as sufficient authority
for the current live identity/membership schema.

No migration is authorized by this decision brief.

Any required database constraint or schema change must be justified by a
separate migration checkpoint using current schema evidence.

## Explicit non-goals

F1.2.4 does not authorize:

- hard deletion of existing identities;
- automatic reactivation;
- Platform Admin bypass;
- generic role administration;
- permission administration;
- public-register redesign;
- frontend invite UI;
- mutation of another organization;
- use of `user_roles` for organization access;
- free mutation of `user_profiles.organization_id`;
- schema/RLS changes without a separate checkpoint.

## Implementation split

F1.2.4 will proceed sequentially:

1. F1.2.4a — invite audit primitive.
2. F1.2.4b — invite functional design and exact state/compensation contract.
3. F1.2.4c — functional implementation and focused tests.
4. broad regression.
5. controlled publication.
6. closeout documentation.

No later subphase begins until the previous checkpoint is validated and
published.
