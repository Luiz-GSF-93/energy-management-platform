# F1.5.7 — License Permission Assignment Decision

## Status

DESIGN APPROVED FOR VALIDATION.

No database or runtime mutation is authorized by this document alone.

Phase 1 remains open.
Phase 2 remains unauthorized.

## Objective

Define the authoritative role assignment matrix for the existing License
Foundation RBAC vocabulary.

The permission vocabulary already exists:

- organization.licenses.view
- organization.licenses.create
- organization.licenses.update

No organization.licenses.delete permission exists.

## Existing architecture

License authorization occurs after authenticated identity and validated
tenant/platform context.

RBAC and license entitlement are independent concerns.

Permission possession answers whether the actor may perform the class of
administrative operation.

License entitlement answers whether the organization may use a licensed
capability.

These responsibilities must remain separate.

## Assignment authority

`roles.permissions` JSONB remains the effective runtime permission assignment
authority.

`role_permissions` is not the effective assignment source and must remain
untouched by this checkpoint.

## Historical constraint

F1.4 intentionally did not automatically grant License permissions to roles.

At that checkpoint, role-permission administration was explicitly deferred as
a separate concern.

Therefore the current assignment matrix must be classified explicitly rather
than inferred to be authoritative merely because it exists in the database.

## Current validated matrix

The current database state is:

| Role | VIEW | CREATE | UPDATE |
| --- | --- | --- | --- |
| admin_platform | grant | grant | grant |
| admin_org | grant | grant | grant |
| gestor | grant | deny | deny |
| operacional | deny | deny | deny |
| consulta | deny | deny | deny |

There are 15 role/permission combinations:

- 7 grants
- 8 denials

## Role decision

### admin_platform

Grant VIEW, CREATE and UPDATE.

Platform administration requires full visibility and controlled lifecycle
management capability.

This does not create an RLS bypass and does not replace explicit platform or
tenant context validation.

### admin_org

Grant VIEW, CREATE and UPDATE.

Organization administration owns the administrative license lifecycle within
the validated organization boundary.

### gestor

Grant VIEW only.

The manager role may inspect the organization's effective license and
capabilities but does not receive authority to create or mutate the license
lifecycle.

CREATE and UPDATE remain administrative operations.

### operacional

Grant no License Foundation administration permission.

Operational business capabilities must be controlled through their own RBAC
permissions plus entitlement evaluation.

Operational use of a licensed capability does not require permission to view
or administer the license record itself.

### consulta

Grant no License Foundation administration permission.

Read-only business access does not imply access to administrative license
configuration.

Licensed business functionality, where applicable, remains governed by the
relevant business permission plus entitlement evaluation.

## Delete decision

No organization.licenses.delete permission is introduced.

License termination remains a controlled lifecycle transition.

Hard deletion remains outside the License Foundation contract.

## Security properties

The approved matrix preserves:

- least privilege;
- separation between license administration and licensed business usage;
- separation between RBAC and entitlement;
- organization tenant boundaries;
- persistent audit requirements for CREATE and UPDATE;
- lifecycle history.

## Required implementation state

The approved implementation state is exactly:

- admin_platform: VIEW + CREATE + UPDATE
- admin_org: VIEW + CREATE + UPDATE
- gestor: VIEW
- operacional: none
- consulta: none

The currently observed database assignment already matches this matrix.

Therefore no permission grant or revocation migration is required if final
validation confirms the state has not drifted.

## Validation requirements

Closeout validation must prove:

1. exactly three License Foundation permission records exist;
2. their UUIDs match the application constants;
3. all 15 role/permission combinations match the approved matrix;
4. exactly 7 combinations are grants;
5. exactly 8 combinations are denials;
6. no unknown permission UUID exists in the five target roles;
7. role_permissions remains empty;
8. organization.licenses.delete does not exist;
9. controller metadata still enforces VIEW, CREATE and UPDATE correctly;
10. backend regression and build remain green.

## Non-goals

F1.5.7 does not:

- create new permissions;
- introduce license DELETE;
- modify role_permissions;
- modify License APIs;
- modify TenantContext;
- modify RLS;
- modify entitlement semantics;
- grant business capabilities through License permissions;
- begin Phase 2.

## Decision

Adopt the currently observed License permission assignment matrix as the
explicit Foundation authorization contract.

If validation confirms the matrix is unchanged, F1.5.7 requires documentation
only and no database migration.

Phase 1 remains open.
Phase 2 must not begin.
