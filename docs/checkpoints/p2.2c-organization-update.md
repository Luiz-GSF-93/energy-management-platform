# P2.2c — Organization Update

## Status

IMPLEMENTED AND LOCALLY VALIDATED — pending publication and controlled
production validation.

Phase 2 — Administration remains active.

P2.2 — Organizations remains open.

This checkpoint implements Organization update only.

Organization deletion remains outside this checkpoint.

P2.3 — User Management remains unauthorized.

## Objective

Add the Organization update experience to the existing Administration
Organizations module while preserving the architecture established by P2.1,
P2.2a and P2.2b.

The implementation reuses the existing platform-scoped backend mutation
contract.

No backend expansion is included.

No database migration is included.

## Existing backend contract

The existing backend exposes:

`PATCH /api/v1/admin/organizations/:id`

The operation requires:

`PLATFORM_ORGANIZATIONS_UPDATE`

The update request accepts:

- optional `name`;
- optional `description`.

If `name` is supplied, it cannot be blank.

The backend:

- loads the existing Organization before mutation;
- trims a supplied name;
- trims a supplied description;
- normalizes an empty supplied description to `null`;
- updates only the supplied mutable fields;
- updates `updated_at`;
- excludes soft-deleted Organizations;
- returns the resulting Organization.

The backend remains the mutation authorization authority.

## Audit and compensation contract

Organization Update uses persistent mutation auditing.

The audit record receives the exact Organization state before mutation and
the resulting Organization state after mutation.

If persistent audit fails after the write, the service attempts to restore:

- the previous name;
- the previous description;
- the previous `updated_at`.

The compensation operation is constrained by:

- Organization identifier;
- the `updated_at` written by the failed operation;
- `deleted_at IS NULL`.

This prevents compensation from blindly overwriting a later concurrent
change.

## Frontend API contract

The centralized Organizations API now exposes:

- `UpdateOrganizationRequest`;
- `updateOrganization()`.

`updateOrganization()` delegates to the existing centralized `apiRequest`
boundary.

The request uses:

- method `PATCH`;
- encoded Organization identifier;
- JSON serialization owned by the API client;
- Bearer authentication owned by the API client.

Components do not call `fetch` directly.

## Permission boundary

The frontend platform permission registry now includes:

`ORGANIZATIONS_UPDATE`

with the existing backend permission identifier.

The Organizations page evaluates this permission through the existing
`hasPermission()` authentication boundary.

The Edit action is rendered only when the current global access context
contains the Organization Update permission.

This is presentation authorization only.

Backend authorization remains authoritative.

## Update interface

Update is implemented inline within the existing Organizations collection.

An authorized user can enter edit mode for an Organization card.

The edit state is initialized from the currently loaded Organization:

- current name;
- current description.

The interface provides:

- editable name;
- editable description;
- Save action;
- Cancel action;
- submitting state;
- mutation error state.

Cancel exits edit mode without mutation.

## No-op protection

Before sending an Update request, the frontend compares the normalized edit
state with the currently loaded Organization.

Only changed fields are included in the PATCH payload.

If neither mutable field changed, the frontend exits edit mode without
issuing an Update request.

This avoids creating an unnecessary persistent mutation and audit event.

## Successful update behavior

After a successful Update:

- edit mode is closed;
- temporary edit state is cleared;
- the Organizations collection is reloaded from the backend.

The refreshed backend collection remains authoritative for rendered state.

## Production validation boundary

Organization Update is a real persistent and audited mutation.

No production Update is performed by this implementation checkpoint before
publication.

After deployment, controlled production validation must operate only on the
Organization created specifically by the P2.2b production validation.

Existing operational Organizations must not be modified by the P2.2c
validation.

The validation must:

- identify the P2.2b validation Organization without printing its identifier;
- verify the Update permission;
- perform one intentional PATCH;
- read the resulting Organization;
- verify the resulting state;
- perform no Delete operation;
- print no token value.

## Security boundary

Frontend Update visibility does not replace the backend permission check.

No credential is introduced into source control.

No database authority is moved to the frontend.

Delete remains unavailable in the frontend.
