# P2.1b — API/Auth Context Foundation

## Status

IMPLEMENTED AND VALIDATED — pending publication.

Phase 2 — Administration remains active.

This checkpoint closes the API, authentication and organization-context
foundation slice of P2.1.

P2.1 remains open for its remaining foundation closeout work.

## Objective

Replace provisional component-level authentication integration with a
centralized frontend API/session/context boundary that relies on the
authoritative backend authentication and tenant-context contract.

This checkpoint does not implement Organizations, User Management, Licenses,
Settings or Dashboard business functionality.

No database migration is included.

## Centralized API boundary

P2.1b introduced a centralized frontend API client.

The API client owns:

- `NEXT_PUBLIC_API_URL` resolution;
- JSON request serialization;
- Bearer authorization headers;
- normalized HTTP errors;
- authenticated and unauthenticated request modes.

Direct `fetch()` calls were removed from pages, providers and presentation
components.

The centralized API client is the only current `fetch()` owner under
`frontend/app`.

## Session boundary

P2.1b introduced a dedicated session abstraction.

The session abstraction is the only current owner of browser authentication
storage under `frontend/app`.

Presentation components no longer read or write `localStorage` directly.

The existing Bearer-token protocol is preserved.

This checkpoint does not claim that browser `localStorage` is the permanent
long-term authentication-storage architecture.

Migration to an HttpOnly-cookie model would require a separate backend and
browser-security design covering protocol, CORS and CSRF behavior.

## AuthProvider

A root `AuthProvider` now owns frontend authentication state.

The provider distinguishes:

- loading;
- authenticated;
- unauthenticated;
- validation error.

Authentication is not considered established merely because an access token
exists locally.

A stored token must successfully resolve `/api/v1/auth/context` before the
provider enters the authenticated state.

HTTP 401 and 403 responses invalidate the local session.

Transient validation failures do not silently classify the user as
unauthenticated.

They enter a fail-closed error state with an explicit retry path while
preserving the token for revalidation.

## Login flow

The login page now uses the centralized authentication provider.

The flow is:

1. submit credentials through the centralized API layer;
2. receive a Supabase access token from the existing backend login contract;
3. store the token through the session abstraction;
4. resolve `/api/v1/auth/context`;
5. enter authenticated state only after successful context validation;
6. redirect to the Backoffice.

If context validation fails after login, the newly established local session
is cleared and authentication fails closed.

## Protected-route behavior

`ProtectedRoute` no longer treats token presence as sufficient proof of an
authenticated Administration session.

It consumes the `AuthProvider` state.

Unauthenticated state redirects to login.

Loading state blocks protected content while identity, organization and
permission context are being validated.

Transient validation errors block protected content and expose an explicit
retry action.

Backend authorization remains authoritative.

## Authoritative auth-context contract

During P2.1b validation, an initial frontend type assumption was found to be
incorrect.

The frontend initially assumed organization names and `role_id` were present
on `currentOrganization`.

Backend implementation, backend regression tests and the production endpoint
were reconciled before publication.

The accepted contract is:

### `organizations[]`

Each organization membership summary contains:

- `id`;
- `role`;
- `role_id`.

It does not expose permissions.

### `currentOrganization`

The current organization contains:

- `id`;
- `role`;
- `permissions`.

It does not currently expose organization name or `role_id`.

The frontend contract was corrected to match this authoritative shape.

No backend change was required.

## Permission boundary

The frontend `hasPermission()` helper evaluates only:

`currentOrganization.permissions`.

Permissions from non-current organizations are not represented in the
frontend context contract.

Frontend permission checks remain presentation controls only.

They do not replace backend RBAC, TenantContext or RLS enforcement.

## Organization-context switching

The existing backend organization-switch contract was integrated into the
frontend API/context foundation.

The backend switch response is explicitly typed.

A successful switch does not require a replacement access token.

The frontend flow is:

1. request the backend organization switch;
2. keep the existing access token;
3. resolve `/api/v1/auth/context` again;
4. replace frontend context with the newly authoritative context.

The frontend does not derive new permissions from the switch response.

If a switch request fails, the provider attempts to resolve the authoritative
context again before deciding whether the session remains usable.

This avoids guessing which organization is active after a failed switch or
backend rollback path.

## Organization selector

The Backoffice Sidebar exposes the organization selector only when the
authenticated context contains more than one valid organization membership.

The current context endpoint does not provide organization names in the
membership summaries.

The frontend therefore does not fabricate organization names.

A future friendly-name requirement must be satisfied by an explicit backend
contract expansion rather than an unsupported frontend assumption.

## Production validation

P2.1b was validated against the deployed production authentication API using
a test user credential entered interactively.

No credential or access-token value was recorded.

Production validation confirmed:

- login request completed successfully;
- login returned HTTP 201;
- an access token was present;
- `/api/v1/auth/context` returned HTTP 200;
- root auth-context contract matched;
- user contract matched;
- organization membership item contract matched;
- current-organization contract matched;
- current organization was present in the returned memberships;
- non-current organization summaries did not expose permissions;
- no context values or access token were printed.

The validation user had one active organization membership.

Therefore:

- organization switching was not executed;
- no organization-context mutation was performed;
- no artificial membership was created for testing.

The switch implementation remains covered by the existing backend contract
and frontend static/type/build validation, but P2.1b does not claim a
production multi-organization switch execution.

## Infrastructure ownership validation

Final validation confirmed:

- browser storage owner: `frontend/app/lib/auth/session.ts`;
- API base-URL owner: `frontend/app/lib/api/client.ts`;
- `fetch()` owner: `frontend/app/lib/api/client.ts`;
- presentation components contain no direct browser-storage access;
- presentation components contain no direct `fetch()` calls;
- providers contain no direct browser-storage access;
- auth response contracts do not expose `Promise<unknown>`.

The generic API request body remains typed as `unknown` intentionally because
the centralized client accepts multiple request payload shapes.
