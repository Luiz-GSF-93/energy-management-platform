# F1.8 — Contract persistence

The contracts API now maps the request to actual energy_contracts columns, requires contract type, volume and price, derives the customer from a tenant-scoped consumer unit, and checks optional management-contract ownership. Creation continues to require the free_market_management entitlement.

API dates use YYYY-MM-DD. Invalid calendar dates and reversed validity are rejected. The database response retains snake_case. Optional notes are stored in a new nullable text column; existing rows and grants are preserved. Contract numbers retain the database's existing global uniqueness constraint.

New contracts default to DRAFT. Create may explicitly choose ACTIVE. Only drafts can be edited or deleted; activation freezes the record. The mutation also filters status=DRAFT to prevent a concurrent activation from being overwritten. APPROVED cannot be assigned through this generic endpoint. A dedicated amendment/versioning workflow is still pending.

Required POST fields: consumerUnitId, contractNumber, contractType, contractedVolumeMwh, currentPrice, startDate, endDate. Optional: status, energyType, supplierId, energySource, adjustmentIndex, adjustmentFrequency, adjustmentDate, managementContractId, notes. PUT accepts endDate, contractedVolumeMwh, currentPrice, status and notes for drafts. Fees minimumSavings/honorariePercentage are rejected as unknown fields; financial configuration belongs to management_contracts and is not fabricated or silently discarded. Full management-contract CRUD and fee calculations remain pending.

Validation before release: 42 Jest suites / 421 tests and backend build passed locally; 18 compiled-service SQL checks passed in PGlite. The SQL adapter tests database payloads, not Supabase HTTP/auth or a real two-user browser session. PostgreSQL 17, production migration and rollout must be verified before declaring deployment complete.
