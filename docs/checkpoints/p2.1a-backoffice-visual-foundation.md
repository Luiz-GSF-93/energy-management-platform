# P2.1a — Backoffice Visual Foundation

## Status

IMPLEMENTED AND VALIDATED — pending publication.

Phase 2 — Administration remains active.

This checkpoint closes only the visual-foundation slice of P2.1.

P2.1 authentication, API and organization-context integration remain
separate follow-up work.

## Objective

Establish the reusable visual foundation required by the Administration
frontend before business modules are implemented.

This checkpoint does not implement Organizations, User Management, Licenses,
Settings or real Dashboard aggregation.

## Implemented foundation

P2.1a introduced:

- global design tokens and base styles;
- reusable Button primitive;
- reusable Input primitive;
- reusable Card primitive;
- reusable Alert primitive;
- reusable LoadingState;
- reusable EmptyState;
- reusable ErrorState;
- reusable Backoffice shell;
- responsive Backoffice navigation structure;
- migrated login presentation;
- migrated protected-route loading presentation;
- migrated Backoffice sidebar;
- migrated Dashboard shell.

Global styles are imported by the root application layout.

## Styling architecture

The frontend previously contained Tailwind-style utility classes but did not
declare an owned Tailwind toolchain in `frontend/package.json`.

A root-level Tailwind installation was resolvable accidentally and was not
accepted as a frontend dependency contract.

P2.1a therefore establishes the new visual foundation using conventional
global CSS and explicit design tokens without introducing a new styling
runtime dependency.

The historical `frontend/tailwind.config.ts` remains untouched in this
checkpoint.

Its eventual removal is deferred until the remaining legacy frontend surface
has been reconciled.

## Login hardening

The login page was migrated to the new Design System primitives.

The explicit test credential previously rendered by the login page was
removed.

The login flow now also fails explicitly when the public API base URL is not
configured or when the authentication response does not contain a usable
access token.

The existing direct authentication integration remains intentionally
unchanged in architectural terms:

- direct `fetch`;
- direct `NEXT_PUBLIC_API_URL` access;
- direct `localStorage` token persistence.

Those concerns belong to P2.1b.

## Backoffice shell

A reusable `BackofficeShell` now owns the common Administration layout.

The Sidebar was migrated away from unowned utility styling.

Navigation entries pointing to frontend routes that do not exist were
removed.

Only the currently implemented Dashboard route remains exposed.

Business-module navigation will be introduced only when the corresponding
Phase 2 module and permission-aware navigation contract exist.

## Dashboard placeholder removal

The previous Dashboard rendered hardcoded production-like metrics.

Those values were removed.

Until real authorized backend aggregation contracts are implemented, the
Dashboard presents an explicit empty state explaining that indicators are not
yet configured.

P2.1a does not claim that the administrative Dashboard business functionality
is implemented.

## Security and authorization boundary

P2.1a does not change backend authentication, TenantContext, RBAC, RLS,
license entitlement or persistent-audit behavior.

Frontend presentation remains non-authoritative for access control.

No database migration was created.

No backend source was modified.

No dependency was added or upgraded.

## Deferred P2.1b boundary

The following existing frontend concerns remain intentionally deferred to
P2.1b — API/Auth Context Foundation:

- centralized typed API client;
- authentication/session abstraction;
- `/api/v1/auth/context` integration;
- organization-context integration;
- permission-context integration;
- permission-aware navigation;
- centralized unauthorized/forbidden handling;
- removal of direct page/component access to authentication storage;
- replacement of the provisional `ProtectedRoute` token-presence check.

P2.1a must not be interpreted as validation of the current `localStorage`
session architecture.

## Validation

- exposed test-credential scan: pass;
- provisional navigation/metric scan: pass;
- TypeScript validation: pass;
- Next.js production build: pass;
- production npm audit: zero vulnerabilities;
- `git diff --check`: pass.

## Decision

P2.1a — Backoffice Visual Foundation is implemented and validated.

The visual foundation is accepted as the base for subsequent Administration
frontend work.

P2.1 remains open.

The next authorized slice after publication is P2.1b — API/Auth Context
Foundation.

P2.2 — Organizations must not begin before the P2.1 foundation boundary is
completed and validated.

## Publication state

P2.1a is pending review and publication.

Until this checkpoint is committed and published to `origin/main`, P2.1b
implementation must not begin.
