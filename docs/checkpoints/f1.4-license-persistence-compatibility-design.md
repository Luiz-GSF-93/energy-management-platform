# F1.4 — License Persistence Compatibility Design

## 1. Status

Design checkpoint.

No database mutation is authorized by this document.

This checkpoint translates the F1.3 License Foundation Decision Brief into
a compatibility design for the authoritative runtime database discovered
during F1.4a.

---

## 2. Governing architecture

License evaluation remains downstream from identity, tenant membership and
RBAC:

Identity -> Membership/Tenant -> RBAC -> License -> Entitlement -> Resource

A license MUST NOT:

- establish tenant identity;
- grant organization membership;
- replace RBAC;
- grant a role;
- bypass authorization;
- permit cross-organization access.

Backend authorization remains authoritative.

---

## 3. Authoritative discovery result

F1.4a proved that the authoritative runtime database already contains a
`licenses` relation.

The relation is currently empty.

Therefore F1.4 MUST preserve and evolve the existing domain rather than
create a competing license persistence model.

No second license table is authorized.

---

## 4. Proven existing contract

The authoritative PostgREST/OpenAPI contract exposes these columns:

- id
- organization_id
- license_type
- documents_limit
- documents_used
- renewal_date
- active
- created_at
- updated_at
- status
- max_consumer_units
- document_management
- advanced_analytics
- report_generation
- free_market_management
- start_date
- end_date

The existing model already contains both commercial limits and feature
capabilities.

These fields MUST be preserved for compatibility.

---

## 5. Proven required fields

The authoritative OpenAPI contract marks these fields as required:

- id
- organization_id
- license_type
- documents_limit
- renewal_date

The persistence/API implementation MUST respect this existing contract unless
a later reviewed migration intentionally and compatibly changes it.

---

## 6. Proven defaults

The authoritative OpenAPI contract exposed these defaults:

- id: gen_random_uuid()
- active: true
- documents_used: 0
- max_consumer_units: 10
- document_management: true
- advanced_analytics: false
- report_generation: false
- free_market_management: false
- status: ACTIVE
- created_at: now()
- updated_at: now()

These defaults are existing compatibility behavior.

They MUST NOT be silently replaced.

---

## 7. Proven primary key

`licenses.id` is exposed as the primary key.

No alternative identity model is required for F1.4.

---

## 8. Unproven database constraints

F1.4a could NOT authoritatively prove the following through the available
read-only interfaces:

- foreign key from licenses.organization_id to organizations.id;
- uniqueness constraints;
- partial uniqueness constraints;
- check constraints;
- indexes;
- row-level-security enablement;
- row-level-security policies.

Absence from OpenAPI MUST NOT be interpreted as absence from PostgreSQL.

Any migration affecting these concerns MUST inspect the authoritative catalog
before executing DDL.

---

## 9. Organization ownership

The license domain is organization-owned.

`organization_id` is the tenant ownership field.

All backend reads and mutations MUST derive organization scope from validated
TenantContext.

The client MUST NOT be trusted to select an arbitrary organization by sending
`organization_id` in a mutation payload.

Cross-organization license access is prohibited.

---

## 10. Existing capabilities

The following existing capability fields MUST be preserved:

- document_management
- advanced_analytics
- report_generation
- free_market_management

F1.4 does not introduce a generic feature catalog.

These fields form the compatibility entitlement surface for the current
license model.

A future plan/feature catalog may be introduced only through a separate
reviewed checkpoint.

---

## 11. Existing quotas

The following existing quota/usage fields MUST be preserved:

- documents_limit
- documents_used
- max_consumer_units

F1.4 MUST NOT replace these fields with a generic quota subsystem.

Usage mutation semantics are outside the persistence migration itself and
must be enforced by the appropriate domain services.

---

## 12. License lifecycle

F1.3 defines the normalized lifecycle states:

- active
- suspended
- expired
- cancelled

The existing table exposes both:

- status
- active

This is a compatibility concern.

F1.4 MUST NOT remove either field.

The backend normalized lifecycle is authoritative for new license-domain
code.

---

## 13. Status normalization

Existing database status values may use a different case convention.

The discovered default is:

ACTIVE

The backend MUST normalize status comparisons without assuming that stored
historical values already use lowercase.

New persistence code SHOULD use one canonical database representation after
the accepted-value contract is proven.

No status rewrite is authorized by this design checkpoint.

---

## 14. active compatibility field

The existing `active` boolean is retained.

It MUST NOT become an independent source of truth that can contradict the
normalized lifecycle.

For new backend mutations, lifecycle transition logic MUST update `status`
and the compatibility `active` value together.

Intended compatibility mapping:

- active -> active = true
- suspended -> active = false
- expired -> active = false
- cancelled -> active = false

Existing records MUST NOT be bulk rewritten merely to establish this mapping.

---

## 15. Validity interval

The existing table exposes:

- start_date
- end_date
- renewal_date

F1.3 requires a validity interval with a start and optional end.

For compatibility:

- start_date represents the beginning of license validity;
- end_date represents the optional end of license validity;
- renewal_date is preserved as an existing commercial/renewal field.

`renewal_date` MUST NOT be silently reinterpreted as `end_date`.

---

## 16. Effective license

An effective license is not determined by RBAC.

A candidate effective license MUST belong to the validated organization.

At minimum, evaluation must consider:

- organization_id;
- normalized lifecycle status;
- active compatibility value;
- start_date;
- end_date.

`renewal_date` remains distinct from validity end.

Exact date-boundary semantics MUST be covered by tests before production use.

---

## 17. Cardinality

F1.3 requires at most one effective active license per organization while
allowing historical licenses to coexist.

The current database uniqueness/index implementation remains unproven.

Therefore application-only enforcement is insufficient for final integrity.

Before any concurrency-sensitive create path is released, database-level
enforcement MUST be proven or added through a reviewed additive migration.

---

## 18. Creation behavior

License creation requires:

- authenticated actor;
- validated TenantContext;
- ORGANIZATION_LICENSES_CREATE;
- organization scope enforced by backend;
- validated input;
- no ambiguous effective license for the organization;
- persistent audit.

No automatic default license provisioning is introduced.

No organization_id supplied by an untrusted client may override TenantContext.

---

## 19. Update behavior

License updates require:

- authenticated actor;
- validated TenantContext;
- ORGANIZATION_LICENSES_UPDATE;
- organization ownership verification;
- validated transition/input;
- persistent audit.

Updates MUST NOT silently change organization ownership.

Validated historical records MUST not be overwritten outside explicit domain
rules.

---

## 20. Read behavior

License reads require:

- authenticated actor;
- validated TenantContext;
- ORGANIZATION_LICENSES_VIEW;
- organization-scoped backend filtering.

A client can only receive license information belonging to its own validated
organization and permitted by the application exposure contract.

---

## 21. No hard delete

Although generic PostgREST metadata exposes DELETE for the relation, F1.4
does not authorize hard deletion.

License termination occurs through lifecycle transition.

No application DELETE endpoint for licenses is introduced by F1.4.

---

## 22. Audit

License mutations MUST generate persistent audit records.

Audit must capture, as available:

- actor user;
- organization;
- action;
- timestamp;
- IP address;
- user agent;
- license record identifier;
- previous values;
- resulting values;
- origin/version context.

Audit failure handling must follow the established mutation/audit integrity
pattern.

---

## 23. Concurrency

Read-then-write checks alone are insufficient to guarantee the
one-effective-license invariant under concurrent requests.

Before production create is enabled, F1.4 MUST establish database-backed
concurrency protection.

The exact mechanism depends on authoritative PostgreSQL constraint/index
discovery.

No constraint shape is assumed by this document.

---

## 24. Migration strategy

F1.4 uses additive compatibility migration only when required.

A migration MUST NOT:

- drop the licenses table;
- recreate the licenses table destructively;
- remove existing capability fields;
- remove existing quota fields;
- rename existing fields without a compatibility layer;
- hard-delete license records;
- alter unrelated tables unnecessarily.

Before executing DDL, the migration procedure MUST inspect authoritative
PostgreSQL metadata for existing FK, unique, check, index and RLS definitions.

Migration SQL MUST be idempotent or explicitly guarded against duplicate
objects where practical.

---

## 25. RLS boundary

Backend tenant enforcement is mandatory regardless of RLS.

RLS state is currently unproven.

F1.4 MUST NOT assume RLS exists merely because Supabase/PostgREST is used.

Any RLS change requires explicit policy review and regression testing.

---

## 26. API foundation target

F1.4 may introduce organization-scoped backend primitives for:

- read current/effective license;
- create license;
- update license;
- lifecycle transition;
- evaluate effective license.

These APIs must use the existing permission catalog:

- ORGANIZATION_LICENSES_VIEW
- ORGANIZATION_LICENSES_CREATE
- ORGANIZATION_LICENSES_UPDATE

No license DELETE permission is introduced.

---

## 27. Entitlement evaluation

Existing capability fields may be exposed through a backend entitlement
evaluation primitive.

Entitlement evaluation MUST happen after:

1. authentication;
2. membership/tenant validation;
3. RBAC authorization;
4. effective-license resolution.

A capability flag never grants tenant or RBAC access by itself.

---

## 28. Out of scope

F1.4 does not implement:

- billing;
- payment processing;
- plan catalog administration;
- generic feature catalog;
- generic quota framework;
- frontend license management;
- automatic subscription renewal;
- automatic license provisioning;
- Platform Admin bypass;
- role administration;
- permission administration;
- hard deletion;
- cross-organization access.

---

## 29. Required pre-DDL gate

Before any license schema migration is executed, the implementation checkpoint
MUST obtain authoritative evidence for:

- current licenses foreign keys;
- current unique constraints;
- current check constraints;
- current indexes;
- RLS enabled/disabled state;
- current RLS policies;
- organizations.id data type;
- licenses.organization_id data type.

If direct catalog access is unavailable, the migration must contain
non-destructive catalog guards and abort safely rather than assuming schema
state.

---

## 30. Implementation sequence

The approved implementation sequence is:

1. preserve the discovered licenses contract;
2. establish authoritative pre-DDL constraint inspection;
3. design the minimum additive migration, if needed;
4. review migration without executing it;
5. execute migration in a controlled checkpoint;
6. verify resulting schema;
7. implement backend persistence primitives;
8. implement effective-license evaluation;
9. implement organization-scoped APIs;
10. implement persistent mutation audit;
11. run focused tests;
12. run broad regression;
13. document and publish checkpoint.

No later step may bypass an unresolved earlier integrity gate.

---

## 31. Decision

F1.4 SHALL reuse the existing authoritative `licenses` domain.

The existing capability and quota fields are compatibility requirements.

The implementation SHALL NOT create a competing license persistence model.

Schema changes, if required, SHALL be additive and SHALL be based on
authoritative constraint inspection.

The Foundation target remains:

one unambiguous effective license per organization, historical coexistence,
backend tenant enforcement, RBAC before license evaluation, fail-closed
behavior, persistent audit, and no hard delete.
