## Scope

F1.4i.3 adds controlled organization-scoped license update and lifecycle
transition behavior.

Public API:

- `PATCH /licenses/:licenseId`
- permission: `ORGANIZATION_LICENSES_UPDATE`
- organization: exclusively from validated `TenantContext`
- actor: exclusively from validated `TenantContext`
- request metadata: IP and user-agent
- no public license delete endpoint

## Update contract

The update DTO permits only controlled license configuration fields:

- `licenseType`
- `documentsLimit`
- `renewalDate`
- `startDate`
- `endDate`
- `maxConsumerUnits`
- `documentManagement`
- `advancedAnalytics`
- `reportGeneration`
- `freeMarketManagement`
- `status`

The client cannot control:

- license ID
- organization ID
- documents used
- active flag
- created timestamp
- updated timestamp
- audit actor

Empty PATCH payloads are rejected.

## Lifecycle contract

Persisted lifecycle vocabulary remains:

- `active`
- `suspended`
- `expired`
- `cancelled`

`active` is not client-controlled.

It is derived atomically from lifecycle status:

- active -> `active = true`
- suspended -> `active = false`
- expired -> `active = false`
- cancelled -> `active = false`

An active license requires a start date.

Validity dates are evaluated on the merged current + requested state, and an
end date before the start date is rejected.

`renewal_date` remains a separate commercial field and is not treated as the
license validity boundary.

## Tenant isolation

The target license is loaded using both:

- `id = licenseId`
- `organization_id = TenantContext.organizationId`

A license absent from that scope is returned as not found.

The organization is never accepted from the request payload.

## Concurrency control

Updates use compare-and-set behavior against the previously loaded
`updated_at`.

For a timestamp value:

- equality on the previous `updated_at` is required.

For a legacy NULL value:

- `IS NULL` is used instead of equality-to-NULL.

A zero-row mutation is treated as a concurrent change and fails closed.

The database exclusion constraint remains the final concurrency authority for
overlapping effective active licenses:

- `licenses_active_validity_excl`

Only SQLSTATE `23P01` associated with that exact constraint is mapped to the
controlled overlap conflict.

Unknown persistence errors fail closed.

## Post-write integrity

The returned row must preserve:

- requested license ID
- validated organization ID
- every field written by the operation

If the returned state violates the requested postcondition, the service
attempts a guarded compensating update.

Compensation is scoped by:

- license ID
- organization ID
- the `updated_at` value produced by the write being compensated

This prevents the compensation path from intentionally overwriting a later
concurrent update.

Failure to confirm compensation is surfaced as a critical integrity error.

## Persistent audit

Successful non-idempotent updates write a persistent audit event:

- action: `UPDATE_LICENSE`
- resource type: `license`
- resource ID: license ID
- organization ID
- actor user ID
- full before snapshot
- full after snapshot
- IP address
- user-agent
- success status
- audit timestamp

Audit persistence is fail-closed.

If audit persistence fails after the license write, the service attempts the
same guarded compensating update.

If compensation succeeds, the operation fails and reports that the update was
reverted.

If compensation cannot be confirmed, the operation fails with a critical
integrity error requiring intervention.

Idempotent requests do not create database writes or audit noise.

## Delete boundary

F1.4i.3 adds no public hard-delete behavior.

The only `.delete()` remaining in `LicensesService` is the pre-existing private
compensation path for a just-created license from F1.4i.2.

Update rollback uses a guarded UPDATE, not DELETE.

## Result

F1.4i.3 establishes controlled, organization-scoped, permission-protected,
audited license update and lifecycle transition behavior while preserving the
existing database contract and concurrency constraints.

The next license checkpoint is entitlement/enforcement. It must remain
backend-authoritative and consume the effective-license primitive rather than
introducing a second license source of truth.
