# P2.2d.6 — Organization Delete Frontend

## Status

IMPLEMENTED AND LOCALLY VALIDATED — pending publication and controlled
production validation.

Phase 2 — Administration remains active.

P2.2 — Organizations remains open.

P2.2d — Organization Delete remains open.

This checkpoint exposes the previously protected Organization Delete contract
through the Administration frontend.

P2.3 — User Management remains unauthorized.

## Objective

Implement the frontend Organization Delete experience only after publication
of the P2.2d backend dependency safety boundary.

The frontend reuses:

- the existing platform-scoped Delete endpoint;
- the existing centralized API client;
- the existing permission-aware authentication context;
- the published backend fail-closed dependency guard.

No backend expansion is included.

No database migration is included.

## Backend safety prerequisite

The backend safety boundary was published before this frontend capability.

Organization Delete now checks exactly these dependency tables before
soft-delete:

- `organization_members`;
- `licenses`;
- `customers`;
- `consumer_units`;
- `energy_contracts`;
- `documents`.

If any checked dependency exists, the backend rejects Delete as a domain
conflict.

If dependency resolution fails, Delete fails closed.

The frontend does not reproduce this dependency logic.

Backend dependency validation remains authoritative.

## Frontend API contract

The centralized Organizations API now exposes:

`deleteOrganization(id)`

The request uses:

`DELETE /api/v1/admin/organizations/:id`

The Organization identifier is URL encoded.

The operation delegates to the existing centralized `apiRequest` boundary.

Components do not call `fetch` directly.

## Permission boundary

The centralized platform permission registry now includes:

`ORGANIZATIONS_DELETE`

The permission identifier is derived from the existing backend permission
contract.

The Organizations page evaluates Delete capability through the existing
`hasPermission()` boundary.

The destructive action is rendered only when the current platform context
contains the Organization Delete permission.

This is presentation authorization only.

Backend permission enforcement remains authoritative.

## Destructive confirmation

Organization Delete is not issued directly from the Organization card.

Selecting Delete opens an explicit destructive confirmation dialog.

The dialog identifies the selected Organization by name and explains that the
server will block deletion when dependencies exist.

The user must explicitly select:

`Confirmar exclusão`

before the DELETE request is issued.

The user may cancel without mutation.

## Delete state

The frontend maintains explicit state for:

- selected Delete target;
- Delete submission;
- Delete error.

While Delete is submitting, destructive and cancellation actions are
disabled.

After a successful Delete:

- the confirmation state is cleared;
- the Organizations collection is reloaded from the backend.

The refreshed backend collection remains authoritative for rendered state.

## Conflict behavior

The frontend does not attempt to predict dependency safety.

If the backend rejects Delete because dependencies exist, the API error is
presented through the existing error presentation boundary.

No dependency is automatically modified.

No cascade operation is issued by the frontend.

No retry that changes domain state is performed.

## Production validation boundary

No production Organization Delete is performed by this implementation
checkpoint before publication.

After deployment, controlled production validation must use only the
Organization created for P2.2b and updated by P2.2c.

The production gate must first confirm:

- Platform Admin authentication succeeds;
- Organization Delete permission is present;
- the validation Organization is uniquely identified;
- the target identifier is not printed;
- the target currently exists through normal read contracts.

The Delete request may proceed only against that uniquely identified
validation Organization.

The backend dependency guard remains responsible for determining whether the
Delete is allowed.

No dependency may be removed merely to make the validation succeed.

## Successful production validation

If the validation Organization has no blocking dependency, a successful
controlled Delete must prove:

- exactly one DELETE request is issued;
- the request succeeds through the protected backend;
- the Organization disappears from the normal Organizations list;
- normal Organization detail read no longer returns the active resource;
- no second Delete is issued;
- no unrelated Organization is modified.

The validation must not perform a hard-delete.

## Blocked production validation

If the validation Organization has a blocking dependency, production
validation must stop on the backend conflict.

A blocked result is evidence that the dependency safety boundary is operating
as designed.

The validation must not remove or mutate the blocking dependency.

The validation must not select another operational Organization merely to
force an allowed-path Delete.

## Security boundary

Frontend Delete visibility does not replace backend authorization.

Frontend confirmation does not replace backend dependency validation.

Automatic cascade remains prohibited.

Hard-delete remains prohibited.

Token values and target identifiers must not be printed by controlled
production validation.
