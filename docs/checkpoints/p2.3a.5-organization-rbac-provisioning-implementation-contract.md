## Objective

Define the exact implementation boundary for canonical Organization RBAC
provisioning.

The implementation must guarantee that every successfully created
Organization has the organization-scoped roles required by the current
authorization model.

The same canonical provisioning authority must support controlled,
idempotent backfill of an eligible existing Organization.

## Published decision

This contract implements the published decision:

`P2.3a.5 — Organization RBAC Provisioning Remediation`

The implementation must preserve every fail-closed and scope boundary defined
by that decision.

## Discovered lifecycle defect

The current Platform Organization Create operation persists:

1. the Organization row;
2. persistent Organization creation audit evidence.

`REG Test 1789688388`

## Canonical Organization roles

Every provisioned Organization must contain exactly one role for each
canonical Organization role name:

- `admin_org`;
- `gestor`;
- `operacional`;
- `consulta`.

Each role must have:

`scope = 'organization'`

The provisioning primitive must not create an `admin_platform` role.

`admin_platform` remains global Platform authority.

## Canonical permission source

Role semantics are defined by canonical permission codes.

Environment-specific permission UUIDs are not the semantic source of
authority.

At execution time the backend/database provisioning authority must resolve
each required permission code against the current `permissions` catalog.

Each required code must resolve exactly once.

Missing, duplicate or malformed permission catalog state must fail closed.

## Canonical contract ownership

The four permission-code sets must have one canonical implementation
definition.

Create provisioning, controlled backfill and tests must consume the same
definition.

The implementation must not maintain separate hand-copied permission sets for
Create and backfill.

## Permission resolution contract

Before creating any role, provisioning must resolve the complete union of
required permission codes.

Resolution must prove:

- every required code exists;
- every required code resolves exactly once;
- every resolved row has a non-empty permission ID;
- no unexpected code is substituted.

The resulting role permission arrays contain permission IDs because
`roles.permissions` is the effective runtime grant authority.

Semantic validation and tests remain code-based.

## Role identifier contract

New Organization role identifiers must be generated by the application or
database using the repository's current identifier convention.

Identifiers must not be copied from another Organization.

Role IDs from `Expert Energy - Default Organization` are reference data only
and must never be reused.

## Role persistence contract

Each created role must persist:

- generated role ID;
- target Organization ID;
- canonical role name;
- resolved permission ID array;
- `scope = 'organization'`;
- current timestamps when required by the schema.

No historical `is_system` field is part of the current contract.

No `role_permissions` write is authorized.

## Atomicity requirement

A successful Organization Create must never expose an Organization without
its canonical RBAC baseline.

The preferred implementation boundary is a database-atomic primitive that
creates:

1. the Organization;
2. all four canonical Organization roles.

The primitive must either commit the complete Organization + RBAC state or
commit none of it.

If repository discovery proves an equivalent existing transactional mechanism,
that mechanism may be used instead.

Independent application-side inserts without an atomic or safely compensating
boundary are not sufficient.

## Create application boundary

The Platform Organization Create endpoint remains the external authority for
creating Organizations.

The client continues to supply Organization business fields only.

The client must not supply:

- role IDs;
- role names;
- permission arrays;
- permission codes;
- role scope.

RBAC provisioning is backend-controlled.

## Create lifecycle

The required lifecycle is:

`validate request`
→ `resolve canonical permissions`
→ `atomically create Organization + four roles`
→ `confirm complete RBAC state`
→ `persist Organization creation audit`
→ `return success`

The endpoint must not return success before complete RBAC confirmation.

## Create result integrity

After atomic creation, the service must prove:

- exactly one Organization was created;
- exactly four canonical roles were created;
- each role belongs to the created Organization;
- every role has scope `organization`;
- role names are exactly the canonical four;
- role permission sets match the canonical contracts.

Unexpected result shape fails closed.

## Audit boundary

Persistent Organization creation audit remains mandatory.

The audit continues to identify:

- authenticated Platform actor;
- created Organization;
- before/after semantics already established by Organization Create;
- request IP when available;
- request user-agent when available.

The RBAC permission arrays do not need to be duplicated into audit payloads
unless required by existing audit infrastructure.

## Audit failure compensation

If Organization + RBAC creation succeeds but persistent audit fails, the
operation must not leave an unaudited Organization.

Compensation must be guarded by ownership of the exact Organization created
by that execution.

The implementation must verify the current foreign-key cascade behavior before
relying on Organization deletion to remove newly created roles.

If guarded compensation cannot be confirmed, the service must surface a
critical integrity failure.

## Create idempotency and conflicts

Ordinary Organization Create is not silently idempotent by Organization name.

Existing Create conflict semantics remain outside this remediation unless
repository constraints already define them.

RBAC provisioning itself must never create duplicate canonical roles for one
Organization.

## Existing Organization boundary

Ordinary Create must not modify roles of pre-existing Organizations.

Existing Organization remediation occurs only through the controlled backfill
boundary.

## Controlled backfill primitive

The implementation must provide a backend/database primitive capable of
provisioning the canonical four-role baseline for an eligible existing
Organization.

The primitive must use the same canonical permission-code authority as Create.

It must not accept arbitrary role names or permission arrays from a browser or
operator.

## Backfill authorization

Production backfill is an exceptional Platform Administration operation.

It must not be exposed as an organization-scoped User Management mutation.

If exposed through Nest, it must require explicit Platform scope and a
dedicated Platform permission, unless implementation discovery establishes a
safer migration-only execution boundary.

The final implementation checkpoint must choose and document exactly one
backfill execution authority.

## Backfill eligibility

Backfill is allowed only when the target Organization:

- exists exactly once;
- is not soft-deleted;
- currently has zero roles;
- currently has zero Organization memberships.

Eligibility must be re-evaluated inside the mutation/concurrency boundary.

A partial role catalog is not automatically repaired.

An Organization with any membership is not automatically rewritten.

Those states fail closed.

## Backfill concurrency

Concurrent backfill attempts for the same Organization must not create
duplicate roles.

The database boundary must serialize or otherwise atomically protect
eligibility and role creation.

The existing P2.3a.5 per-Organization advisory-lock strategy may be reused if
the implementation proves compatible lock-key semantics.

## Backfill result integrity

Successful backfill must return or allow confirmation of:

- target Organization;
- exactly four created roles;
- canonical role names;
- organization scope;
- exact canonical permission sets.

No membership is created by RBAC backfill.

No identity/profile is created by RBAC backfill.

## Backfill idempotency

A second invocation against an exactly provisioned Organization performs no
new role creation.

It must return an explicit already-provisioned/domain-conflict outcome or an
equivalent no-mutation result documented by the implementation.

Partial or divergent role state fails closed.

## Decision

Organization creation and Organization RBAC baseline provisioning are one
successful lifecycle invariant.

Exactly four organization-scoped roles are required:

- `admin_org`;
- `gestor`;
- `operacional`;
- `consulta`.

Their semantic authority is defined by the canonical permission-code
contracts in this document.

The implementation must provide one canonical provisioning authority consumed
by both new Organization creation and controlled eligible backfill.

`REG Test 1789688388` remains blocked from bootstrap retry until that
provisioning authority is implemented, published, deployed and its controlled
backfill is validated.

P2.3a remains open.

P2.3b remains blocked.
