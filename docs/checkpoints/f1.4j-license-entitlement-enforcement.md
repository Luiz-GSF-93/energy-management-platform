## Objective

Introduce the first backend-authoritative license entitlement primitive and
apply real enforcement to an existing licensed resource without creating a
second source of truth for licenses or mixing entitlement with RBAC.

The authorization chain remains conceptually:

Identity -> Membership/Tenant -> RBAC -> License -> Entitlement -> Resource

## Existing source of truth

`LicensesService.resolveEffectiveLicense(organizationId)` remains the single
application primitive for resolving the effective license.

F1.4j does not duplicate effective-license resolution rules.

The entitlement primitive delegates to that existing resolver.

## Capability contract

The closed capability vocabulary introduced by this checkpoint is:

- `document_management`
- `advanced_analytics`
- `report_generation`
- `free_market_management`

These names correspond directly to fields already present in the authoritative
license persistence contract.

## Entitlement primitive

`LicensesService.requireEntitlement(organizationId, capability)`:

1. resolves the effective license using `resolveEffectiveLicense`;
2. denies when no effective license exists;
3. grants only when the requested capability is exactly `true`;
4. denies `false`;
5. denies `null`;
6. propagates effective-license resolution failures fail-closed;
7. returns the effective license when entitlement is granted.

The primitive performs no license mutation.

It exposes no new HTTP endpoint.

## Separation from RBAC

Entitlement is not implemented inside `RoleGuard`.

Existing permission/RBAC behavior is not replaced or weakened.

F1.4j introduces an additional license boundary after the existing identity,
tenant and RBAC layers.

The existing Documents controller currently has no `RequirePermission`
metadata. That is a pre-existing RBAC debt and was intentionally not changed
inside this license-entitlement checkpoint.

It must be reviewed separately rather than silently mixing an unrelated RBAC
change into F1.4j.

## Document management enforcement

`document_management` is the first capability connected to a real existing
business resource.

`DocumentsModule` imports `LicensesModule`, which already exports
`LicensesService`.

`DocumentsService` requires `document_management` before persistence access for
all five existing resource operations:

- find all
- find one
- create
- update
- delete

The organization passed to entitlement enforcement is the same validated
organization scope already used by the Documents persistence queries.

A denied entitlement prevents the Documents service from obtaining the
Supabase client for the resource operation.

Therefore denial occurs before Documents persistence access begins.

## Tenant isolation

F1.4j preserves the existing organization-scoped Documents persistence model.

Document queries continue to scope resource access by `organization_id`.

The entitlement check is also evaluated for that organization.

No organization identifier is introduced through license payload data or a new
client-controlled entitlement parameter.

## Fail-closed behavior

The following conditions deny access:

- no effective license;
- requested capability is `false`;
- requested capability is `null`.

Failures while resolving the effective license are not converted into grants.

Only an explicit boolean `true` grants the requested capability.

## Quota boundary

F1.4j intentionally does not implement quota enforcement.

The following license fields remain outside the boolean entitlement primitive:

- `documents_limit`
- `documents_used`
- `max_consumer_units`

No Documents quota behavior was invented because the current Documents module
does not contain an established usage-accounting or quota-enforcement flow.

Quota semantics require a separate design and concurrency analysis before
implementation.

## Other capabilities

F1.4j defines but does not attach enforcement for:

- `advanced_analytics`
- `report_generation`
- `free_market_management`

No artificial endpoints or modules were created merely to consume those
capabilities.

They remain available to future real resources through the same entitlement
primitive.

## API compatibility

F1.4j adds no license HTTP route.

The existing license API remains:

- POST `/licenses`
- PATCH `/licenses/:licenseId`
- GET `/licenses/effective`

The Documents controller route surface is unchanged.
