# F1.5.3c — Customers Permission Model Decision

## Problem

Customers is an independent application resource exposed through its own
controller, service, DTOs, routes, persistence table, and tenant filtering.

However, Customers authorization currently reuses the Contracts permission
domain:

- POST /customers -> organization.contracts.create
- GET /customers -> organization.contracts.view
- GET /customers/:id -> organization.contracts.view
- PUT /customers/:id -> organization.contracts.update
- DELETE /customers/:id -> organization.contracts.delete

CUSTOMERS_PERMISSIONS is also only an alias of the Contracts permissions.

## Evidence

CustomersService operates directly on the customers table and scopes all
operations by organization_id.

Customers is referenced independently by multiple domain resources,
including consumer units, energy contracts, documents, invoices, and other
schema relationships.

Historical inspection shows that the Contracts permission reuse was
introduced together with the initial granular RoleGuard integration.

No historical dedicated Customers permission model was found.

Current database catalog discovery returned no permission whose code or
resource contains customer.

Therefore, the current model is classified as legacy authorization coupling,
not as an authoritative Customers permission domain.

## Decision

Introduce a dedicated Customers permission domain:

- organization.customers.view
- organization.customers.create
- organization.customers.update
- organization.customers.delete

The database generates the permission IDs.

After database validation, those authoritative IDs are transported to the
backend PERMISSIONS constants.

CustomersController will then reference only the dedicated Customers
permissions.

## Permission assignment authority

roles.permissions JSONB remains the effective permission assignment
authority.

role_permissions must remain untouched.

Existing permission IDs and existing role grants must not be removed or
rewritten.

Only missing approved Customers permission IDs may be appended.

## Migration requirements

The migration must be idempotent.

Permission insertion must preserve existing catalog records.

Role updates must:

- target only the five approved roles
- append only missing approved permission IDs
- preserve existing JSONB permission array contents
- avoid removing permissions
- avoid role_permissions
- avoid unrelated role mutations

Structural guards must fail if the expected Customers permission catalog or
target role set cannot be resolved.

## Controller mapping after catalog validation

- POST /customers -> ORGANIZATION_CUSTOMERS_CREATE
- GET /customers -> ORGANIZATION_CUSTOMERS_VIEW

Controller wiring must occur only after the database-generated IDs have been
validated and transported to backend constants.
