# F1.2.2 — Organization Membership Role Update Design

Date: 2026-09-21

## Status

APPROVED FOR IMPLEMENTATION

Implementation has not started in this checkpoint.

## Objective

Add the organization-scoped administrative mutation:

`PATCH /api/v1/admin/users/:userId/role`

Permission:

`ORGANIZATION_USERS_UPDATE`

The endpoint changes only the contextual role of the target user's
membership in the actor's validated active organization.

## Authorities

Identity authority:

`auth.users`

Organization membership authority:

`organization_members`

Organization contextual role authority:

`organization_members.role_id`

Global platform assignments:

`user_roles`

`user_roles` MUST NOT be used by this endpoint.

## Tenant boundary

The target membership MUST be selected using both:

- target user ID
- validated active organization ID

The organization comes from the validated tenant context.

The request body cannot select or override the organization.

No Platform Admin bypass is introduced by F1.2.2.

## DTO

Minimum request:

`{ roleId: UUID }`

The DTO MUST validate `roleId` as a UUID.

No role name is accepted as authorization authority.

No organization ID is accepted in the body.

## Target membership validation

Before mutation, the service MUST load the target membership using:

- `user_id = targetUserId`
- `organization_id = organizationId`
- `status = active`

Expected result:

exactly one membership.

Zero matching memberships:

NotFound.

More than one matching membership:

data-integrity failure.

The current membership role MUST be structurally valid before mutation.

## Destination role validation

The destination role MUST be loaded by `roleId`.

It MUST satisfy all of:

- role exists
- role ID matches requested role ID
- `role.organization_id === organizationId`
- `role.scope === organization`

A role belonging to another organization MUST be rejected.

A global role MUST be rejected.

The endpoint MUST NOT create or modify a `user_roles` assignment.

## Idempotency

If:

`beforeRoleId === requestedRoleId`

the operation returns successfully without:

- membership UPDATE
- persistent audit entry

This prevents audit noise and unnecessary writes.

## Mutation

Only this field may be changed:

`organization_members.role_id`

The update MUST be compare-and-set guarded using:

- target user ID
- organization ID
- active status
- previous role ID

Conceptually:

`user_id = targetUserId`
`organization_id = organizationId`
`status = active`
`role_id = beforeRoleId`

Set:

`role_id = requestedRoleId`

The update MUST return affected membership identity/role data.

Exactly one affected row is required.

Zero or multiple affected rows MUST fail closed as a concurrency or
integrity error.

## Persistent audit

Successful role changes require persistent audit.

Audit action:

`UPDATE_USER_MEMBERSHIP_ROLE`

Audit resource type:

`organization_membership`

Audit resource identifies the target membership.

The record MUST contain:

- authenticated actor user ID
- validated organization ID
- target user ID
- membership/resource ID
- before role ID
- after role ID
- IP address when available
- user agent when available
- success status
- timestamp

No synthetic `org_default` is permitted.

## Audit failure compensation

The membership update and audit are not currently executed in a shared
database transaction.

Therefore an audit failure MUST trigger guarded compensation.

Rollback may execute only while the value written by this operation is
still current.

Rollback conditions MUST include:

- target user ID
- organization ID
- active status
- `role_id = requestedRoleId`

Rollback sets:

`role_id = beforeRoleId`

Exactly one reverted row is required.

If audit fails and rollback succeeds:

fail the request and report that the role update was reverted.

If audit fails and rollback cannot be confirmed:

fail closed with a critical integrity error.

The rollback MUST NOT overwrite a later concurrent role change.

## Response

Minimum successful response:

- `userId`
- `role.id`
- `role.name`

The response MUST NOT expose:

- raw permissions
- role organization internals
- auth metadata
- tokens

## Compatibility

F1.2.2 MUST NOT modify:

- existing user list contract
- existing single-user read contract
- `updateAffiliation`
- public `/auth/register`
- organization switching
- `/auth/context`
- TenantGuard
- RoleGuard
- Platform Admin authorization model
- RLS

- migrations
- package dependencies
- TypeScript configuration

## Required service tests

At minimum:

1. scopes target membership to target user + current organization + active status
2. rejects missing active target membership
3. fails closed on duplicate membership
4. fails closed on membership query error
5. validates current membership role integrity
6. loads destination role by requested role ID
7. rejects missing destination role
8. rejects destination role from another organization
9. rejects global destination role
10. rejects malformed destination role
11. idempotent same-role request performs no UPDATE
12. idempotent same-role request performs no audit
13. updates only `organization_members.role_id`
14. CAS includes user, organization, active status, and previous role ID
15. exactly one updated row is required
16. detects concurrent/CAS conflict
17. fails closed on update query error
18. successful mutation audits actor/context/target/before/after/origin
19. audit failure triggers guarded rollback
20. rollback is conditioned on the newly written role ID
21. audit failure + successful rollback fails request as reverted
22. audit failure + unconfirmed rollback produces critical integrity failure
23. no `user_roles` access
24. no profile role mutation

## Required controller tests

At minimum:

1. route is `PATCH /admin/users/:userId/role`
2. declares `ORGANIZATION_USERS_UPDATE`
3. RoleGuard grants when UPDATE permission is present
4. RoleGuard denies when UPDATE permission is absent
5. forwards target user ID
6. forwards validated tenant organization ID
7. forwards DTO role ID
8. forwards authenticated actor ID
9. forwards request IP
10. forwards user-agent
11. existing affiliation authorization contract remains unchanged

## Database discovery confirmation

Read-only production discovery confirmed:

`organization_members` exposes:

- id
- organization_id
- role_id
- status
- user_id

`roles` contains both organization and global scopes.

`audit_logs` exposes the persistent audit fields required by the
existing audit foundation.

No write was executed during discovery.

## Out of scope

F1.2.2 does not implement:

- membership deactivation
- membership reactivation
- invitation/provisioning
- role CRUD
- permission CRUD
- frontend user administration
- Platform Admin user-management bypass
- public registration redesign

## Final implementation rule

Security order remains:

security -> integrity -> compatibility -> scalability -> performance -> UX

Implementation must be incremental and limited to the approved role
mutation and its persistent audit contract.
