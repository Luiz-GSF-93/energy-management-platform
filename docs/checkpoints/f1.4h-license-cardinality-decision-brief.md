# F1.4h — License Cardinality Decision Brief

## Status

DESIGN — no DDL authorized by this document.

## Objective

Enforce, under concurrent transactions, the invariant:

> An organization must not have overlapping effective active license
> validity periods.

Historical and non-overlapping scheduled licenses must remain possible.

## Authoritative baseline

The authoritative database is PostgreSQL 17.6.

At discovery time:

- active license rows: 0;
- overlapping active license pairs: 0;
- no existing license exclusion constraint was found;
- no user-defined license trigger was found;
- `btree_gist` is available at version 1.7;
- `btree_gist` is not installed.

F1.4g already added organization FK, lifecycle consistency, and validity-date
integrity constraints.

## Rejected approaches

### Global UNIQUE organization_id

Rejected.

A global unique constraint on `organization_id` would prevent historical and
non-overlapping scheduled licenses from coexisting.

### Application read-before-write only

Rejected.

Two concurrent transactions can both observe no conflicting license and then
both insert overlapping records.

Application validation may improve error messages, but it is not the
authoritative concurrency barrier.

### Membership-only RLS write enforcement

Rejected as a cardinality mechanism.

RLS is an authorization/isolation boundary, not a replacement for database
integrity constraints.

License RLS policy design remains outside this checkpoint.

## Candidate A — Declarative exclusion constraint

Preferred architecture, subject to an isolated implementation proof.

The intended database invariant is conceptually:

- equal `organization_id`;
- overlapping license validity ranges;
- only rows representing active licenses participate.

A PostgreSQL GiST exclusion constraint naturally expresses this invariant and
lets the database resolve concurrent conflicting writes.

Because `organization_id` is text, the intended implementation requires
appropriate GiST equality support.

The authoritative environment exposes `btree_gist` version 1.7 but does not
currently have it installed.

Installing the extension is therefore an explicit database capability change
and must never occur implicitly.

## Candidate B — Trigger plus transactional locking

Fallback architecture.

A database trigger/function could serialize conflicting writes per
organization, acquire a transaction-scoped lock, inspect overlapping active
ranges, and reject conflicts.

This can avoid adding `btree_gist`, but introduces:

- procedural database code;
- explicit lock semantics;
- additional concurrency reasoning;
- trigger lifecycle and maintenance;
- greater implementation surface.

It is retained as fallback if the declarative approach cannot be proven safe
in the authoritative environment.

## Decision

Proceed toward the declarative PostgreSQL exclusion-constraint architecture.

Do not install `btree_gist` or create the exclusion constraint as part of this
Decision Brief.

The implementation checkpoint must first prove the exact extension,
operator-class, range-expression, predicate, and concurrency behavior before
production DDL is authorized.

If that proof fails, stop and return to the trigger/transactional-locking
alternative.

## Temporal semantics

`start_date` is the beginning of license validity.

`end_date` is optional.

A missing end date represents an open-ended validity interval.

The implementation must preserve the F1.4 contract that historical and
non-overlapping scheduled licenses can coexist.

Boundary semantics must be explicitly tested before the final exclusion
expression is approved.

## Lifecycle semantics

The approved lifecycle vocabulary remains:

- active;
- suspended;
- expired;
- cancelled.

The existing F1.4g status/active consistency constraint remains authoritative.

The cardinality constraint must apply only to rows that represent an active
license according to the approved lifecycle contract.

## Concurrency requirement

The final mechanism must be database-backed and safe when two independent
transactions attempt conflicting writes concurrently.

A sequential insert test alone is insufficient proof.

The implementation checkpoint must include a genuine concurrent-transaction
test or equivalent authoritative database evidence.

## Failure behavior

A conflicting write must fail closed.

Existing validated license data must not be overwritten or deleted to resolve
a conflict.

Application code may later translate the database conflict into a domain
error, but that API behavior is outside this checkpoint.

## Explicit non-goals

F1.4h does not authorize:

- license endpoints;
- frontend work;
- RLS policy creation;
- role-permission grants;
- hard deletes;
- global UNIQUE constraints on organization_id;
- unrelated schema refactoring;
- changes to authentication or TenantContext;
- Jest/tooling remediation.

## Implementation gate

Before production DDL, the next checkpoint must validate:

1. explicit `btree_gist` installation requirements;
2. text equality support under GiST after installation;
3. the exact license validity range representation;
4. boundary behavior for adjacent validity periods;
5. the partial predicate for active licenses;
6. coexistence of historical and scheduled licenses;
7. rejection of overlapping active licenses;
8. concurrent conflicting writes;
9. compatibility with existing F1.4g constraints;
10. rollback/failure behavior.

No production DDL is authorized until this gate is satisfied.

## Security and compatibility

Security and data integrity take precedence over convenience.

The implementation must remain additive, preserve the existing `licenses`
contract, and must not weaken backend tenant/RBAC enforcement.

Extension installation, if ultimately approved, must be explicit, versioned,
reviewed, and limited to the capability required by the chosen constraint.
