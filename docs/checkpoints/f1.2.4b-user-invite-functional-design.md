# F1.2.4b — Organization User Invite Functional Design

## Status

Design checkpoint only.

No production implementation, database mutation, Auth mutation,
schema change, RLS change, invite email, or runtime audit insertion
is authorized by this document.

## Baseline

F1.2.4a persistent invite audit primitive is already published.

The invite endpoint remains:

`POST /admin/users/invite`

Required permission:

`ORGANIZATION_USERS_INVITE`

The organization is always derived from validated TenantContext.
`organizationId` is not accepted from the request body.

## Request

Minimum request:

- `email`
- `name`
- `roleId`
- `affiliationType`

`affiliationType` is restricted to:

- `internal`
- `external`

Email normalization is:

`trim().toLowerCase()`

No provider-specific plus-address or dot normalization is allowed.

## Authorities

Identity authority:

`auth.users`

Profile authority:

`user_profiles`

Organization access authority:

`organization_members`

Organization role authority:

`organization_members.role_id`

`user_profiles.role_id` is not organization-role authority.

`user_roles` must not be used to provision organization access.

## Role validation

Before any provisioning write, the requested role must resolve to
exactly one role that:

- has the requested `roleId`;
- belongs to the current organization;
- has organization scope.

Invalid, missing, ambiguous, global, or cross-organization roles fail
closed before provisioning.

## Identity resolution

Identity resolution is two-stage.

### Stage 1 — application profile lookup

Look up `user_profiles` using the normalized email.

Zero profiles:

continue to Stage 2.

Exactly one profile:

- require a valid `user_id`;
- validate the corresponding Auth identity using
  `auth.admin.getUserById(profile.user_id)`;
- require Auth identity email to normalize to the requested email;
- otherwise fail closed as an integrity conflict.

More than one profile:

fail closed as an integrity conflict.

### Stage 2 — Auth lookup

When no application profile exists, inspect Auth identities using
bounded paginated `auth.admin.listUsers`.

Every returned email comparison uses the same normalized email rule.

The lookup must continue until:

- a matching identity is found and uniqueness is established; or
- pagination is exhausted.

Zero Auth matches:

`new_identity`

Exactly one Auth match:

`existing_identity_without_profile`

More than one normalized Auth match:

fail closed as an integrity conflict.

The implementation must impose a bounded maximum pagination policy and
fail closed if the bound is reached before exhaustion.

## Existing identity with valid profile

The invite must never duplicate the Auth identity.

The existing profile is not rewritten by this operation.

The request `affiliationType` must exactly equal the existing
`user_profiles.affiliation_type`.

Affiliation mismatch:

`409 Conflict`

The invite does not silently mutate global affiliation.

The invite does not overwrite:

- profile name;
- profile organization pointer;
- profile role_id;
- existing memberships in any organization.

## Existing identity without profile

Fail closed.

F1.2.4 does not silently reconstruct a missing profile and then grant
organization access.

Profile recovery is a separate lifecycle concern.

No membership is created.

No existing Auth identity is deleted.

## Current-organization membership state

### Existing active membership

No mutation.

Return explicit conflict.

Invite is not a role-update operation.

### Existing inactive membership

No mutation.

Return explicit conflict.

Invite is not a reactivation operation.

### No current-organization membership

Provisioning may continue after all integrity and role checks pass.

Memberships in other organizations remain untouched.

## New identity

Use:

`auth.admin.inviteUserByEmail`

Do not use `createUser` as the normal invite mechanism.

The returned Auth identity must be present, have a valid ID, and its
email must normalize to the requested email.

The operation records ownership of the identity only when creation by
the current invite operation is positively established.

No pre-existing Auth identity may ever be deleted by compensation.

## New profile

For a newly created identity, explicitly provision the application
profile.

Do not assume an undocumented Auth-to-profile trigger.

The new profile uses:

- Auth user ID;
- normalized email;
- requested name;
- requested affiliation type;
- current organization as initial organization context.

`user_profiles.role_id` is not organization-role authority and must
not be populated with the requested organization role.

The implementation must preserve compatibility with the actual
database constraints before performing the first live write.

## Membership creation

The new organization membership uses:

- Auth user ID;
- current organization ID;
- validated organization role ID;
- status `active`.

F1.2.4 does not introduce a new `pending` membership lifecycle.

Current authorization requires active membership, and no approved
pending-to-active lifecycle currently exists.

For F1.2.4:

- `invited_at = null`
- `accepted_at = null`

These timestamps are not authorization authority and existing live
memberships demonstrate compatibility with null values.

Any future semantic use of invitation/acceptance timestamps requires
a separate lifecycle checkpoint.

## Active organization pointer

For an existing valid profile:

do not modify `user_profiles.organization_id`.

For a newly provisioned profile:

initialize `user_profiles.organization_id` to the organization that
issued the invite, subject to confirmed database compatibility.

The membership remains the access authority.

The profile organization field remains only the active/default context
pointer and must never substitute for membership validation.

## Persistent audit

Successful provisioning calls the published F1.2.4a primitive:

`logUserInvite`

The audit resource is the newly created organization membership.

The audit records:

- actor;
- organization;
- target user;
- membership;
- normalized email;
- role;
- affiliation;
- provisioning path;
- IP when available;
- user agent when available;
- success timestamp.

Provisioning path is restricted to:

- `new_identity`
- `existing_identity`

No authentication secret is persisted.

## Compensation ownership

Compensation is ownership-aware.

The implementation tracks independently:

- `createdIdentity`
- `createdProfile`
- `createdMembership`

Only resources positively proven to have been created by the current
operation may be compensated.

Pre-existing resources must never be deleted or overwritten by
compensation.

Rollback order is:

1. newly created membership;
2. newly created profile;
3. newly created Auth identity.

### Existing identity path

If the operation created only a membership, compensation may remove
only that exact newly created membership.

The Auth identity and pre-existing profile remain untouched.

### New identity path

Compensation may remove membership, profile, and Auth identity only
when ownership of each resource is positively established.

Each compensation operation must use exact identifiers and guarded
conditions where supported.

Unconfirmed or failed compensation is a CRITICAL operational failure.

## Audit failure

Persistent audit failure means the invite operation is not considered
successfully committed.

Attempt guarded compensation of resources created by the current
operation in reverse ownership order.

If compensation cannot be confirmed, surface a critical failure rather
than reporting success.

## Concurrency

The implementation must not assume read-then-write is atomic.

Duplicate membership creation or concurrent invite races must fail
closed.

Existing data must never be overwritten merely to resolve a race.

If database uniqueness required for safe concurrency is absent, schema
work requires a separate migration checkpoint before production
authorization.

## Public registration compatibility

The existing public `/auth/register` flow remains unchanged.

F1.2.4 does not redesign registration or authentication.

## Explicit non-goals

F1.2.4 does not:

- hard-delete existing identities;
- reactivate inactive memberships;
- change an existing membership role;
- mutate existing global affiliation;
- mutate existing active organization context;
- use `user_roles` for organization access;
- introduce role or permission administration;
- add Platform Admin bypass;
- redesign `/auth/register`;
- add frontend invite UI;
- introduce a pending membership lifecycle;
- change schema or RLS without a separate checkpoint.

## Implementation sequence

After this design is published:

1. DTO and controller contract;
2. focused service implementation;
3. focused state-machine and compensation tests;
4. broad regression;
5. controlled publication;
6. F1.2.4 closeout.

No production mutation is authorized by publishing this design.
