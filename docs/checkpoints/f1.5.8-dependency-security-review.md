# F1.5.8 — Dependency Security Review

## Status

IMPLEMENTED AND VALIDATED — pending publication.

Phase 1 remains open.
Phase 2 remains unauthorized.

## Objective

Review and remediate dependency-security exposure in the Foundation
runtime without expanding this checkpoint into unrelated application,
frontend-architecture, test-architecture, or tooling work.

The review covers the independently installed backend and frontend Node
projects.

## Baseline

The review started from a clean and synchronized repository baseline.

Initial audits identified security findings in both projects.

The frontend included critical production exposure in the Next.js
dependency chain.

The backend included production findings in the NestJS / Express
dependency chain and additional development-tooling findings.

## Frontend dependency ownership

The existing frontend imported `lucide-react` from application source but
did not declare it in `frontend/package.json`.

Resolution therefore escaped the frontend project and loaded
`lucide-react` from the repository-root `node_modules`.

That root installation resolved against React 19 type definitions while
the frontend itself used React 18 type definitions.

This caused the existing frontend baseline to fail TypeScript validation
with incompatible `ReactNode` definitions.

The dependency ownership defect was corrected by declaring
`lucide-react@1.46.0` directly in the frontend project.

After local ownership was established:

- React remained on 18.3.1;
- `@types/react` remained on 18.3.31;
- Lucide resolved from `frontend/node_modules`;
- frontend type-check passed;
- frontend production build passed.

## Frontend security remediation

Next.js 14.2.35 retained production security findings.

Next.js 15.5.26 removed the original critical finding but continued to
pin a vulnerable PostCSS version.

Next.js 16.3.6 was validated as the supported remediation candidate.

The accepted frontend runtime contract is:

- Next.js 16.3.6;
- React 18.3.1;
- React DOM 18.3.1;
- PostCSS 8.5.23 through Next.js;
- lucide-react 1.46.0.

Next.js 16 generated the corresponding TypeScript contract changes in
`frontend/tsconfig.json` and `frontend/next-env.d.ts`.

Frontend validation proved:

- dependency tree valid;
- TypeScript validation passes;
- production build passes;
- full npm audit reports zero vulnerabilities;
- production npm audit reports zero vulnerabilities.

## Frontend lint boundary

Next.js 16 no longer provides the legacy `next lint` command.

An explicit ESLint replacement was investigated.

ESLint 9.39.5 was marked deprecated / unsupported by its published
package metadata.

ESLint 10.11.0 was also evaluated, but the
`eslint-config-next@16.3.6` dependency chain was not runtime-compatible
with it during validation.

The experimental ESLint dependencies and configuration were therefore
removed.

The obsolete `next lint` script was removed rather than retaining a
command known to fail.

The current frontend is provisional and is scheduled to be rebuilt
according to the approved target architecture.

Functional frontend refactoring and the final frontend lint architecture
are outside this checkpoint.

## Backend NestJS remediation

The backend originally used the NestJS 10 runtime line.

A coordinated NestJS 11 candidate was validated using:

- `@nestjs/common@11.2.5`;
- `@nestjs/core@11.2.5`;
- `@nestjs/platform-express@11.2.5`;
- `@nestjs/config@4.0.4`;
- `@nestjs/jwt@12.0.2`;
- `@nestjs/passport@11.0.5`.

NestJS 11 passed:

- dependency-tree validation;
- TypeScript validation;
- backend build;
- all existing regression tests.

Regression result:

- 34 test suites passed;
- 284 tests passed.

## NestJS 12 investigation

NestJS 12.0.4 was separately evaluated because npm audit identified it as
the framework-level remediation path for the remaining NestJS 11
production findings.

The NestJS 12 runtime removed those production findings, but the existing
Jest 29 / CommonJS test environment was incompatible with the NestJS 12
module distribution.

The experiment caused widespread test-loader failures and was rejected.

Migrating the backend test/module architecture to support NestJS 12 is
not authorized as part of this dependency-security checkpoint.

No NestJS 12 dependency remains in the accepted runtime contract.

## Multer remediation

The remaining NestJS 11 production findings were traced to the Multer
version installed by `@nestjs/platform-express@11.2.5`.

That package declares Multer 2.2.0.

A narrowly scoped npm override was validated:

    "overrides": {
      "@nestjs/platform-express": {
        "multer": "2.4.0"
      }
    }

The effective installed Multer version is 2.4.0.

The override preserves the validated NestJS 11 runtime while removing the
vulnerable Multer dependency chain.

## Multer compatibility evidence

The backend source contains no current multipart/upload integration.

No current source usage was found for:

- FileInterceptor;
- FilesInterceptor;
- AnyFilesInterceptor;
- FileFieldsInterceptor;
- NoFilesInterceptor;
- UploadedFile;
- UploadedFiles;
- MulterModule;
- multipart/form-data;
- diskStorage;
- memoryStorage.

Direct module loading of Multer 2.4.0 succeeded.

Its memory and disk storage factories are available.

With the override active:

- dependency-tree validation passes;
- TypeScript validation passes;
- backend build passes;
- 34 test suites pass;
- 284 tests pass;
- production npm audit reports zero vulnerabilities.

The override is intentionally narrow and security-motivated.

Any future introduction of multipart upload behavior must revalidate this
override against the active NestJS platform-express version.

dependency remediation.

No ESLint configuration or source-code lint remediation is introduced by
F1.5.8.
