# F7.1 — Trading Hub

Trading Hub adds a licensed, tenant-scoped workflow for supplier registration, energy opportunities, invitations, private proposal PDFs, comparison, internal approval, customer commercial approval and recording a formalized contract. Registrations and decisions use modal forms. Customers and invited suppliers use an expiring email-verified portal.

## Access and audit

- Existing plans and licenses default to `trading_hub=false`; selecting the module requires a plan that includes it.
- Backoffice calls require an active organization membership or a current authorized platform operation, contract permissions and the Trading Hub entitlement.
- Internal approval, customer invitations and contract recording require gestor/admin authority. A customer can see only the internally approved proposal associated with their invitation.
- Invitations and sessions store hashes. A six-digit OTP is bound to the invitation, with cooldown, daily limit and five-attempt lockout. The URL capability stays in its fragment, then is removed from the address bar.
- Supplier contact changes revoke pending invitations. License validity and expiry are checked at every portal operation. PDFs are private, scoped and signed for 60 seconds. Audit/history updates and deletes are rejected.
- An accepted commercial proposal does not automatically sign a contract. Recording a contract requires a verified document associated with the opportunity customer and unit.

## Email

Use `RESEND_API_KEY` on the server and set `TRADING_EMAIL_FROM=cotacoes@cotacoes.expertenergy.com.br`. Domain verified in Resend on 2026-10-05, using the DKIM TXT and two DNS-only CNAME records supplied by Resend. Existing notification DNS and domain were preserved.

Invitations, customer approval notices and OTP messages use the responsive EnergyOS HTML renderer with a plain-text alternative. Opportunity values are escaped and portal links are restricted to the application's HTTPS portal. API requests use a timeout and idempotency key. Provider acceptance is recorded as `ACCEPTED`, never as proof of delivery. An uncertain response requires operator review before retrying.

Reusable Resend template: `5a71ab51-1ae1-4e63-aeb6-ba5305a90d12`, alias `energyos-trading-hub-convite-de-cotao`. Published with seven string variables: `OPORTUNIDADE`, `SUBMERCADO`, `MODALIDADE`, `CONSUMO`, `FORNECIMENTO`, `PRAZO_RESPOSTA`, `PORTAL_URL`. Application emails render actual data directly; they do not depend on changing the dashboard template.

## Release sequence

1. Validate both migrations inside a rollback transaction against the target schema.
2. Apply `20261005_f7_1_trading_hub.sql`, then `20261005_f7_2_trading_portal.sql`. Each is transactional and must be applied once by the authorized database operator.
3. Deploy backend/frontend together and set the server sender configuration. Do not put the API key in the frontend or in documentation.
4. Confirm the module option in the plan/license editor and access denial with an unlicensed organization. Enable only the specifically selected plan/license through the normal audited workflow.
5. Exercise a real invitation only with an explicitly authorized recipient. No supplier/client emails are sent by release verification.

## Validation

Backend TypeScript and 40 tests across trading validation/comparison, portal, email renderer, plans and license entitlement passed locally. The email tests mock the provider and check escaped data, unsafe URLs, OTP presentation, text/HTML payloads and idempotency. Remote rollback tests exercised plan/license preservation, public-role denial, private storage, supplier scoping, OTP limits, response replay denial and immutable audit. No fixtures were committed to the database.

Deployment status must be confirmed separately from template publication and domain verification.
