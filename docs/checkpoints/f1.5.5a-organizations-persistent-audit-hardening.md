# F1.5.5a — Organizations Persistent Audit Hardening

## Status

COMPLETE — pending publication commit.

## Scope

This checkpoint hardens persistent audit coverage for platform-level
Organization mutations without changing routes, DTO payload contracts,
RBAC permissions, tenant resolution, or soft-delete semantics.

Covered mutations:

- CREATE organization
- UPDATE organization
- DELETE organization

## Persistent audit primitives

AuditService now exposes generic persistent primitives:

- logCreate
- logUpdate

Both write to `audit_logs` and fail closed when persistent audit
persistence fails.

Existing `logDelete` remains the persistent DELETE primitive.

## Actor context

Organization mutation controllers forward authenticated platform actor
metadata to the service:

- actorUserId
- ipAddress
- userAgent

No tenant organization context is inferred from the platform actor.

For organization audit entries, the target organization is the audit
`organization_id`.

## CREATE integrity

Organization CREATE:

1. persists the organization;
2. audits the database-confirmed created state;
3. uses the returned database identity as audit authority;
4. if audit persistence fails, attempts guarded compensation of the
   just-created organization;
5. propagates the audit failure when compensation succeeds;
6. surfaces an integrity error if compensation itself fails.

Compensation is guarded by the created organization identity and its
written state.

## UPDATE integrity

Organization UPDATE:

1. captures the before state;
2. persists the mutation;
3. audits exact before/after states;
4. if audit persistence fails, attempts guarded rollback;
5. rollback is conditioned on the `updated_at` value written by the
   failed audited mutation, preventing blind overwrite of a newer state;
6. propagates audit failure when compensation succeeds;
7. surfaces an integrity error if compensation fails.

## DELETE integrity

Organization DELETE remains a soft-delete.

The operation now:

1. captures the before state;
2. writes a single generated `deleted_at`;
3. persists the DELETE audit;
4. if audit persistence fails, attempts to restore `deleted_at = null`;
5. compensation is guarded by organization id plus the exact
   `deleted_at` written by the failed audited mutation;
6. propagates audit failure when compensation succeeds;
7. surfaces an integrity error if compensation fails.

No hard-delete behavior was introduced.

## Authorization compatibility

Existing platform RBAC remains unchanged:

- platform organizations create
- platform organizations update
- platform organizations delete
- platform organizations view

No organization mutation derives authorization from frontend state.

## Non-goals

This checkpoint does not:

- add persistent audit to unrelated business modules;
- change organization routes;
- change organization DTO payloads;
- change RBAC permission assignments;
- redesign audit_logs;
- change tenant membership resolution;
- modify RLS;
- introduce hard delete;
- begin Phase 2.

## Remaining F1.5 work

F1.5.5a closes only Organizations persistent audit hardening.

Persistent audit coverage for other mutation domains must be classified
against the phased architecture before additional audit enforcement is
introduced.

Other Foundation closeout work remains separately tracked, including
RLS review, license permission assignment review, dependency security
review, and external credential rotation.
