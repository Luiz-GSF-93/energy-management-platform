# F1.2.3 — Organization Membership Deactivation

Status: APPROVED DESIGN
Phase: Foundation / F1.2 User Lifecycle
Baseline: ee5819ece43cb918b4ac8043aa4c07634facb111

## 1. Objective

Add organization-scoped administrative user deactivation without deleting
the Supabase identity, user profile, membership history, or access belonging
to another organization.

This checkpoint implements access revocation for one organization by changing
the authoritative organization membership status.

## 2. Existing authority

Organization access authority is:

- `organization_members`
- scoped by `user_id + organization_id`
- active access requires `status = 'active'`
- organization role authority remains `organization_members.role_id`

Existing authentication/context and tenant enforcement already require an
active organization membership.

The existing status vocabulary already includes `active` and `inactive`.

Therefore F1.2.3 MUST reuse:

`active -> inactive`

No new membership status is introduced.

## 3. API contract

Endpoint:

`DELETE /api/v1/admin/users/:userId`

Required permission:

`ORGANIZATION_USERS_DELETE`

The organization MUST come only from the validated tenant/access context.

The request body MUST NOT be allowed to select or override organization ID.

## 4. Mutation authority

F1.2.3 changes only:

`organization_members.status`

Allowed transition:

`active -> inactive`

F1.2.3 MUST NOT:

- delete the organization_members row;
- delete or disable auth.users;
- mutate user_profiles;
- mutate affiliation_type;
- mutate role_id;
- mutate user_roles;
- mutate memberships belonging to another organization;
- introduce global/platform-admin bypass behavior;
- change authentication or tenant guards;
- change RLS or database schema.

## 5. Target validation

The service MUST resolve the target membership using:

- target user ID;
- actor current organization ID;
- status = active.

Exactly one active membership MUST exist.

Zero active memberships MUST fail closed.

Multiple active memberships MUST be treated as a data-integrity failure.

The returned membership row MUST be structurally validated before mutation.

## 6. Self-deactivation policy

F1.2.3 MUST reject self-deactivation when:

`targetUserId === actorUserId`

Rationale:

The actor's current organization membership is the authority used for the
request context. Silently invalidating that authority during the same
administrative operation introduces ambiguous post-operation context and
recovery behavior.

Self-removal or organization-exit behavior requires a separately designed
workflow and is outside F1.2.3.

## 7. Compare-and-swap mutation

The mutation MUST be a guarded compare-and-swap equivalent to:

WHERE
  user_id = targetUserId
  AND organization_id = actorOrganizationId
  AND status = 'active'

SET
  status = 'inactive'

Exactly one row MUST be returned/confirmed.

Zero rows after validation MUST be treated as a concurrent or invalid update.

More than one affected row MUST be treated as a data-integrity failure.

## 8. Persistent audit

A dedicated audit primitive MUST be introduced.

Recommended action:

`DEACTIVATE_USER_MEMBERSHIP`

Resource type:

`organization_membership`

Resource ID:

membership ID

Audit context MUST include:

- actor user ID;
- organization ID;
- target user ID;
- membership ID;
- before status = active;
- after status = inactive;
- IP address when available;
- user agent when available;
- success status;
- timestamp.

The generic DELETE audit primitive MUST NOT be used as the semantic authority
for this operation because the membership is not deleted.

## 9. Audit failure compensation

Audit is mandatory.

If the membership update succeeds but persistent audit fails, the service MUST
attempt a guarded rollback.

Rollback predicate MUST include:

- target user ID;
- same organization ID;
- current status = inactive;
- same membership identity where practical.

Rollback transition:

`inactive -> active`

Exactly one reverted membership MUST be confirmed.

The rollback MUST NOT overwrite a later concurrent status change.

If rollback is confirmed, return an internal error stating that audit failed
and the deactivation was reverted.

If rollback cannot be confirmed, return a CRITICAL internal error requiring
administrative intervention.

## 10. Response

On success, return only the minimum organization-scoped result, for example:

{
  "userId": "...",
  "membershipStatus": "inactive"
}

No profile or global-role information is required.

## 11. Tenant isolation

The operation MUST never mutate a membership in another organization.

A user with memberships in organizations A and B who is deactivated in A
MUST retain the membership in B unchanged.

No organization ID from URL parameters or request body may replace the
validated actor organization context.

## 12. Authentication/context compatibility

After deactivation, the target membership MUST no longer qualify as active
authority for:

- /auth/context;
- TenantGuard organization resolution;
- organization switching to that organization.

Existing recovery behavior MUST remain unchanged.

F1.2.3 MUST NOT modify auth/context, switch-organization, TenantGuard,
RoleGuard, or recovery endpoint semantics.

## 13. Read compatibility

Existing admin user list/read behavior intentionally includes membership
statuses beyond active.

Therefore an inactive membership remains visible to authorized organization
administrators through existing read surfaces.

No read-contract change is required.

## 14. Reactivation

Reactivation is explicitly OUT OF SCOPE for F1.2.3.

No endpoint may silently reactivate an inactive membership.

If reactivation is required, it MUST be implemented in a separately reviewed
checkpoint with explicit authorization, CAS, audit, and regression coverage.

## 15. Required tests

Service coverage MUST prove at least:

1. target query is scoped by user + current organization + active status;
2. missing active membership fails closed;
3. duplicate active memberships fail closed;
4. membership query failure fails closed;
5. malformed membership fails closed;
6. self-deactivation is rejected;
7. only status is changed;
8. CAS includes target user;
9. CAS includes current organization;
10. CAS includes before status active;
11. successful update requires exactly one row;
12. zero-row CAS result fails;
13. update query failure fails;
14. other-organization memberships are not targeted;
15. auth.users is never mutated;
16. user_profiles is never mutated;
17. user_roles is never mutated;
18. successful mutation emits exact audit context;
19. audit failure triggers rollback;
20. rollback is scoped to target user;
21. rollback is scoped to current organization;
22. rollback requires current status inactive;
23. successful rollback produces reverted-operation error;
24. failed/unconfirmed rollback produces CRITICAL error.

Controller coverage MUST prove:

1. route is DELETE /admin/users/:userId;
2. ORGANIZATION_USERS_DELETE is required;
3. insufficient permission is rejected by guard contract;
4. target user ID is forwarded;
5. organization comes from tenant context;
6. actor user ID is forwarded;
7. IP is forwarded;
8. user-agent is forwarded;
9. no organization body parameter is accepted;
10. existing role route remains unchanged;
11. existing affiliation route remains unchanged.
