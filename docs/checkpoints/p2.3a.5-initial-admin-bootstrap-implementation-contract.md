# P2.3a.5 — Initial Admin Bootstrap Implementation Contract

## Status

IMPLEMENTATION CONTRACT APPROVED — implementation pending.

Phase 2 — Administration remains active.

P2.3 — User Management remains active.

P2.3a remains open pending positive production read validation.

P2.3b remains blocked.

## Objective

Define the exact implementation boundary for the exceptional first
Organization Administrator bootstrap authorized by the published P2.3a.5
decision.

The implementation must establish exactly one initial active `admin_org`
membership without weakening normal organization-scoped User Management.

## Platform endpoint

Bootstrap is exposed through Platform Administration.

The controller must follow the existing Organizations platform pattern:

- `@PlatformScope()`;
- explicit `@RequirePermission(...)`;
- authenticated Platform actor from the request;
- explicit target Organization identifier;
- no tenant organization context.

The operation must not add a Platform Admin bypass to
`/api/v1/admin/users`.

## Dedicated permission

A dedicated platform permission must be introduced.

Canonical permission name:

`platform.organizations.bootstrap_admin`

Canonical backend constant:

`PLATFORM_ORGANIZATIONS_BOOTSTRAP_ADMIN`

The permission must be cataloged through a database migration and assigned
only to the existing `admin_platform` role.

The permission UUID must be generated once during implementation and then
used consistently by:

- permission catalog migration;
- backend permission constant;
- controller authorization tests.

It must not be added to organization roles.

## Request contract

Bootstrap must receive:

- target Organization identifier;
- target email;
- target name;
- target affiliation type.

The client must not supply:

- destination role identifier;
- membership status;
- actor identifier;
- arbitrary permission set.

The backend always resolves the destination role as `admin_org`.

Membership status is always `active`.

## Organization validation

Before identity provisioning, the backend must prove that the target
Organization:

- exists;
- is not soft-deleted;
- is uniquely resolved.

Missing Organization is a not-found condition.

Ambiguous or malformed persistent state fails closed.

## Role validation

The backend must resolve exactly one role satisfying:

- target Organization;
- scope `organization`;
- name `admin_org`.

The client does not choose the bootstrap role.

Missing or ambiguous `admin_org` state fails closed.

## Identity and profile resolution

Bootstrap must reuse the identity-resolution semantics already established by
User Invite.

The preferred resolution path is profile-first.

For an existing profile:

- email integrity must match;
- the corresponding Auth identity must exist;
- Auth identity and profile must refer to the same user.

If no profile exists, Auth lookup must be bounded and prove exhaustion.

An existing Auth identity without a valid profile fails closed.

Bootstrap must not silently repair identity/profile inconsistency.

## New identity provisioning

If no identity exists, bootstrap may provision an invited identity through
the existing administrative Auth mechanism.

A newly created identity must be followed by creation of the corresponding
user profile.

The profile must preserve:

- normalized email;
- requested name;
- target Organization;
- requested affiliation.

Only resources created by the bootstrap execution are owned by bootstrap
compensation.

## Existing profile boundary

Bootstrap must not rewrite an existing profile's:

- name;
- Organization pointer;
- affiliation.

If the existing profile affiliation differs from the bootstrap request,
bootstrap returns a domain conflict.

## Atomic membership bootstrap

The first-admin eligibility decision and membership creation must occur in one
database concurrency boundary.

Nest must not implement:

`check zero administrators → separate membership insert`

as independent operations.

A database RPC must perform the authoritative atomic membership bootstrap.

## RPC contract

The migration must introduce a narrowly scoped database function for initial
Organization administrator membership creation.

The RPC receives only:

- target Organization ID;
- target User ID.

The RPC itself resolves `admin_org`.

The RPC must not accept a role ID supplied by the caller.

## RPC concurrency boundary

The RPC must serialize bootstrap attempts per Organization.

A transaction-scoped PostgreSQL advisory lock derived from the target
Organization identifier is the approved serialization mechanism.

After acquiring the lock, the RPC must re-evaluate every bootstrap
precondition.

The lock must not be global across all Organizations.

## RPC eligibility checks

Inside the serialized boundary, the RPC must prove:

1. target Organization exists and is not soft-deleted;
2. exactly one target `admin_org` role exists;
3. no active membership exists for a role named:
   - `admin_org`;
   - `gestor`;
4. target User has no existing membership in the target Organization.

The dependency checks are existence-based.

Invalid or ambiguous state fails closed.

## RPC mutation

Only after all eligibility checks pass may the RPC create:

- one organization membership;
- for the target User;
- in the target Organization;
- with the resolved `admin_org` role;
- with status `active`.

The RPC must return enough identifiers and state for the Nest service to
confirm the mutation.

## RPC conflict semantics

The RPC must distinguish expected bootstrap conflicts from infrastructure
failures.

Expected conflict conditions include:

- Organization already has an active administrative membership;
- target User already has a membership in the Organization;
- concurrent bootstrap completed first.

The Nest service maps expected bootstrap conflicts to HTTP 409.

Missing target Organization maps to HTTP 404.

Invalid persistent integrity or database execution failure fails closed.

## Function exposure

The bootstrap function is an internal service-role primitive.

It must not become an anonymous or authenticated-client mutation surface.

Execution privileges must be restricted appropriately for the existing
backend service-role architecture.

The browser must never call the RPC directly.

## Persistent audit

After successful membership creation, the Nest service must persist bootstrap
audit evidence through the existing AuditService infrastructure.

The audit must identify:

- authenticated Platform actor;
- target Organization;
- target User;
- resulting membership;
- resulting `admin_org` role;
- bootstrap action;
- request IP when available;
- request user-agent when available.

Credential values must never be included.

## Audit failure compensation

A successful membership bootstrap followed by audit failure must not leave
unaudited administrative authority.

If audit persistence fails, the Nest service must attempt guarded compensation
of the membership created by that bootstrap execution.

Compensation must be guarded by:

- exact membership ID;
- target User ID;
- target Organization ID;
- resolved `admin_org` role ID;
- status `active`.

The compensation must not delete any pre-existing identity or profile.

## Identity/profile compensation

If bootstrap created a new identity and profile but membership bootstrap
fails, compensation may remove only the identity/profile created by that
execution.

If membership creation succeeds and later audit compensation succeeds, any
new identity/profile created solely by that bootstrap may also be compensated
only when ownership can be proven.

Pre-existing identity/profile resources must never be deleted.

If compensation cannot be confirmed, the service must surface a critical
integrity error.

## Idempotency

A successfully bootstrapped Organization cannot be bootstrapped again.

Repeated execution returns a domain conflict and performs no new membership
mutation.

Bootstrap is not a general administrator-creation endpoint.

## Frontend boundary

No new frontend bootstrap UI is included in the first implementation.

Controlled bootstrap is exercised through the protected backend Platform
Administration contract.

`/backoffice/users` remains organization-scoped.

## Required tests

The implementation must include focused tests proving:

- controller is platform-scoped;
- controller requires the dedicated bootstrap permission;
- controller forwards authenticated Platform actor;
- target Organization validation;
- `admin_org` role resolution;
- profile-first identity reuse;
- fail-closed identity-without-profile behavior;
- affiliation conflict;
- new identity/profile provisioning;
- existing membership conflict;
- already-bootstrapped conflict;
- atomic RPC invocation;
- successful bootstrap result validation;
- persistent audit;
- audit-failure compensation;
- compensation does not delete pre-existing identity/profile;
- infrastructure failure fails closed.

The database migration must include preflight/postflight assertions where
appropriate.

## Production validation boundary

Production bootstrap validation is intentionally mutating and must occur
exactly once for the controlled target Organization.

Before bootstrap, production validation must confirm:

- zero active `admin_org` memberships;
- zero active `gestor` memberships.

The controlled target identity must be explicitly chosen.

After bootstrap:

- exactly one active `admin_org` membership must exist;
- the bootstrapped actor must authenticate normally;
- organization context must resolve;
- `ORGANIZATION_USERS_VIEW` must be present.

Then P2.3a validation returns to read-only behavior:

- Users list HTTP 200;
- User detail HTTP 200;
- safe User contracts valid;
- no further mutation.

## Scope boundary

This implementation does not authorize:

- changing `consulta`;
- changing `operacional`;
- permanent Platform Admin User Management bypass;
- arbitrary role assignment;
- Membership Reactivation;
- P2.3b Invite frontend implementation;
- P2.4 or later Phase 2 work.

## Decision

P2.3a.5 requires a backend Platform Administration endpoint plus a database
migration providing the atomic bootstrap RPC and dedicated permission catalog
entry.

Identity/profile provisioning remains in Nest because it integrates with
Supabase Auth.

The first-admin eligibility decision and organization membership creation
remain database-atomic.

P2.3a remains open until bootstrap is deployed and the positive Users
list/detail production validation succeeds.

P2.3b remains blocked.

## Publication state

This implementation contract is pending review and publication.

Bootstrap code and database migration must not begin until this contract is
published.
