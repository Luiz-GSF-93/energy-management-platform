## HTTP contract

Endpoint:

`POST /licenses`

Required permission:

`ORGANIZATION_LICENSES_CREATE`

The controller uses the validated `TenantContext` as the source of:

- actor user id
- organization id

Request metadata used for persistent audit:

- IP address
- user-agent

The route uses a local hardened `ValidationPipe` with:

- `transform: true`
- `whitelist: true`
- `forbidNonWhitelisted: true`

The existing `GET /licenses/effective` and its VIEW permission remain
unchanged.

## Create DTO

Required client fields:

- `licenseType`
- `documentsLimit`
- `renewalDate`
- `startDate`

Optional client fields:

- `endDate`
- `maxConsumerUnits`
- `documentManagement`
- `advancedAnalytics`
- `reportGeneration`
- `freeMarketManagement`

Not client-controlled:

- id
- organization id
- documents used
- active
- status
- created timestamp
- updated timestamp

Numeric limits use a minimum value of zero.

Date fields are constrained to valid date strings in the exact
`YYYY-MM-DD` representation expected by PostgreSQL `date` columns.

## Lifecycle behavior

New licenses created through this endpoint are initialized by the backend
with:

- `status = ACTIVE`
- `active = true`

The client cannot choose the initial lifecycle state.

`startDate` is required for active license creation.

If `endDate` is supplied and is before `startDate`, the application rejects
the request before persistence.

The database validity CHECK remains the final persistence authority.

`renewalDate` remains a commercial/renewal field and is not interpreted as
the effective-license validity boundary.

## Tenant isolation

`organization_id` is never accepted from the request DTO.

The persisted organization is derived from:

`TenantContext.organizationId`

This preserves the ADR 009 authority chain:

identity -> membership/tenant context -> RBAC -> license

No client-provided tenant selector is introduced.

## Concurrency and conflict handling

F1.4h remains the authoritative concurrency control for effective active
license cardinality.

The application does not rely on a read-before-write overlap check.

A database error is translated to a create conflict only when:

- SQLSTATE/code is `23P01`; and
- constraint evidence identifies
  `licenses_active_validity_excl`.

Other database failures fail closed as internal errors.

## Post-insert integrity

After a successful insert response, the service first confirms that the
created identity can be safely attributed to this operation:

- non-empty license id
- returned organization equals validated organization

If that identity cannot be confirmed, the operation fails critically and
does not perform a broad compensating delete.

After identity confirmation, the service validates the required creation
contract and lifecycle state.

If returned content violates the expected creation contract, the service
attempts compensation using the exact:

- license id
- organization id

The compensation must confirm exactly one matching deleted row.

Failure to confirm compensation is treated as a critical integrity error.

## Persistent audit

Successful creation is audited through `AuditService.logLicenseCreation`.

Audit contract:

- action: `CREATE_LICENSE`
- resource type: `license`
- resource id: created license id
- organization id: validated organization
- user id: authenticated actor
- before: null
- after: created license record
- IP address when available
- user-agent when available
- persistent success record

Audit insertion failure fails closed.

## Audit compensation

If persistent audit fails after successful license creation, the service
attempts to remove only the license created by the current operation.

Compensation is scoped by both:

- exact created license id
- validated organization id

The delete result must confirm exactly one matching record.

If compensation succeeds, creation fails and reports that the operation was
reverted.

If compensation cannot be confirmed, the service raises a critical error.

This internal compensation mechanism does not expose a public hard-delete
license capability.

## Focused specifications added or updated

Create service specification contains 11 cases covering:

1. invalid temporal range rejected before persistence
2. successful active creation and audit
3. explicit optional configuration
4. approved exclusion-constraint conflict mapping
5. generic database failure not misclassified as overlap conflict
6. unconfirmed created identity fails critically without broad deletion
7. returned-content integrity violation triggers exact compensation
8. integrity compensation failure is critical
9. persistent audit failure triggers exact compensation
10. unconfirmed audit compensation is critical
11. compensation database error is critical

Controller specifications cover:

- CREATE permission metadata
- validated tenant forwarding
- actor forwarding
- organization forwarding
- IP forwarding
- user-agent forwarding
- preservation of effective-license VIEW behavior

Audit specifications cover:

- exact persistent `CREATE_LICENSE` audit payload
- nullable request metadata
- fail-closed persistent audit failure

The pre-existing effective-license service specification was updated only
to supply the newly required `AuditService` constructor dependency.

## Security properties

F1.4i.2 preserves the following properties:

- authentication remains handled by the existing application stack
- authorization requires the existing CREATE permission
- organization scope comes from validated tenant context
- request payload cannot select another organization
- request payload cannot choose lifecycle state
