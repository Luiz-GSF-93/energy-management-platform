# F1.5.6b — Foundation RLS Migration Design

## Status

Exact migration design approved for implementation preparation.

No RLS DDL is authorized for execution by this document.

## Baseline

The target tables are:

- organizations
- organization_members
- audit_logs
- licenses

Current policy inventory:

- audit_logs: one legacy SELECT policy derived from user_profiles.organization_id
- organization_members: one legacy INSERT policy derived from user_profiles.organization_id
- organization_members: one SELECT policy without active-membership enforcement
- organizations: one unconditional SELECT policy
- organizations: one unconditional UPDATE policy
- licenses: RLS enabled with zero policies

## Authority

ADR-009 active organization membership is the tenant authority.

New Foundation RLS MUST NOT derive tenant authorization solely from
user_profiles.organization_id.

Backend authentication, TenantContext and RBAC remain authoritative for
application authorization.

## Helper contract

Introduce a narrowly scoped helper:

`public.is_active_org_member(target_organization_id text) -> boolean`

Requirements:

- authenticated identity comes exclusively from auth.uid();
- caller cannot provide a user id;
- membership must match target organization;
- membership status must equal `active`;
- null authenticated identity fails closed;
- null organization id fails closed;
- helper performs no RBAC evaluation;
- helper is SECURITY DEFINER only to avoid organization_members RLS recursion;
- search_path is fixed;
- execution privileges are explicit;
- PUBLIC execution is revoked.

The legacy get_user_organization(uuid) helper is not modified or reused.

## Policy contract

### organizations

SELECT:
allow authenticated users only when an active membership exists for the row
organization id.

No direct authenticated INSERT, UPDATE or DELETE policy is introduced.

The existing unconditional UPDATE policy must be removed.

### organization_members

SELECT:
allow authenticated users to see membership rows only for organizations in
which the authenticated user has an active membership.

No direct authenticated INSERT, UPDATE or DELETE policy is introduced.

The legacy INSERT policy must be removed.

### audit_logs

SELECT:
allow authenticated users only when an active membership exists for the audit
row organization id.

No authenticated write policy is introduced.

### licenses

SELECT:
allow authenticated users only when an active membership exists for the
license row organization id.

No authenticated write policy is introduced.

## Anonymous access

No new policy is granted TO anon.

Anonymous access to rows in the four hardened tables must remain fail-closed
through RLS.

## Platform Admin

No RLS-wide Platform Admin bypass is introduced.

Platform-global operations continue through explicitly authorized backend
flows using the privileged service client.

Service-client privilege is not application authorization.

## Direct-write compatibility decision

The migration intentionally removes these legacy direct authenticated/public
write paths:

- organizations UPDATE through the unconditional legacy policy;
- organization_members INSERT through the user_profiles-derived legacy policy.

No replacement direct-write policy is introduced in this checkpoint.

Authorized application writes continue through backend service-role flows
protected by TenantContext and RBAC.

## Out of scope

This migration does not modify:

- roles
- role_permissions
- user_profiles
- user_roles
- get_user_organization(uuid)
- domain-table RLS
- table grants
- JWT claims
- TenantContext semantics
- organization switching
- application permissions

## Migration requirements

The migration must:

1. create the membership helper deterministically;
2. revoke PUBLIC execution explicitly;
3. grant helper execution only as required for authenticated RLS evaluation;
4. drop the five known legacy policies by exact name;
5. create explicit SELECT policies TO authenticated;
6. leave direct writes fail-closed;
7. keep RLS enabled;
8. avoid disabling or bypassing RLS;
9. avoid unrelated schema changes.

## Validation requirements

Postflight must prove:

1. the five legacy policies no longer exist;
2. exactly four target SELECT policies exist;
3. target policies apply to authenticated;
4. organizations has no direct authenticated write policy;
5. organization_members has no direct authenticated write policy;
6. licenses has an active-membership SELECT policy;
7. helper is SECURITY DEFINER with fixed search_path;
8. PUBLIC cannot execute the helper;
9. authenticated can execute the helper;
10. anon cannot execute the helper;
11. RLS remains enabled on all four tables;
12. backend regression remains green.

A separate JWT-based proof must validate:

- active member can read own organization-scoped rows;
- cross-tenant reads fail;
- inactive/non-member reads fail;
- anonymous reads fail;
- direct authenticated writes fail;
- backend authorized service-role flows remain compatible.

## Decision

Proceed to versioned migration implementation.

Do not execute the migration until its exact SQL has been reviewed.
