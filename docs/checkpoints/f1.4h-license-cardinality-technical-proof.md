# F1.4h — License Cardinality Technical Proof

## Status

PRE-DDL PROOF — no production DDL authorized by this document.

- no user-defined license trigger was found.

## Intended architecture

The preferred implementation remains a declarative PostgreSQL GiST exclusion
constraint.

The intended invariant is:

- same organization;
- overlapping validity periods;
- both rows participate in the active-license subset.

The database, not application read-before-write logic, must be the
authoritative concurrency barrier.

## Temporal semantics

`start_date` is the first valid calendar day.

`end_date`, when present, is the last valid calendar day.

Therefore both contractual boundaries are semantically inclusive.

A missing `end_date` represents open-ended validity.

## daterange proof

Read-only PostgreSQL expressions were executed without modifying application
tables.

Observed results:

- contained interval: overlap = true;
- next-calendar-day interval: overlap = false;
- same end/start calendar day: overlap = true;
- open-ended interval against a later interval: overlap = true.

PostgreSQL canonicalized finite inclusive discrete date ranges into its
canonical half-open representation.

For example, a contractual inclusive end date of 2026-01-31 is represented
canonically with an exclusive upper bound of 2026-02-01.

This canonicalization preserves the approved contractual semantics.

## Boundary decision

Two active licenses must conflict when one license starts on the same calendar
day that the other license ends.

They must not conflict when the second license starts on the calendar day
immediately after the first license ends.

The future exclusion expression must preserve this behavior.

## Open-ended decision

A license with no `end_date` must conflict with every later active license for
the same organization whose validity intersects that open-ended period.

No artificial maximum date should be introduced into persisted license data.

## Lifecycle predicate

The F1.4g lifecycle contract remains authoritative.

The exclusion mechanism must apply only to rows representing an active
license.

The implementation predicate must remain compatible with the existing
status/active consistency constraint.

No lifecycle vocabulary change is authorized here.

## Extension installation gate

`btree_gist` is available but not installed.

Installing it is an explicit database capability change.

No `CREATE EXTENSION` is authorized by this proof document.

Any production installation must be:

- explicit;
- versioned;
- reviewed;
- performed only as part of the approved implementation migration;
- verified after execution.

## Concurrency proof still required

The range-expression semantics are proven, but production concurrency
enforcement is not yet proven.

Before F1.4h implementation can close, authoritative evidence must demonstrate
that two concurrent conflicting writes cannot both commit.

A sequential conflict test alone is insufficient.

## Rollback and failure requirements

The implementation must fail closed on conflicting active-license periods.

It must not:

- overwrite an existing validated license;
- delete historical license data;
- silently deactivate another license;
- install unrelated extensions;
- weaken F1.4g constraints;
- weaken tenant or RBAC enforcement.

## Remaining implementation gate

Before production DDL is approved:

1. define the exact `CREATE EXTENSION` behavior;
2. define the exact exclusion constraint expression;
3. define the exact active-license predicate;
4. validate null `start_date` behavior;
5. validate open-ended `end_date` behavior;
6. validate historical/non-active coexistence;
7. validate adjacent calendar-day behavior;
8. validate overlapping active rejection;
9. validate genuine concurrent conflicting writes;
10. define post-DDL verification and rollback evidence.

## Non-goals

This proof does not authorize:

- license APIs;
- frontend changes;
- RLS policies;
- permission grants;
- authentication changes;
- TenantContext changes;
- Jest/tooling remediation;
- unrelated database refactoring.

## Conclusion

The declarative exclusion-constraint architecture remains the preferred
implementation path.

Temporal range semantics required by the license domain have been proven
against the authoritative PostgreSQL engine.

Production DDL remains blocked until the remaining implementation gate is
satisfied.
