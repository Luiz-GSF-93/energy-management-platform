# F1.2.4c.2a — Organization Membership Uniqueness Integrity

## Status

Closed by authoritative database verification.

No database migration is required for this checkpoint.

## Context

F1.2.4 organization-user invitation requires database-level protection
against concurrent creation of duplicate organization memberships.

The required invariant is:

> A user may have at most one membership for a given organization.

The initial migration draft proposed a unique constraint on:

`(organization_id, user_id)`

## Authoritative database verification

The authoritative datastore was identified as the Supabase PostgreSQL
database used by the application's SupabaseService.

The separate Railway PostgreSQL service was verified not to contain the
application membership schema and was therefore excluded as the migration
target.

A read-only PostgreSQL catalog probe against the authoritative Supabase
database confirmed:

- `public.organization_members` exists;
- the table contained 2 membership rows at verification time;
- duplicate `(organization_id, user_id)` groups: 0;
- an existing validated database constraint protects the membership pair;
- existing constraint:
  `UNIQUE (user_id, organization_id)`.

For uniqueness semantics, column order does not change the invariant:
both `(user_id, organization_id)` and `(organization_id, user_id)` prevent
duplicate values of the same two-column pair.

## Application access pattern

Current membership operations commonly filter by both `user_id` and
`organization_id`.

The existing unique index therefore provides the required integrity
protection for F1.2.4 without introducing a redundant second unique index.

## Decision

Do not apply the draft migration that would add:

`UNIQUE (organization_id, user_id)`.

The draft was never committed and was never applied to any database.

It is intentionally discarded because the authoritative database already
enforces the required invariant through:

`UNIQUE (user_id, organization_id)`.

## F1.2.4 provisioning consequence

The database integrity prerequisite for organization-user invitation is
satisfied.

Provisioning logic may rely on the database uniqueness constraint as the
final concurrency boundary, while still performing application-level
preflight checks and fail-closed handling of uniqueness conflicts.

This decision does not authorize:

- membership reactivation;
- cross-organization mutation;
- profile role authority;
- Platform Admin bypass;
- generic role or permission administration;
- changes to public registration;
- unrelated schema changes.

## Security

No credential or connection string is recorded in this document.

No database write was performed as part of the disposition decision.
