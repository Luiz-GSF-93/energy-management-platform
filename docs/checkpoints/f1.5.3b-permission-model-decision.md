# F1.5.3b — Permission Model Decision

## Status

DESIGN APPROVED — implementation not yet applied.

This checkpoint does not close F1.5.3 or Phase 1.

## Problem

F1.5.3a identified authorization gaps that could not be safely
resolved using the existing permission catalog:

- PUT /documents/:id has no authoritative update permission.
- Consumer Units CRUD has no authoritative permission set.

Existing unrelated permissions must not be reused merely to close
the authorization audit.

## Current authorization authority

The current database contains both:

- roles.permissions JSONB
- role_permissions relational table

Runtime data shows that roles.permissions is the populated permission
assignment mechanism.

All current roles have JSON permission arrays.

role_permissions currently contains zero assignments.

Therefore F1.5.3b must preserve roles.permissions as the effective
assignment mechanism and must not populate role_permissions.

## Documents update

PUT /documents/:id updates document metadata/data, including description
and OCR data.

It is not semantically equivalent to:

- documents.documents.upload
- documents.documents.delete
- documents.archive.manage
- report permissions

A dedicated permission is required:

documents.documents.update

Initial role grants:

- admin_platform: granted
- admin_org: granted
- gestor: granted
- operacional: not granted
- consulta: not granted

This preserves the current Documents authorization profile: administrators
have full domain authority, gestor has document creation/management
capability, and read-oriented roles do not gain a new write capability.

## Consumer Units

Consumer Units is an independent organization-scoped CRUD resource.

It must not reuse Contract, Customer, Invoice, or other domain permissions.

New permissions:

- organization.consumer_units.view
- organization.consumer_units.create
- organization.consumer_units.update
- organization.consumer_units.delete

Initial grants:

| Role | View | Create | Update | Delete |
| --- | --- | --- | --- | --- |
| admin_platform | yes | yes | yes | yes |
| admin_org | yes | yes | yes | yes |
| gestor | yes | yes | yes | yes |
| operacional | yes | yes | yes | no |
| consulta | yes | no | no | no |

The grant model follows the existing role capability pattern without
granting destructive access to operational/read-only roles.

## Implementation rules

1. Permission records must be created in the authoritative permissions
   catalog.
2. IDs must be generated by the database. UUIDs must not be invented in
   application code before catalog creation.
3. Permission creation must be idempotent by canonical code.
4. Existing permission records must not be replaced.
5. Existing role permission arrays must not be reset or reconstructed.
6. New grants must append only the intended generated permission IDs.
7. role_permissions must remain untouched.
8. Generated UUIDs must be captured from the database and only then added
   to backend permission constants.
9. Controllers must not receive the new decorators until catalog creation,
   role grants, constants, and validation are complete.
10. No automatic grant outside the approved matrix is allowed.

## Intended controller mapping

Documents:

- PUT /documents/:id -> documents.documents.update

Consumer Units:

- POST /consumer-units -> organization.consumer_units.create
- GET /consumer-units -> organization.consumer_units.view
- GET /consumer-units/:id -> organization.consumer_units.view
- PUT /consumer-units/:id -> organization.consumer_units.update
- DELETE /consumer-units/:id -> organization.consumer_units.delete

## Security model

Identity
-> Tenant / Membership
-> RBAC
-> License entitlement where applicable
-> organization_id resource isolation

License entitlement does not replace RBAC.

## Compatibility constraints

No existing permission is removed.

No existing role permission is removed.

No existing permission UUID is changed.

No role_permissions migration is introduced.

No unrelated authorization model is refactored.

## Remaining implementation sequence

1. Create controlled permission-catalog/grant migration.
2. Review migration before execution.
3. Apply manually and verify exact catalog/grant postconditions.
4. Capture generated UUIDs.
5. Add backend constants.
6. Add controller decorators.
7. Add metadata tests.
8. Run focused tests.
9. Run full regression and build.
10. Publish F1.5.3b implementation checkpoint.

F1.5.3 remains open after this design checkpoint.
Phase 2 remains unauthorized.
