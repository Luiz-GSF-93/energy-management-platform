# P2.2d.5 — Organization Delete Backend Safety Boundary

## Status

IMPLEMENTED AND LOCALLY VALIDATED — pending publication.

Phase 2 — Administration remains active.

P2.2 — Organizations remains open.

P2.2d — Organization Delete remains open.

This checkpoint establishes the backend dependency safety boundary required
before Organization Delete may be exposed through the Administration
frontend.

P2.3 — User Management remains unauthorized.

## Objective

Implement the fail-closed Organization Delete dependency policy authorized by
the published P2.2d Organization Delete Safety Decision.

The safety boundary closes the historical gap between the original
Organization Delete architecture and the live backend implementation.

The existing soft-delete, persistent audit and guarded compensation behavior
is preserved.

No frontend Delete capability is implemented by this checkpoint.

No database migration is included.

## Published safety decision

The P2.2d Organization Delete Safety Decision established:

- dependency blocking instead of automatic cascade;
- existence-based dependency checks;
- fail-closed behavior when dependency resolution fails;
- preservation of the existing soft-delete contract;
- preservation of persistent audit and compensation;
- frontend Delete prohibition until the backend safety boundary passes.

The authorized dependency set is exactly:

- `organization_members`;
- `licenses`;
- `customers`;
- `consumer_units`;
- `energy_contracts`;
- `documents`.

No additional dependency table is introduced by this implementation.

## Dependency guard

`OrganizationsService` now resolves the authorized dependency set before
writing `organizations.deleted_at`.

For each dependency table, the service:

1. selects only the dependent row identifier;
2. constrains the query by the target `organization_id`;
3. limits the query to one row;
4. checks the query result before continuing.

The guard is existence-based.

It does not infer whether a dependency is active, inactive, historical,
expired or otherwise eligible for cascade.

No dependent row is mutated by the guard.

## Block path

If any authorized dependency query returns a row, Organization Delete is
rejected with a domain conflict.

The Organization soft-delete is not executed.

Persistent Delete audit is not executed because no Organization mutation
occurred.

The response does not expose dependent row contents.

Focused tests independently prove blocking for:

- `organization_members`;
- `licenses`;
- `customers`;
- `consumer_units`;
- `energy_contracts`;
- `documents`.

## Dependency-resolution failure

Dependency resolution fails closed.

If a dependency query returns an error, the operation stops before the
Organization soft-delete.

A dependency-query failure is never interpreted as an empty dependency set.

The focused safety test verifies that:

- the dependency error prevents Delete;
- `organizations.deleted_at` is not written;
- persistent Delete audit is not called.

## Allow path

Organization Delete may proceed only after every authorized dependency query
completes successfully and returns no blocking row.

The focused allow-path test proves that all six dependency tables are checked.

Only after those checks does the existing Organization soft-delete execute.

The Delete mutation remains constrained by:

- the target Organization identifier;
- `deleted_at IS NULL`.

Persistent Delete audit remains required after the mutation.

## Existing audit and compensation contract

The dependency guard does not replace or weaken the existing persistent
Delete audit architecture.

The existing Delete path still:

- captures the Organization state before mutation;
- generates one `deleted_at` value;
- writes that value through soft-delete;
- constructs the audited after-state from the same value;
- records persistent Delete audit.

If persistent audit fails, compensation attempts to restore:

`deleted_at = null`

only when the stored `deleted_at` still equals the value written by the failed
operation.

If persistent audit and compensation both fail, the existing integrity error
continues to surface.

## Legacy regression remediation

Existing Delete audit tests predated the dependency precondition.

Their Supabase mocks previously modeled only the Organizations mutation.

Those tests were adapted to model six successful empty dependency checks
before reaching the original Delete path.

No existing audit or compensation assertion was removed.

The preserved regression contract includes:

- audit failure propagation;
- two-write mutation/compensation expectation;
- rollback target Organization guard;
- rollback `deleted_at` guard;
- equality between the audited `deleted_at` and compensated `deleted_at`;
- integrity error when audit and compensation both fail.

The platform audit test was similarly adapted to permit empty dependency
queries while preserving its existing audit assertions.

## Frontend boundary

Organization Delete remains unavailable in the Administration frontend.

This checkpoint does not add:

- `deleteOrganization()`;
- `ORGANIZATIONS_DELETE`;
- an Organization Delete button;
- destructive confirmation UI.

Those capabilities remain blocked until this backend safety boundary is
published.

Frontend presentation authorization will not replace backend authorization or
dependency validation.

## Production boundary

No production Organization Delete is performed by this backend safety
checkpoint.

After publication, the frontend Delete slice may be implemented and locally
validated.

Production Delete validation remains separately gated.

The Organization created for P2.2b and updated by P2.2c remains the intended
candidate for a future controlled allowed-path validation, provided the live
dependency guard confirms no blocking dependencies.

No dependency may be removed merely to make that validation succeed.

## Security boundary

The backend now fails closed both when:

- a known Organization dependency exists;
- dependency resolution itself fails.

Automatic cascade remains prohibited.

Hard-delete remains prohibited.

The existing permission, soft-delete, persistent audit and guarded
compensation contracts remain authoritative.
