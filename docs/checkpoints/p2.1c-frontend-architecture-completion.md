## Objective

Complete the remaining Backoffice Foundation architecture requirements before
formal P2.1 closeout.

The remaining requirements were:

- establish the sustainable frontend lint baseline required by P2.0;
- materialize permission-aware navigation;
- remove obsolete Tailwind configuration after proving it was no longer part
  of the executable frontend architecture.

No Administration business module is implemented by this checkpoint.

## Lint architecture

P2.0 required the rebuilt frontend to establish a sustainable lint baseline
rather than restoring the obsolete `next lint` workflow.

P2.1c introduced a frontend-owned ESLint flat configuration.

The accepted lint baseline uses:

- ESLint 10;
- `@eslint/js`;
- `typescript-eslint`;
- `eslint-plugin-react-hooks`;
- `globals`.

The frontend package now exposes:

`npm run lint`

The lint architecture does not use `eslint-config-next`.

Compatibility discovery established that the available
`eslint-config-next@16.3.6` path and the previously attempted ESLint 10
combination were not accepted as the repository baseline.

ESLint 9 releases inspected during P2.1c were also reported by the package
registry as unsupported.

The selected architecture therefore uses the supported ESLint 10 core with
plugins whose published peer contracts accept that major version.

Plugins whose inspected peer contracts did not declare ESLint 10 support were
not forced into the dependency tree.

No peer-dependency override is used.

## First lint execution

The first execution of the new lint baseline found two real issues:

1. the CommonJS `next.config.js` environment was not represented in the flat
   lint configuration;
2. the authentication bootstrap called a state-changing refresh path directly
   from a React effect.

Both findings were corrected.

The CommonJS configuration environment is now explicitly represented in the
flat lint configuration.

The authentication bootstrap now schedules its asynchronous refresh path and
preserves the existing fail-closed authentication behavior.

No lint suppression was introduced to hide either finding.

The subsequent lint regression passed.

## Permission-aware navigation

P2.0 explicitly requires permission-aware navigation as part of P2.1.

Before P2.1c, the authentication provider already exposed:

`hasPermission(permission)`

That helper evaluates only the current organization permission context.

The Sidebar, however, still rendered its Dashboard link statically.

P2.1c introduced a reusable Backoffice navigation contract with:

- route;
- label;
- optional permission requirement.

Navigation visibility is now filtered through the existing
`hasPermission()` authority.

Items without a permission requirement remain visible to authenticated
Backoffice users.

Items with a permission requirement are visible only when
`hasPermission()` accepts that permission.

## Current navigation boundary

The current navigation configuration contains only:

- Dashboard.

Dashboard has no permission requirement because it belongs to the authenticated
Backoffice shell rather than a Phase 2 business module.

P2.1c does not add routes for:

- Organizations;
- User Management;
- Licenses;
- Settings.

P2.1c also does not copy future Administration permission UUIDs or permission
constants into the frontend.

Later modules may extend the navigation contract only when their own scoped
checkpoint authorizes the corresponding route and permission requirement.

Frontend navigation visibility remains presentation behavior only.

Backend authorization remains authoritative.

## Navigation validation

The permission-aware navigation primitive was validated with three cases:

- an item without a permission requirement remains visible;
- an item with a granted permission remains visible;
- an item with a denied permission is filtered out.

The previous static Dashboard link in the Sidebar was removed in favor of the
navigation configuration.

No P2.2 route was created.

No Administration business permission was hardcoded into the navigation
foundation.

## Tailwind cleanup

P2.1a had intentionally preserved the historical
`frontend/tailwind.config.ts` until the styling architecture could be fully
reconciled.

P2.1 closeout review confirmed:

- Tailwind is not declared by `frontend/package.json`;
- no remaining frontend component depends on Tailwind utility classes;
- the historical Tailwind config was the only executable frontend reference
  to Tailwind.

P2.1c therefore removes the obsolete `frontend/tailwind.config.ts`.

The accepted styling architecture remains the global CSS/design-token and
reusable-component foundation established by P2.1a.
