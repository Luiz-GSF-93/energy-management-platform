# F1.4f — License Integrity & RLS Design

## Status

Design checkpoint only. No DDL is authorized by this document.

## Authoritative baseline

F1.4e established the authoritative persistence state for `public.licenses`.

The table exists, is empty, has RLS enabled, has no RLS policies, has no
foreign key on `organization_id`, and has no CHECK constraints.

## Tenant ownership

A license belongs to exactly one organization through `organization_id`.

`licenses.organization_id` and `organizations.id` are both `text` and are
type-compatible.

The persistence integrity target is a foreign key from
`licenses.organization_id` to `organizations.id`.

The existing non-unique organization index is preserved.

## Tenant authorization

The approved Multi-Org authority remains:

identity -> organization_members -> active organization context -> RBAC.

New license RLS must not copy the legacy pattern that derives tenant
authorization solely from `user_profiles.organization_id`.

For organization-scoped access, membership must be validated through
`organization_members` for the authenticated user, matching the license
organization and requiring an active membership.

RLS is defense in depth. It does not replace backend enforcement.

The backend remains responsible for:

- authentication;
- validated TenantContext;
- organization scope;
- role;
- permission;
- input validation.

## RBAC

The authoritative permission catalog already contains:

- `organization.licenses.view`;
- `organization.licenses.create`;
- `organization.licenses.update`.

No license permission is currently assigned to any role.

F1.4 must not automatically grant these permissions or create aliases.

Role-permission administration remains a separate administration concern.

There is no license DELETE permission. License termination is lifecycle based,
not hard deletion.

## Lifecycle

The normalized lifecycle vocabulary is:

- active;
- suspended;
- expired;
- cancelled.

`status` and `active` represent the same lifecycle boundary and must remain
consistent.

An active lifecycle maps to `active = true`.

Suspended, expired and cancelled lifecycles map to `active = false`.

Unknown lifecycle values must fail closed.

## Temporal integrity

`start_date` represents the beginning of the license validity interval.

`end_date` is optional.

When `end_date` is present, it must not precede `start_date`.

`renewal_date` remains a separate commercial field and is not treated as the
validity end date.

## Cardinality and concurrency

Historical licenses may coexist for one organization.

A global `UNIQUE(organization_id)` is prohibited.

Overlapping effective active periods for the same organization are not
allowed by the target model.

Neither `btree_gist` nor `btree_gin` is currently installed.

F1.4 must not silently install PostgreSQL extensions.

Application-only read-before-write is not sufficient as a concurrency
guarantee.

Therefore concurrency-safe temporal cardinality remains explicitly unresolved
until a compatible database-backed mechanism is designed and approved.

License creation must not be considered production-complete while this
invariant lacks an approved enforcement mechanism.

## RLS boundary

The target RLS responsibility is tenant isolation through active organization
membership.

RBAC permission evaluation remains authoritative in the backend for F1.4.

This avoids coupling database policies to role-permission administration while
still providing a database-level tenant boundary.

Exact CREATE/UPDATE policy DDL requires a separate implementation review
before execution.

## Existing security debt

Existing policies on several legacy tenant tables derive organization access
from `user_profiles.organization_id`.

The authoritative Multi-Org model uses `organization_members`.

Existing `organizations` policies were also observed with unconditional
expressions.

These findings are security-hardening debt and are not modified as part of
the license foundation checkpoint.

New license security must not copy these legacy patterns.

## Migration boundary

A subsequent additive migration may address:

- organization foreign key;
- lifecycle CHECK constraints;
- temporal CHECK constraints;
- approved license RLS policies.

It must not:

- install PostgreSQL extensions implicitly;
- create `UNIQUE(organization_id)`;
- hard-delete licenses;
- grant license permissions to roles;
- rewrite unrelated RLS policies;
- weaken backend tenant or RBAC enforcement.

Cardinality/concurrency enforcement requires a separate explicit decision
before production license creation is enabled.
