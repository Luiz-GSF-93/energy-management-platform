# F1.2.4 — Organization User Invite — Closeout

## Status

CLOSED / PUBLISHED

## Scope

Secure organization-scoped user invitation for the Admin user lifecycle.

Endpoint:

- `POST /admin/users/invite`

Required permission:

- `ORGANIZATION_USERS_INVITE`

Tenant authority is derived from the validated backend tenant context.
The request body is not an authority source for organization selection.

## Input contract

The invite contract accepts:

- email
- name
- roleId
- affiliationType

`affiliationType` is restricted to:

- internal
- external

No organization or tenant identifier is accepted as request-body authority.

## Authority model

Identity authority:

- Supabase Auth identity

Profile authority:

- `user_profiles`

Organization membership authority:

- `organization_members`

Organization role authority:

- `organization_members.role_id`

Global platform assignment remains separate from organization access.

The invite flow does not use `user_roles` as organization-access authority.

## Role validation

The requested role must resolve to exactly one valid role belonging to the
active organization and must have organization scope.

A role outside the active organization is rejected.

## Identity resolution

The flow first resolves an existing profile by normalized email.

When no profile exists, Supabase Auth identities are searched using bounded,
paginated lookup.

The lookup is fail-closed:

- enumeration must prove exhaustion;
- reaching the configured pagination bound without proving exhaustion fails;
- an existing Auth identity without a valid profile is not silently repaired;
- identity/profile recovery is a separate workflow.

## Existing identity behavior

Existing identity + valid profile + no current-organization membership:

- identity is reused;
- profile is not rewritten;
- only the organization membership is created.

Existing active membership:

- rejected;
- invite does not become a role-update operation.

Existing inactive membership:

- rejected;
- invite does not become a reactivation operation.

Existing profile affiliation mismatch:

- rejected;
- affiliation is not rewritten.

## New identity provisioning

For a genuinely new identity:

1. invite the Auth identity;
2. validate the returned Auth identity;
3. explicitly create the user profile;
4. validate the returned profile;
5. create the organization membership;
6. persist the invite audit record.

The implementation does not assume an Auth-to-profile database trigger.

## Returned-data integrity

The created Auth identity must return:

- a valid user id;
- an email matching the normalized requested email.

The created profile must return exactly one row matching:

- target user id;
- normalized email;
- active organization id;
- requested affiliation type.

Unexpected returned state fails closed.

## Membership behavior

The membership is created only for the active organization.

Initial status:

- active

The invite flow does not modify memberships belonging to other organizations.

Database uniqueness for the user/organization membership pair was verified
against the authoritative Supabase schema before implementation.

A uniqueness race during membership creation is mapped to conflict behavior.

## Audit

Successful mutation is persisted through the invite audit primitive.

Audit action:

- `INVITE_ORGANIZATION_USER`

Audit resource:

- organization membership

The audit records the relevant organization/user/provisioning context without
storing credentials or secrets.

Audit failure triggers compensation of resources owned by the current invite
operation.

## Compensation

Compensation ownership is explicit.

Only resources created by the current invite operation are eligible for
rollback.

Pre-existing identity/profile resources are never deleted by invite
compensation.

Rollback order for newly owned resources:

1. membership
2. profile
3. Auth identity

Compensation steps are isolated so a rollback failure is captured without
silently skipping subsequent owned-resource cleanup.

Double compensation is prevented by explicit control-flow state.

## Security invariants

The published implementation proves:

- backend tenant enforcement;
- organization-scoped role validation;
- strict invite DTO validation;
- no organization authority from request body;
- no organization access derived from `user_roles`;
- no silent membership reactivation;
- no silent role mutation through invite;
- no silent affiliation rewrite;
- fail-closed Auth lookup;
- returned Auth email integrity;
- returned profile integrity;
- ownership-aware compensation;
- persistent audit;
- public registration flow unchanged;
- no schema change in this functional checkpoint.
