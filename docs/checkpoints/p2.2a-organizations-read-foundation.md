# P2.2a — Organizations Read Foundation

## Status

IMPLEMENTED AND LOCALLY VALIDATED — pending publication and production
post-deployment validation.

Phase 2 — Administration remains active.

P2.2 — Organizations remains open.

This checkpoint implements the read-only Organizations foundation.

Organization create, update and delete operations are not implemented by
this checkpoint.

## Objective

Establish the first Administration Organizations slice over the existing
platform-scoped backend contract.

The slice provides:

- typed Organizations read API;
- centralized Organizations permission constant;
- permission-aware Organizations navigation;
- Organizations list route;
- loading, empty and error states;
- global Platform Admin frontend authentication context;
- preservation of organization-scoped authentication behavior.

No database migration is included.

## Existing backend contract

The existing Organizations backend already provides platform-scoped
Administration routes.

The read contract used by P2.2a is:

- `GET /api/v1/admin/organizations`;
- `GET /api/v1/admin/organizations/:id`.

Both routes require the existing platform Organizations view permission.

No new Organizations repository, service, table or database authority is
introduced.

## Organizations response contract

The frontend Organization contract reflects the live backend response:

- `id`;
- `name`;
- optional or nullable `description`;
- optional `created_at`;
- optional `updated_at`.

The frontend does not invent additional Organization fields.

## Permission boundary

The Organizations view permission is centralized in the frontend permission
contract.

Navigation visibility and page presentation use that permission.

Frontend permission checks remain presentation behavior only.

The backend remains the authorization authority.

The Organizations API continues to enforce the platform-scoped permission
independently of frontend visibility.

## Read-only frontend

P2.2a introduces:

- `/backoffice/organizations`;
- Organizations collection loading;
- responsive Organization cards;
- empty state;
- error state;
- permission-denied presentation.

The page does not perform Organization mutation.

The typed API boundary contains list and detail GET operations only.

Detail API support is established for the existing backend read contract even
though this checkpoint does not introduce a separate detail route.

## Platform-scope production discovery

Production validation with the existing organization-scoped validation user
confirmed:

- login succeeded;
- organization auth context succeeded;
- the platform Organizations view permission was absent;
- Organizations list returned HTTP 403;
- the permission response was consistent with the runtime permission context;
- no mutation was performed.

This validates the deny path.

Production validation with the existing Platform Admin account then
confirmed:

- login returned HTTP 201;
- `GET /api/v1/admin/organizations` returned HTTP 200;
- the Organizations collection contract was valid;
- two Organizations were returned during that validation;
- `GET /api/v1/admin/organizations/:id` returned HTTP 200;
- the detail response contract was valid;
- no Organization value was printed by the validation gate;
- no mutation was performed.

This validates the existing backend Platform Admin read path.

## Organization context versus platform context

The same Platform Admin production validation confirmed that
`GET /api/v1/auth/context` returns HTTP 403 for the global actor while the
platform-scoped Organizations routes return HTTP 200.

Repository inspection confirmed that this is an architectural scope
distinction rather than an Organizations authorization failure.

The existing organization auth context is membership-based.

Platform-scoped routes instead resolve a global access context from the
existing global role assignment.

A Platform Admin must not be given artificial organization membership merely
to initialize the Administration frontend.

## Platform frontend context gap

P2.1 established the frontend AuthProvider around the organization-scoped
`/api/v1/auth/context` contract.

P2.2a therefore exposed a concrete Phase 2 requirement not satisfied by the
previous browser contract: the frontend requires the already-authoritative
global PlatformContext when operating as Platform Admin.

The backend already maintained `AccessContext` as a discriminated
organization/global authorization model, but did not expose the global
context through an authentication endpoint.

## Platform context endpoint

P2.2a adds:

`GET /api/v1/auth/platform-context`

The endpoint is explicitly platform-scoped.

It serializes the global access context already resolved and validated by the
existing TenantGuard.

Its response contains:

- `scope`;
- user `id`;
- user `email`;
- `role`;
- `roleId`;
- `permissions`.

It does not contain:

- `organizationId`;
- `currentOrganization`;
- organization memberships.

The endpoint does not introduce a second database lookup or duplicate
Platform Admin authorization logic in AuthService.

## Access context decorator

P2.2a adds an Access decorator that reads the already-resolved
`request.accessContext`.

The decorator:

- does not resolve tenant context;
- does not use `org_default`;
- does not query the database;
- does not create a new authorization authority.

The TenantGuard remains the authority that validates and constructs the
access context.

## Dual-scope frontend authentication

The frontend AuthContext now represents either:

- organization context; or
- global platform context.

Authentication resolution follows this boundary:

1. attempt the existing organization auth context;
2. HTTP 200 resolves organization scope;
3. HTTP 403 attempts the platform-context endpoint;
4. successful platform-context resolution establishes global scope;
5. HTTP 401 remains an invalid-session result and does not trigger platform
   fallback;
6. failure of both authorized context paths remains fail-closed.

The organization auth contract is preserved rather than rewritten.

## Permission evaluation

`hasPermission()` now evaluates the effective context:

- organization scope uses
  `currentOrganization.permissions`;
- global scope uses the global
  `permissions` array.

This does not change backend authorization.

## Organization switching

Organization switching remains available only for organization-scoped
contexts.

A global Platform Admin does not receive an artificial organization selector
or organization context.

The Sidebar presents the global role directly when global context is active.

## Infrastructure ownership

P2.2a preserves the P2.1 infrastructure boundary:

- browser storage remains owned by
  `frontend/app/lib/auth/session.ts`;
- `fetch()` remains owned by
  `frontend/app/lib/api/client.ts`;
- `NEXT_PUBLIC_API_URL` remains owned by
  `frontend/app/lib/api/client.ts`.

No business component directly owns those concerns.

## Production publication dependency

The new frontend global-context flow depends on the new backend
`/api/v1/auth/platform-context` endpoint.

That endpoint is not present in production until this checkpoint is
published and the backend deployment completes.

Therefore the global frontend flow cannot be honestly claimed as
post-deployment validated before publication.

After deployment, the publication gate must validate both:

1. organization-scoped authentication continues to resolve through
   `/api/v1/auth/context`;
2. Platform Admin authentication falls back from the expected organization
   context HTTP 403 to `/api/v1/auth/platform-context` HTTP 200 and can read
   Organizations.

No mutation is required for that validation.

## Security boundary

P2.2a does not:

- weaken TenantGuard;
- weaken RoleGuard;
- alter Foundation RLS;
- derive global access from organization membership;
- derive organization access from global affiliation;
- change `roles.permissions` authority;
- add artificial membership for Platform Admin;
- bypass backend Organizations authorization;
- expose credential values.

Platform and organization authorization scopes remain distinct.
