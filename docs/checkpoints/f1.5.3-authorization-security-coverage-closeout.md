# F1.5.3 — Authorization & Security Coverage Audit Closeout

## Status

CLOSED AND VALIDATED.

Phase 1 remains open.

## Scope

This audit systematically reviewed every backend HTTP controller and route
for explicit authorization classification.

The review covered:

- public endpoints
- authentication/context endpoints
- recovery endpoints
- platform-scoped administration
- organization-scoped administration
- tenant business resources
- explicit resource permissions

## Global security infrastructure

The application registers globally:

- TenantGuard
- RoleGuard
- TenantInterceptor

TenantGuard remains responsible for authentication and tenant/access
context resolution.

RoleGuard enforces endpoint permissions when @RequirePermission metadata
is present.

An endpoint without @RequirePermission is not automatically protected by
resource-level RBAC because RoleGuard intentionally allows handlers with
no required permission metadata.

Therefore every business/resource endpoint was reviewed explicitly.

## Route inventory

42 HTTP routes were identified.

All 42 routes have an intentional authorization classification.

### Public

AppController:

- GET /health
- GET /

AuthController:

- POST /auth/register
- POST /auth/login

These routes are explicitly marked @Public().

### Authenticated context

AuthController:

- GET /auth/context
- GET /auth/profile

These are identity/context endpoints rather than resource CRUD endpoints.
They are not public and therefore pass through the normal global
TenantGuard authentication/context flow.

They do not require artificial resource permissions.

### Recovery

AuthController:

- GET /auth/my-organizations
- POST /auth/switch-organization/:organizationId

These routes are explicitly marked @RecoveryEndpoint().

Recovery behavior is deliberately limited to authenticated identity/profile
resolution without requiring a fully resolved organization role context.

Existing guard/interceptor tests cover recovery behavior.

### Explicit resource RBAC

Every route in the following resource/admin controllers has an explicit
@RequirePermission declaration:

- OrganizationsController
- UsersController
- ConsumerUnitsController
- ContractsController
- CustomersController
- DocumentsController
- LicensesController

No business CRUD endpoint remains dependent solely on the global guard
chain without explicit permission metadata.

## Gaps resolved during F1.5.3

F1.5.3 resolved the authorization gaps identified during the audit:

- Contracts CRUD received explicit permission metadata.
- Documents CRUD permission coverage was completed.
- Consumer Units received a dedicated permission model and controller wiring.
- Documents UPDATE received a dedicated permission.
- Customers was decoupled from the Contracts permission domain and received
  a dedicated permission model while preserving effective access.
