# F1.5.6a — Foundation RLS Decision Brief

## Status

Design approved for migration preparation. No RLS DDL has been executed by
this checkpoint.

## Architecture

Primary authorization remains in the backend:

identity -> TenantGuard/TenantContext -> RBAC -> service-role database client.

RLS is defense in depth for non-privileged database/API access and MUST NOT
replace backend authentication, tenant validation, role or permission checks.

## Tenant authority

ADR-009 organization membership is authoritative.

Organization-scoped RLS MUST use active `organization_members` membership.

Legacy derivation based solely on `user_profiles.organization_id` MUST NOT be
used for new policies.

## Platform scope

Platform Admin global authorization remains a backend responsibility.

No synthetic organization membership or broad RLS bypass will be introduced
for Platform Admin.

## Membership helper

A new narrowly scoped helper may be introduced to avoid recursive RLS checks
on `organization_members`.

Target contract:

`is_active_org_member(target_organization_id text) -> boolean`

The authenticated identity MUST come from `auth.uid()` internally.

The caller MUST NOT provide an arbitrary user id.

If implemented as SECURITY DEFINER:

- owner and execution privileges must be explicit;
- search_path must be fixed;
- PUBLIC execution must not be inherited accidentally;
- the function must perform only the membership existence check;
- it must not evaluate application RBAC.

The legacy `get_user_organization(uuid)` helper is not authoritative for the
ADR-009 multi-org model and will not be reused or modified in this checkpoint.

## Migration scope

First hardening batch:

- organizations
- organization_members
- audit_logs
- licenses

Deferred for separate review:

- roles
- role_permissions
- user_profiles
- user_roles
- domain tables outside Foundation

## Policy direction

Organizations:
authenticated organization-scoped visibility requires active membership.

Organization members:
authenticated visibility is restricted through the approved membership
boundary without self-referential RLS recursion.

Audit logs:
organization-scoped visibility requires active membership.

Licenses:
organization-scoped visibility requires active membership.

Write policies MUST NOT be treated as a replacement for backend RBAC.

## Existing backend behavior

The backend uses a privileged Supabase service client and intentionally bypasses
RLS. Existing backend authorization therefore remains mandatory and fail-closed.

## Compatibility

This hardening MUST NOT:

- change TenantContext semantics;
- change organization switching;
- change JWT claims;
- change service-role backend behavior;
- create synthetic memberships;
- restore user_profiles.organization_id as tenant authority;
- grant Platform Admin direct RLS bypass;
- rewrite unrelated domain policies;
- change application RBAC;
- remove legacy helpers without dependency proof.

## Validation requirement

Before execution, the exact migration must be reviewed.

After execution, validation must prove:

1. RLS remains enabled;
2. unconditional organization policies are removed;
3. active membership is required for the hardened tenant boundary;
4. licenses no longer rely on zero-policy as their final RLS design;
5. backend regression remains green;
6. cross-tenant access fails for non-privileged authenticated access;
7. service-role backend flows remain compatible.

## Decision

Proceed to exact migration design.

Do not execute RLS DDL until that migration has been separately reviewed.
