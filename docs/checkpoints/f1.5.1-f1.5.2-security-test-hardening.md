## Status

Technically validated and ready for publication.

- F1.5.1 — Supabase configuration hardening

## F1.5.1 — Supabase configuration hardening

### Problem

The centralized Supabase service contained hardcoded fallback configuration,
including credential material, and logged the configured Supabase URL.

Because the centralized service is shared by multiple backend modules, silent
fallback behavior was incompatible with the Foundation fail-closed security
requirement.

### Change

`SupabaseService` now:

- reads `SUPABASE_URL` only from configuration;
- reads `SUPABASE_SERVICE_KEY` only from configuration;
- throws `Supabase configuration unavailable` when either value is absent;
- contains no hardcoded Supabase URL fallback;
- contains no hardcoded service-key fallback;
- no longer logs the configured Supabase URL;
- preserves fail-closed behavior in `createAuthClient()`.

### Focused contract coverage

Added `supabase.service.spec.ts` covering:

1. missing `SUPABASE_URL` fails closed;
2. missing `SUPABASE_SERVICE_KEY` fails closed;
3. complete configuration creates the primary client;
4. `createAuthClient()` remains fail-closed when configuration is unavailable.

Focused result:

- suites: 1 passed / 1 total
- tests: 4 passed / 4 total

### Credential rotation boundary

Removing hardcoded credentials from source does not revoke credentials that
were previously exposed.

Operational credential rotation remains required before formal Foundation
closeout.

At minimum, previously exposed Supabase service credentials and database
connection credentials must be treated as compromised and rotated through
their authoritative providers.

No credential values are recorded in this checkpoint.

## F1.5.2 — Backend test runner recovery

### Problem

The backend declared:

`test=jest`

but the repository did not declare or configure a functional Jest TypeScript
runner.

Before this checkpoint:

- Jest dependency: absent
- ts-jest dependency: absent
- Jest type declarations: absent
- Jest configuration: absent
- backend spec files: 28

Historical inspection found no previously complete Jest configuration to
restore.

### Decision

Introduce the minimum runner required by the existing test suite.

Added direct development dependencies:

- jest 29.7.0
- ts-jest 29.4.12
- @types/jest 29.5.14

`@nestjs/testing` was not added because none of the 28 existing specs imports
or requires it.

Added a minimal `backend/jest.config.js` using:

- Node test environment;
- existing `src/**/*.spec.ts` convention;
- ts-jest TypeScript transformation;
- existing backend tsconfig;
- clearMocks.

### License create spec typing correction

The recovered runner exposed one compile-time problem in the existing license
create test harness.

The mocked Supabase `insert` function had been inferred as accepting zero
arguments even though production code correctly calls it with an insert
payload.

Only the test harness typing was corrected.

No production license behavior was changed.

Focused result after correction:

- suites: 1 passed / 1 total
- tests: 11 passed / 11 total
