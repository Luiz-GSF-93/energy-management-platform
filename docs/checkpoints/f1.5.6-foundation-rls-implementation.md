# F1.5.6 — Foundation RLS Hardening Implementation

## Status

IMPLEMENTED AND VALIDATED — pending publication.

Phase 1 remains open.
Phase 2 remains unauthorized.

## Objective

Harden the Foundation RLS boundary to align non-privileged database/API
access with the ADR-009 active organization membership model.

Backend TenantContext and RBAC remain the primary application authorization
boundary.

RLS remains defense in depth.

## Hardened tables

The migration hardens:

- organizations
- organization_members
- audit_logs
- licenses

No unrelated domain-table RLS was changed.

## Membership authority

The new RLS boundary uses active `organization_members` membership.

New Foundation policies no longer derive tenant authority from
`user_profiles.organization_id`.

The legacy `get_user_organization(uuid)` helper was not modified or reused.

## Membership helper

The migration introduces:

`public.is_active_org_member(target_organization_id text) -> boolean`

Properties validated after execution:

- SECURITY DEFINER
- STABLE
- owner: postgres
- fixed `search_path=pg_catalog`
- identity obtained internally through `auth.uid()`
- membership requires matching organization
- membership requires active status
- PUBLIC has no EXECUTE
- anon has no EXECUTE
- authenticated has EXECUTE
- service_role retains EXECUTE

The helper exists to avoid recursive RLS evaluation on
`organization_members`.

It performs tenant-membership evaluation only and does not implement RBAC.

## Policy replacement

Five legacy policies were removed:

- audit_logs legacy organization SELECT
- organization_members legacy INSERT
- organization_members legacy SELECT
- organizations unconditional UPDATE
- organizations unconditional SELECT

Four policies now remain across the hardened tables:

- foundation_audit_logs_select
- foundation_organization_members_select
- foundation_organizations_select
- foundation_licenses_select

All four are:

- SELECT policies
- TO authenticated
- active-membership scoped

No INSERT, UPDATE, DELETE or ALL policy remains on the four hardened tables.

## Authenticated read proof

A real authenticated JWT for an organization-scoped `consulta` user was used
through the non-privileged Supabase REST path.

Validated behavior:

- own organization read: HTTP 200, exactly one expected row
- foreign organization read: HTTP 200, zero rows
- organization_members read: only memberships from `org_default`
- licenses read: zero foreign rows
- audit_logs read: zero foreign rows
- anonymous organization read: zero rows

This proves runtime tenant isolation through the non-privileged JWT/RLS path.

## Direct-write proof

The two legacy direct-write paths removed by this migration were tested.

### organization_members INSERT

Authenticated direct INSERT returned HTTP 403.

No duplicate membership was created.

### organizations UPDATE

PostgREST returned HTTP 200 rather than an authorization error.

However, exact-count/representation proof returned:

- `Content-Range: */0`
- zero returned rows
- `WRITE_FILTERED_OUT=True`

A subsequent read confirmed the organization state remained unchanged.

Therefore the authenticated UPDATE path is fail-closed through RLS row
invisibility even though PostgREST represents the zero-row UPDATE as HTTP 200.

The validation does not incorrectly classify this behavior as HTTP 403.
