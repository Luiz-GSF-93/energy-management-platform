# F1.2 — User Lifecycle Decision Brief

Date: 2026-09-21
Status: Architecture Proposed — Implementation Pending
Authority: ADR 009 + Phase 5.5/5.6/5.7 approved runtime architecture

## 1. Objective

Establish the minimum secure user lifecycle foundation for organization-scoped
administration without creating a second authorization authority or breaking the
existing multi-organization model.

## 2. Current Verified State

The runtime currently has:

- Supabase Auth as authentication identity authority.
- `user_profiles` for profile information and the temporary active organization pointer.
- `organization_members` as organization membership authority.
- `organization_members.role_id` as contextual organization role authority.
- `roles.scope = organization` for organization roles.
- `user_roles` reserved in the new architecture for explicit global assignments.
- `roles.scope = global` for Platform Admin authorization.
- persistent audit support for selected critical mutations.
- `/admin/users/:userId/affiliation` as the only current administrative user mutation.

The current public `/auth/register` route calls Supabase `auth.signUp()`.

No explicit profile or organization membership write occurs in the visible
`register()` implementation.

Database trigger/function provenance for registration remains unverified.

`TRIGGER_PROVENANCE=UNVERIFIED`

## 3. Sources of Authority

### Identity

`auth.users`

Responsibilities:

- authentication identity;
- email identity;
- authentication lifecycle managed by Supabase Auth.

It MUST NOT become organization authorization authority.

### Profile

`user_profiles`

Responsibilities:

- profile attributes;
- affiliation classification;
- compatibility active-organization pointer while current RLS depends on it.

`user_profiles.organization_id` MUST NOT become membership authority.

### Organization Membership

`organization_members`

This is the sole organization membership authority.

An organization-scoped user has access only when the membership is valid under
the approved TenantGuard rules.

No fallback to `user_roles` is allowed for organization authorization.

### Contextual Role

`organization_members.role_id`

The membership role is authoritative only when:

- membership belongs to the target organization;
- membership is active;
- role exists;
- role belongs to the same organization;
- role scope is exactly `organization`.

### Global Role

`user_roles`

May be used only for explicit global assignments validated with a role whose
scope is exactly `global`, as approved in Phase 5.7.

It MUST NOT be used as fallback for organization membership or organization role.

## 4. Administrative API Contract

The minimum target surface is:

### `GET /admin/users`

Permission:

`ORGANIZATION_USERS_VIEW`

Returns users associated with the actor's active organization only.

Cross-organization enumeration is forbidden.

### `GET /admin/users/:userId`

Permission:

`ORGANIZATION_USERS_VIEW`

The target must have a membership in the actor's active organization.

### `POST /admin/users/invite`

Permission:

`ORGANIZATION_USERS_INVITE`

Target behavior:

- validate input;
- validate requested role;
- role must belong to actor's active organization;
- role scope must be exactly `organization`;
- provision or associate identity through an explicitly designed flow;
- create or restore the organization membership only under the approved lifecycle;
- persist audit;
- fail closed on ambiguity or partial integrity failure.

The exact Supabase Auth invitation/identity compensation algorithm MUST be
designed and tested before this endpoint is implemented.

### `PATCH /admin/users/:userId/role`

Permission:

`ORGANIZATION_USERS_UPDATE`

Changes only the role of the target membership in the actor's active organization.

It MUST NOT modify roles in another organization.

It MUST NOT create a global assignment.

### `PATCH /admin/users/:userId/affiliation`

Existing endpoint.

Permission:

`ORGANIZATION_USERS_UPDATE`

Existing Phase 5.6 contract remains unchanged.

### `DELETE /admin/users/:userId`

Permission:

`ORGANIZATION_USERS_DELETE`

Semantic meaning for F1.2:

Deactivate/revoke the target user's membership in the actor's active organization.

It MUST NOT hard-delete `auth.users`.

It MUST NOT remove memberships belonging to other organizations.

It MUST NOT delete the user profile merely because one organization membership
was revoked.

It MUST be audited.

## 5. CREATE Permission

`ORGANIZATION_USERS_CREATE` exists in the permission catalog.

F1.2 MUST NOT invent semantics for it.

Direct identity creation without an invitation remains outside the first
implementation increment until its business and security contract is explicitly
approved.

## 6. Public Registration

The existing public:

`POST /auth/register`

is a compatibility-sensitive route.

It MUST NOT be silently removed or behaviorally changed during the first F1.2
implementation increment.

Its current implementation calls Supabase `auth.signUp()` but contains no
explicit profile or membership provisioning in the visible service code.

Database trigger provenance is currently unverified.

Therefore:

- F1.2 MUST NOT assume registration creates a membership;
- F1.2 MUST NOT assume registration does not create a profile through database automation;
- administrative authorization MUST never depend on unverified registration side effects;
- public registration hardening or retirement requires a separate compatibility decision.

## 7. Invite / Provisioning Integrity

Supabase Auth and application tables are separate mutation boundaries.

The implementation MUST NOT claim full SQL atomicity across:

- Auth identity provisioning;
- profile mutation;
- membership mutation;
- audit mutation.

Before invite implementation, a compensation strategy must be approved.

Partial failures must fail closed and must not silently leave an authorized
membership in an inconsistent state.

The implementation must distinguish at least:

- existing identity with valid profile;
- existing identity without target membership;
- existing membership;
- inactive membership;
- conflicting role;
- new identity;
- Auth provisioning failure;
- profile failure;
- membership failure;
- audit failure;
- concurrent request.

## 8. Tenant Isolation

Every organization-scoped administrative user operation must derive the actor
organization from the validated organization access context.

Client-provided `organization_id` is not authorization authority.

Target organization membership must be checked on the backend.

No cross-organization mutation is permitted.

## 9. Role Validation

A requested organization role is valid only when:

- the role exists;
- `role.organization_id` equals the actor's active organization;
- `role.scope` equals `organization`.

Role name alone is never authorization authority.

## 10. Audit

The following F1.2 mutations require persistent audit:

- invitation/provisioning outcome;
- membership role change;
- membership deactivation;
- future membership reactivation if implemented.

Audit records must identify:

- actor;
- actor organization context;
- target user;
- action;
- resource;
- before/after where applicable;
- request origin metadata already supported by the audit foundation.

No synthetic `org_default` may be used as audit authority.

## 11. Non-Goals

F1.2 does not include:

- generic role CRUD;
- generic permission CRUD;
- Platform Admin user-management bypass;
- hard deletion of Auth identities;
- global user impersonation;
- broad RLS redesign;
- removal of the active organization pointer;
- replacement of Supabase Auth;
- resurrection of legacy organization authorization through `user_roles`;
- automatic access to every organization for Platform Admin;
- frontend user-management implementation;
- public registration redesign in the first increment.

## 12. Implementation Sequence

Implementation must remain incremental.

1. User list/read contract.
2. Tests and regression.
3. Membership role update contract.
4. Persistent audit for role update.
5. Tests and regression.
6. Membership deactivation contract.
7. Persistent audit for deactivation.
8. Tests and regression.
9. Invite/provisioning design checkpoint.
10. Invite implementation only after compensation strategy approval.
11. Full F1.2 regression.
12. Checkpoint and publish.

## 13. Required Regression

At minimum:

- organization membership remains authoritative;
- organization role remains membership role;
- global assignment remains isolated to explicit platform endpoints;
- cross-tenant user reads are blocked;
- cross-tenant user mutations are blocked;
- role from another organization is rejected;
- global role cannot be assigned through organization user API;
- affiliation endpoint remains compatible;
- organization switching remains compatible;
- `/auth/context` remains membership-authoritative;
- Platform Admin architecture from Phase 5.7 remains intact;
- production build passes;
- test specs remain excluded from production compilation.

## 14. Security Invariants

A user administration request is authorized only when all applicable conditions
hold:

authenticated identity
+ validated organization context
+ active actor membership
+ actor contextual role
+ required permission
+ target membership boundary
+ valid requested organization role where applicable.

No single role name, profile organization pointer, frontend state, or client
payload may bypass these conditions.
