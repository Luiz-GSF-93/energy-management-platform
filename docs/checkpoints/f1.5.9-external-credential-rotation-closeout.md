# F1.5.9 — External Credential Rotation Closeout

## Status

VALIDATED — pending publication.

Phase 1 remains open.
Phase 2 remains unauthorized.

## Objective

Close the external credential-rotation requirement identified during the
Foundation security hardening review.

Previously exposed credential material must be treated as compromised even
after hardcoded values are removed from source control.

No credential values are recorded in this checkpoint.

## Historical exposure evidence

Repository-history inspection confirmed that the historical
`backend/.env.example` contained populated credential material.

The exposed categories included:

- a Supabase PostgreSQL connection credential;
- a privileged Supabase service credential;
- the application JWT signing secret.

The historical database connection targeted the Supabase PostgreSQL
datastore.

The separate Railway PostgreSQL service is not the authoritative datastore
for the current Foundation model.

## Supabase privileged credential rotation

A new Supabase secret key using the current `sb_secret_...` format was
created.

The local backend configuration was migrated from the historical privileged
credential to the new secret key.

The production Railway backend was migrated to the same new credential.

Before retirement of the legacy key, production validation proved:

- login completed successfully;
- a new access token was returned;
- authenticated `/api/v1/auth/context` returned HTTP 200.

The legacy Supabase service key was then retired.

After retirement, the complete authenticated production flow was executed
again and succeeded.

This proves that the production backend no longer depends on the retired
legacy service credential.

No privileged credential value was committed or recorded in documentation.

## Supabase PostgreSQL credential rotation

Historical inspection confirmed that the exposed `DATABASE_URL` targeted
the Supabase PostgreSQL datastore and contained a populated password.

The database password for the correct Supabase project was reset through
the provider.

The local ignored `backend/.env` was updated with the new password while
preserving the existing database connection target.

The password was URL-encoded before insertion into the connection string.

Structural validation confirmed:

- PostgreSQL scheme present;
- database host present;
- database user present;
- database password present;
- database port present.

No database connection string or password value is recorded in this
checkpoint.

The Railway production `DATABASE_URL` was separately inspected and was
identified as a Railway-internal PostgreSQL connection.

That Railway database is distinct from the authoritative Supabase
PostgreSQL datastore.

The Railway-internal `DATABASE_URL` was therefore not replaced with the
Supabase connection string.

## Application JWT secret rotation

Historical inspection also confirmed that the previous application
`JWT_SECRET` had been populated in tracked repository history.

A new high-entropy application JWT secret was generated locally.

The ignored local backend environment was updated.

The same new secret was then configured on the Railway production backend
and the service was redeployed.

A fresh production login after the redeploy returned an access token.

That newly issued token was accepted by authenticated
`/api/v1/auth/context`, which returned HTTP 200.

The temporary local file used to transfer the new JWT secret to the
deployment environment was deleted after successful validation.

No JWT secret value is recorded in this checkpoint.

## Production validation

Production was validated at multiple points during rotation.

After migration to the new Supabase secret key:

- the backend remained reachable;
- unauthenticated `/api/v1/auth/context` remained protected;
- a fresh login succeeded;
- authenticated `/api/v1/auth/context` returned HTTP 200.

After rotation of the application JWT secret:

- a fresh login succeeded;
- a new access token was issued;
- the new token was accepted by `/api/v1/auth/context`.

After retirement of the legacy Supabase service key:

- a fresh login succeeded;
- an access token was issued;
- authenticated `/api/v1/auth/context` returned HTTP 200;
- the complete legacy-key-retirement flow succeeded.

These validations demonstrate that the active production backend uses the
replacement credential set rather than the retired privileged key.

## Secret-handling controls

During validation:

- secret values were not written to tracked files;
- `backend/.env` remained ignored by Git;
- passwords and tokens were entered through silent prompts where practical;
- access tokens were kept in process-local temporary state;
- temporary response files were removed;
- the temporary JWT-secret transfer file was removed after validation;
- no secret value is included in this checkpoint.

The repository remained clean and synchronized throughout the operational
rotation.

## Rotation result

The identified historical external credential exposure has been addressed.

Completed rotation actions:

1. Supabase privileged backend credential replaced with a new secret key;
2. production backend migrated to the replacement Supabase credential;
3. historical Supabase PostgreSQL password reset;
4. local Supabase database connection updated;
5. application JWT signing secret replaced locally and in production;
6. production authentication validated after JWT rotation;
7. legacy Supabase service credential retired;
8. production authentication validated again after legacy-key retirement.

The unrelated Railway-internal PostgreSQL credential was not changed
because the historical exposed database credential was confirmed to target
the authoritative Supabase PostgreSQL datastore.

## Decision

The external credential-rotation requirement identified by the Foundation
security hardening review is satisfied.

No further credential rotation is required by this checkpoint based on the
identified historical exposure set.

This closeout does not authorize Phase 2.

Phase 1 remains open pending final Foundation regression and formal
Phase 1 closeout.

Phase 2 must not begin.
