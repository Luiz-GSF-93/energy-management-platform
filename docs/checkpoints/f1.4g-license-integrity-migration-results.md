`public.licenses` table.

- PostgreSQL extensions;

## Applied integrity constraints

The authoritative database was verified after execution with exactly:

1. `licenses_organization_id_fkey`
   - FOREIGN KEY (`organization_id`) REFERENCES `organizations(id)`.

2. `licenses_status_check`
   - accepted populated lifecycle values, case-normalized with `lower()`:
     `active`, `suspended`, `expired`, `cancelled`.

3. `licenses_status_active_check`
   - populated `status` and `active` values must represent a consistent lifecycle.

4. `licenses_validity_dates_check`
   - when both dates are populated, `end_date >= start_date`.

No hard delete behavior was introduced by the foreign key.

## RLS boundary

`public.licenses` already had RLS enabled before this checkpoint.

No license RLS policy was created here.

This is intentional: the authoritative permission catalog has license
view/create/update permissions, but they currently have no role assignments.
A membership-only write policy would therefore risk bypassing application
authorization semantics.

Backend authorization remains responsible for validated tenant context,
role/permission enforcement, and input validation.

## Cardinality boundary

This checkpoint does not enforce the invariant:

> At most one effective active license per organization for an overlapping
> validity period.

A global UNIQUE constraint on `organization_id` remains prohibited because
historical licenses must coexist.

Application read-before-write alone is not considered sufficient concurrency
protection.

Database-backed cardinality enforcement remains a separate design and
implementation checkpoint.
