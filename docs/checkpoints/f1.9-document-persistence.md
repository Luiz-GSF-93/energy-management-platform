# F1.9 — Document metadata persistence

The document API previously spread camelCase fields into SQL and omitted required columns. It now maps explicit metadata and checks customer, consumer unit and optional energy contract within the active organization. The uploader comes from the authenticated tenant context; all operations retain the document_management entitlement and controller permissions.

POST requires customerId, consumerUnitId, fileName, fileType (application/pdf, image/jpeg or image/png), documentType (existing database enum), referenceMonth (YYYY-MM-01), fileHash (SHA-256 hexadecimal), fileSizeBytes (positive PostgreSQL integer), and filePath. Optional energyContractId and description are supported. Object keys must begin with organizationId/consumerUnitId/ and cannot contain traversal, encoded separators, URLs or empty path segments. Responses retain database snake_case.

This endpoint registers metadata only: it does not upload, download, inspect bytes, recompute hashes or validate MIME content. Supplied metadata always starts PENDING/PENDING, with no OCR result or invoice link. Actual upload, verified hashing, storage policies, size/quota enforcement and OCR remain future work. The unique index prevents duplicate declared hashes within the organization, case-insensitively, including concurrent inserts; the same hash in another tenant remains allowed. Migration fails without changing rows if pre-existing duplicates need review.

PUT accepts only description while processing_status and ocr_status are PENDING and invoice_id is null. SQL mutation repeats these conditions to guard concurrent processing. OCR fields and validation status cannot be supplied through this API. DELETE returns 409 for existing documents: exceptional administrative deletion with atomic audit is not implemented, so no destructive shortcut is exposed. Missing/foreign records return 404. Internal database errors are sanitized.

The additive migration introduces nullable description text and mime_type varchar(100) and an organization/lower(file_hash) unique index. Existing content and access grants remain unchanged. It must run before backend rollout. No documents are created or changed in production by validation.

Validation includes the full backend build/test suite plus 22 compiled-service SQL checks in isolated PostgreSQL, using synthetic tenants and schema fixtures. Those tests do not emulate Supabase HTTP/auth or replace browser end-to-end validation. Production preflight found zero duplicate hash groups and zero inconsistent customer/unit links. Release outcome belongs in the delivery report.
