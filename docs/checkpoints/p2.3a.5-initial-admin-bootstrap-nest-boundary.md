## Objective

Implement the NestJS Platform Administration boundary for the exceptional
first Organization Administrator bootstrap authorized by P2.3a.5.

The application boundary connects the previously deployed service-role-only
database primitive to an explicitly permission-protected Platform endpoint.

The implementation preserves normal organization-scoped User Management.

## Platform permission

The backend permission registry now includes the published bootstrap
permission identifier as:

`PLATFORM_ORGANIZATIONS_BOOTSTRAP_ADMIN`

The Platform controller requires this dedicated permission.

The bootstrap permission is not an organization role permission.

## Platform endpoint

The existing Organizations Platform controller exposes:

`POST /api/v1/admin/organizations/:id/bootstrap-admin`

The controller remains under the existing:

`@PlatformScope()`

boundary.

The endpoint forwards:

- target Organization identifier;
- validated bootstrap request;
- authenticated Platform actor;
- request IP when available;
- request user-agent when available.

No tenant Organization context is accepted as bootstrap authority.

## Request contract

The request DTO accepts:

- target email;
- target name;
- target affiliation type.

Affiliation remains constrained to the existing:

- `internal`;
- `external`.

The client cannot provide:

- destination role identifier;
- membership status;
- actor identifier;
- arbitrary permissions.

The backend always resolves `admin_org`.

Membership status is always `active`.

## Organization validation

Before identity provisioning, the service validates the target Organization.

The Organization must:

- exist;
- not be soft-deleted;
- resolve uniquely.

Missing Organization fails as not found.

Ambiguous or malformed persistent state fails closed.

## Bootstrap role validation

The service resolves exactly one role satisfying:

- target Organization;
- scope `organization`;
- name `admin_org`.

The request cannot select another role.

Missing, ambiguous or malformed `admin_org` state fails closed.

## Identity and profile resolution

Bootstrap follows the established User Invite identity semantics.

Resolution is profile-first.

For an existing profile:

- profile email integrity is checked;
- the corresponding Auth identity must exist;
- Auth identity and profile must resolve to the same User;
- requested affiliation must match the existing profile.

An existing profile is not rewritten by bootstrap.

## Bounded Auth lookup

When no profile exists, Auth lookup is bounded.

The implementation uses:

- 100 identities per page;
- at most 20 pages.

Provisioning occurs only after lookup proves exhaustion.

If bounded pagination cannot prove exhaustion, bootstrap fails closed.

An existing Auth identity without a valid profile is rejected.

Bootstrap does not silently repair identity/profile inconsistency.

## New identity provisioning

When no identity exists, bootstrap may use the existing administrative Auth
invite mechanism.

The returned identity is validated against the requested normalized email.

A corresponding explicit User profile is then created with:

- User identifier;
- normalized email;
- requested name;
- target Organization;
- requested affiliation.

Only identity/profile resources created by the bootstrap execution are owned
by bootstrap compensation.

## Atomic membership authority

NestJS does not directly insert the bootstrap membership.

Membership authority is delegated exclusively to:

`public.bootstrap_initial_organization_admin(text, uuid)`

through the backend service-role client.

The RPC receives only:

- `target_organization_id`;
- `target_user_id`.

The destination role and active membership state remain database-controlled.

## RPC result integrity

A successful RPC result must prove exactly one membership.

The returned membership must match:

- membership identifier;
- target Organization;
- target User;
- resolved `admin_org` role;
- status `active`.

If membership ownership cannot be proven from the RPC result, the service
fails closed.

It does not perform an unsafe broad membership delete.

Identity/profile resources independently proven to belong to the current
bootstrap execution may still be compensated.

## RPC error mapping

Expected database bootstrap conditions are mapped into application semantics.

The implementation handles:

- `P3005`;
- `P3010`;
- `P3011`;
- `P3012`.

Already-bootstrapped Organization, existing membership and concurrent

Database structural integrity failures remain server integrity failures.

## Persistent audit

After confirmed membership creation, the service persists bootstrap audit
evidence through the existing AuditService infrastructure.

Audit identifies:

- authenticated Platform actor;
- target Organization;
- target User;
- created membership;
- resolved `admin_org` role;
- affiliation;
- provisioning path;
- request IP when available;
- request user-agent when available.

Credential material is not included.

## Audit failure compensation

A successful bootstrap membership followed by persistent audit failure cannot
leave unaudited administrative authority.

Membership compensation is guarded by all of:

- exact membership ID;
- target User ID;
- target Organization ID;
- resolved `admin_org` role ID;
- status `active`.

Only after membership compensation succeeds may bootstrap-owned profile and
identity resources be removed.

If membership compensation fails, bootstrap does not remove identity/profile
resources underneath potentially surviving administrative authority.

## Identity and profile compensation

Pre-existing identity/profile resources are never owned by bootstrap
compensation.

For newly provisioned resources, compensation is guarded by the exact
bootstrap identity/profile state.

Profile compensation validates:

- User ID;
- normalized email;
- Organization ID;
- affiliation.

Identity deletion is attempted only for an Auth identity created by the
current bootstrap execution.

If compensation cannot be confirmed, the service surfaces an integrity error.
