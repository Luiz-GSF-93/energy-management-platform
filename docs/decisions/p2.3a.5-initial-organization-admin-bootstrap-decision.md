# P2.3a.5 — Initial Organization Administrator Bootstrap Decision

## Status

ACCEPTED — implementation pending.

Phase 2 — Administration remains active.

P2.3 — User Management remains active.

P2.3a — User Management Read Foundation is published but its positive
production validation is blocked by the absence of an authorized
organization administrator.

P2.3b — User Invite must not begin until the bootstrap boundary defined by
this decision is implemented, validated and the P2.3a positive read path is
completed.

P2.4 and later Phase 2 modules remain unauthorized.

## Context

P2.3a production validation established that the available organization test
actor authenticates successfully but holds the `consulta` role.

The production RBAC authority confirms:

- `admin_org` has `ORGANIZATION_USERS_VIEW`;
- `gestor` has `ORGANIZATION_USERS_VIEW`;
- `operacional` does not have `ORGANIZATION_USERS_VIEW`;
- `consulta` does not have `ORGANIZATION_USERS_VIEW`.

Production discovery also confirmed that there are currently no active
`admin_org` or `gestor` organization memberships.

The Platform Admin actor cannot use the organization User Management endpoints
because organization context correctly returns HTTP 403.

No Platform Admin bypass exists for organization User Management.

## Existing authority model

`organization_members` is the organization membership authority.

`organization_members.role_id` is the contextual organization-role authority.

Organization User Management permissions are resolved from the role associated
with the active organization membership.

The existing User Invite operation requires:

`ORGANIZATION_USERS_INVITE`

It therefore assumes an already-authorized organization administrator and
cannot bootstrap the first organization administrator by itself.

## Public registration boundary

The existing public registration route remains independent from
administrative bootstrap.

`POST /auth/register`

uses the existing public identity-registration flow.

Public registration must not implicitly grant:

- organization membership;
- `admin_org`;
- `gestor`;
- organization User Management permissions.

Administrative bootstrap must not be hidden inside public registration.

## Bootstrap problem

The system currently contains:

- Organizations;
- organization-scoped administrative roles;
- granular User Management permissions;
- organization-scoped User Management APIs.

However, production currently contains no active organization membership with
an administrative role capable of exercising User Management.

This creates a bootstrap boundary:

an organization administrator is required to use User Invite, but no
organization administrator currently exists to perform that first
administrative action.

## Rejected strategy — broaden consulta

The `consulta` role must not receive User Management permissions merely to
enable production validation.

`consulta` currently represents a lower-privilege organization role.

Granting administrative User Management capability to it would change the
authorization model rather than solve bootstrap.

This strategy is rejected.

## Rejected strategy — permanent Platform Admin bypass

Organization User Management endpoints must not receive a permanent Platform
Admin bypass.

The existing endpoints are organization-scoped and derive authority from
organization membership.

Changing their normal authorization model would weaken the tenant boundary.

This strategy is rejected.

## Rejected strategy — mutate validation user manually

The existing validation user's membership must not be manually changed from
`consulta` to `admin_org` merely to make the P2.3a validation pass.

Direct production data mutation would bypass the application authorization,
audit and lifecycle contracts.

This strategy is rejected.

## Accepted strategy — explicit first-admin bootstrap

The system will use a separately authorized Platform Administration bootstrap
operation for establishing the first organization administrator.

This operation is exceptional.

It is not part of normal organization User Management.

Its only purpose is to transition an organization from:

`no active administrative organization membership`

to:

`one active admin_org organization membership`

under explicit Platform Administration authority.

## Platform authority

The bootstrap operation must be platform-scoped.

It must require an explicit Platform Admin permission dedicated to
organization administrator bootstrap.

The operation must not reuse organization-scoped User Management permission as
its authorization boundary.

The Platform Admin actor must remain outside organization membership.

Successful bootstrap must not create an organization membership for the
Platform Admin actor.

## Target organization

The operation must receive an explicit target Organization identifier through
the protected Platform Administration contract.

The target Organization must:

- exist;
- not be soft-deleted;
- be resolved by the backend.

The frontend must not infer target Organization ownership.

## Target identity

Bootstrap must target an explicit user identity.

The implementation must determine whether the target identity already exists.

Identity provisioning behavior must reuse the established safe identity/profile
contracts where applicable rather than introducing an unrelated identity
model.

No password or credential value may be exposed by bootstrap responses or
audit payloads.

## Bootstrap role

The initial administrative role is:

`admin_org`

Bootstrap must not assign `gestor`, `operacional` or `consulta`.

Normal role changes after bootstrap remain governed by the organization-scoped
User Management lifecycle.

## Eligibility guard

Bootstrap is allowed only when the target Organization has no active
administrative organization membership.

For bootstrap eligibility, administrative memberships are active memberships
whose organization role is:

- `admin_org`;
- `gestor`.

If any active administrative membership already exists, bootstrap must fail
closed.

The operation must not create a second bootstrap administrator.

Additional administrators must be established through normal organization
User Management after bootstrap.

## Existing membership boundary

The implementation must explicitly resolve whether the target identity already
has an organization membership.

It must not silently overwrite an existing active or inactive membership.

Existing membership handling must be decided and tested explicitly before
mutation.

No direct role overwrite is authorized by this decision.

## Concurrency boundary

Bootstrap must protect against concurrent first-admin creation.

Two concurrent requests must not both succeed after independently observing
that no administrator exists.

The implementation must provide a database-enforced or equivalently strong
concurrency boundary before production use.

A check-then-insert sequence without concurrency protection is insufficient.

## Audit boundary

Successful bootstrap is a privileged Platform Administration mutation and must
produce persistent audit evidence.

Audit must identify:

- authenticated Platform Admin actor;
- target Organization;
- target identity;
- resulting organization membership;
- resulting `admin_org` role;
- bootstrap action.

Credential values must never be audited.

## Compensation boundary

If bootstrap performs multiple persistent mutations, failure after partial
mutation must not leave an untracked administrative authority.

Compensation behavior must be ownership-aware.

Resources that pre-existed the bootstrap attempt must not be deleted as
compensation.

If safe compensation cannot be guaranteed, the operation must use a stronger
transactional boundary.

## Idempotency and conflict behavior

Repeated bootstrap attempts must not create duplicate administrative
memberships.

An already-bootstrapped Organization must return a domain conflict.

An existing target membership must not be silently converted.

Invalid Organization, identity, role or membership state must fail closed.

## Frontend boundary

P2.3a does not require a general bootstrap UI.

The first implementation may expose bootstrap only through a narrowly scoped
Platform Administration contract suitable for controlled provisioning.

A permanent end-user interface requires a separately reviewed presentation
contract.

Normal `/backoffice/users` remains organization-scoped.

## P2.3a validation relationship

After successful controlled bootstrap:

1. the newly authorized organization administrator authenticates normally;
2. organization context resolves through `organization_members`;
3. `ORGANIZATION_USERS_VIEW` is obtained from the `admin_org` role;
4. P2.3a Users list is validated with HTTP 200;
5. P2.3a User detail is validated with HTTP 200.

P2.3a production validation remains read-only after bootstrap itself has been
completed.

Bootstrap must not be repeated merely for P2.3a testing.

## Scope boundary

This decision does not authorize:

- permanent Platform Admin bypass for User Management;
- changing `consulta` permissions;
- changing `operacional` permissions;
- public-register redesign;
- arbitrary organization role assignment;
- Membership Reactivation;
- P2.3b User Invite frontend implementation;
- P2.4 or later Phase 2 implementation.

## Required implementation discovery

Before bootstrap implementation begins, the repository must be inspected for:

- existing Platform Administration controller patterns;
- existing platform permission catalog patterns;
- persistent platform audit contracts;
- identity creation/reuse contracts from User Invite;
- organization membership uniqueness guarantees;
- transaction or RPC patterns available for concurrency safety;
- existing database constraints covering organization membership.

Implementation must reuse those established boundaries where possible.

## Decision

P2.3 adopts an explicit first-organization-administrator bootstrap boundary.

The bootstrap is a privileged Platform Administration operation.

It exists only to establish the first active `admin_org` membership when no
active `admin_org` or `gestor` membership exists for the target Organization.

Normal User Management remains organization-scoped after bootstrap.

P2.3a remains open until its positive list/detail production validation is
completed through a legitimately authorized organization administrator.

P2.3b remains blocked.

## Publication state

This decision is pending review, commit and publication to `origin/main`.

Bootstrap implementation must not begin until this decision is published.
