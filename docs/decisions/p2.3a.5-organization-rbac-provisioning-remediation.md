# P2.3a.5 — Organization RBAC Provisioning Remediation

## Status

ACCEPTED — implementation pending.

Phase 2 — Administration remains active.

P2.3 — User Management remains active.

P2.3a remains open pending successful initial administrator bootstrap and
positive production read validation.

P2.3b remains blocked.

A production bootstrap attempt against the controlled REG Test Organization
failed closed and left no identity, profile or membership residue.

No second bootstrap attempt is authorized until this remediation is
implemented, published, deployed and validated.

## Objective

Correct the Organization creation lifecycle so that every newly created
Organization receives the organization-scoped RBAC baseline required by the
existing authorization model.

The same canonical provisioning authority must support controlled backfill of
the existing REG Test Organization that currently has no roles.

This remediation must not weaken or bypass the P2.3a.5 initial administrator
bootstrap boundary.

## Discovered defect

The current Platform Organization Create service inserts only the
`organizations` row and persists Organization creation audit evidence.

It does not provision Organization roles.

Production validation confirmed that:

`REG Test 1789688388`

exists but has zero roles.

The Organization therefore cannot satisfy the P2.3a.5 bootstrap prerequisite
that exactly one organization-scoped `admin_org` role exists.

## Bootstrap failure relationship

The controlled initial administrator bootstrap returned HTTP 500.

Post-failure production validation confirmed:

- bootstrap Auth identity count: zero;
- bootstrap User profile count: zero;
- bootstrap Organization membership count: zero.

No administrative authority survived the failed request.

Subsequent production validation established:

- target Organization count: 1;
- target `admin_org` role count: 0;
- active `admin_org` / `gestor` membership count: 0.

The Nest bootstrap service resolves the target `admin_org` role before identity
provisioning.

The missing role therefore explains the observed fail-closed bootstrap result
without requiring identity provisioning to have occurred.

## Current effective Organization RBAC baseline

The canonical production reference is the current effective Organization role
catalog of:

`Expert Energy - Default Organization`

Only organization-scoped roles are part of the per-Organization baseline.

The required roles are:

- `admin_org`;
- `gestor`;
- `operacional`;
- `consulta`.

`admin_platform` is global Platform authority and must not be provisioned as
an Organization-scoped role for each new Organization.

## admin_org baseline

`admin_org` currently resolves exactly 53 permissions.

All 53 permission identifiers resolve to entries in the current permission
catalog.

Unresolved permission count is zero.

## gestor baseline

`gestor` currently resolves exactly 39 permissions.

All 39 permission identifiers resolve to entries in the current permission
catalog.

Unresolved permission count is zero.

## operacional baseline

`operacional` currently resolves exactly 26 permissions.

All 26 permission identifiers resolve to entries in the current permission
catalog.

Unresolved permission count is zero.

## consulta baseline

`consulta` currently resolves exactly 12 permissions.

All 12 permission identifiers resolve to entries in the current permission
catalog.

Unresolved permission count is zero.

## Permission authority

Provisioning must derive role permissions from the current permission catalog
using permission codes.

Implementation must not hard-code environment-specific permission UUIDs as the
semantic source of authority.

Permission UUIDs may be persisted in `roles.permissions` only after resolving
the required permission codes against the current `permissions` catalog.

Every required permission code must resolve exactly once.

Missing or ambiguous permission catalog state must fail closed.

## Role permission contracts

The canonical role permission sets are the permission-code sets validated
against the current production reference Organization.

The implementation must preserve exact role semantics.

It must not broaden or reduce role authority as part of this remediation.

The role permission contracts must be encoded in one canonical backend
provisioning authority and covered by tests.

## Role persistence contract

Each provisioned Organization role must contain:

- a unique role identifier;
- the target Organization identifier;
- the canonical role name;
- `scope = 'organization'`;
- the exact resolved permission identifier array;
- timestamps consistent with the current role schema.

Provisioning must create exactly one of each required Organization role.

## Uniqueness boundary

The effective logical uniqueness requirement is:

`Organization + role name`

Provisioning must fail closed if the target Organization contains:

- duplicate canonical role names;
- malformed canonical roles;
- canonical roles with an unexpected scope.

Provisioning must never silently select one row from ambiguous role state.

## New Organization creation

Successful Platform Organization Create must no longer produce an Organization
without its RBAC baseline.

The desired successful lifecycle is:

`Organization → RBAC baseline → persistent creation audit`

A Create response must not be returned as successful until the Organization
and its required Organization roles are confirmed.

## Create failure compensation

If RBAC provisioning fails after the Organization row is created, the
Organization creation operation must fail.

The just-created Organization must be compensated using the existing guarded
Organization ownership boundary.

Because Organization role rows are Organization-owned and the existing foreign
key uses cascading Organization deletion, compensation may rely on the
Organization ownership boundary only after schema behavior is verified by the
implementation checkpoint.

Pre-existing Organizations must never be deleted by Create compensation.

## Audit failure compensation

If Organization creation and RBAC provisioning succeed but persistent
Organization creation audit fails, the existing guarded Organization
compensation remains required.

Compensation must not leave orphaned Organization roles.

The implementation must validate this behavior explicitly.

## Backfill boundary

Existing Organizations are not automatically rewritten by ordinary Create
execution.

A separate controlled backfill is authorized for:

`REG Test 1789688388`

only after the canonical provisioning implementation is published and
deployed.

The backfill must use the same canonical role/permission authority as new
Organization creation.

It must not use a separately maintained manual permission list.

## Backfill eligibility

Controlled backfill is allowed only when the target Organization:

- exists exactly once;
- is not soft-deleted;
- has no Organization roles;
- has no Organization memberships requiring role reconciliation.

Any unexpected existing role or membership state must stop the backfill and
require separate analysis.

## Backfill idempotency

After successful backfill, re-execution must not create duplicate roles.

An already-provisioned Organization must either:

- return an explicit already-provisioned result; or
- prove exact canonical state and perform no mutation.

Partial or divergent state must fail closed.

## Historical schema boundary

The historical `docs/supabase-schema.sql` role seed is not the current
provisioning authority.

That historical model used concepts including:

- `is_system`;
- `SUPER_ADMIN`;
- `role_permissions`.

The current model instead relies on:

- role `scope`;
- `roles.permissions` JSONB;
- the current permission catalog.

The historical seed must not be copied into the current implementation.

## Database boundary

This remediation may require a database primitive if atomic Organization +
role creation cannot be guaranteed safely through the existing application
operations.

That decision must be made during implementation design.

No database migration is authorized merely by publication of this decision.

## Testing boundary

Implementation validation must cover at least:

- creation of all four canonical Organization roles;
- exact role names;
- organization scope;
- exact permission-code contracts;
- permission resolution integrity;
- missing permission failure;
- ambiguous permission failure;
- partial role state failure;
- duplicate role state failure;
- Create success only after RBAC confirmation;
- Create compensation when RBAC provisioning fails;
- Create compensation when persistent audit fails;
- no `admin_platform` Organization role creation;
- idempotent controlled backfill behavior.

Existing Organization mutation, Delete safety, bootstrap, User Invite and Auth
regressions must remain green.

## Production validation boundary

After publication and deployment, production validation must occur in this
order:

1. validate the canonical provisioning authority;
2. re-check REG Test backfill eligibility;
3. perform exactly one controlled REG Test RBAC backfill;
4. validate exactly four organization-scoped roles;
5. validate exact permission counts and zero unresolved permissions;
6. confirm no active administrative membership exists;
7. only then reconsider the P2.3a.5 initial administrator bootstrap.

The failed bootstrap request must not be retried before these steps complete.

## Scope exclusions

This remediation does not authorize:

- manual creation of only `admin_org`;
- copying `admin_platform` into the target Organization;
- changing role permission semantics;
- broadening `consulta`;
- broadening `operacional`;
- manual creation of the bootstrap identity;
- manual creation of the bootstrap membership;
- a second bootstrap attempt before RBAC remediation validation;
- P2.3b;
- P2.4 or later Phase 2 work.

## Decision

Organization RBAC provisioning is a required invariant of successful
Organization creation.

The canonical per-Organization baseline consists of exactly:

- `admin_org`;
- `gestor`;
- `operacional`;
- `consulta`.

Their permissions are resolved from the current permission catalog by
canonical permission code.

`REG Test 1789688388` requires controlled backfill using the same provisioning
authority before the initial administrator bootstrap may be retried.

P2.3a remains open.

P2.3b remains blocked.

this decision is published to `origin/main`.
