# P2.2d — Organization Delete Safety Decision

## Status

ACCEPTED — implementation pending.

Phase 2 — Administration remains active.

P2.2 — Organizations remains open.

P2.2d — Organization Delete is authorized to proceed only under the safety
contract defined by this decision.

P2.3 — User Management remains unauthorized.

## Context

The existing Organizations backend exposes a platform-scoped Organization
Delete operation.

The operation is a soft-delete:

- the Organization row is preserved;
- `deleted_at` is written;
- normal Organization reads exclude soft-deleted rows;
- persistent mutation audit records the before and after states;
- audit failure triggers guarded compensation.

The original Phase 5.4 architecture required more than soft-delete.

It explicitly required:

- dependency checking;
- a cascade strategy;
- a decision between blocking deletion and marking dependencies inactive.

The implemented Organization Delete never materialized that dependency
policy.

The current service proceeds from Organization lookup directly to writing
`deleted_at`.

## Architecture evolution

The dependency model has expanded since the original Phase 5.4 brief.

Current application code contains Organization ownership or access
relationships including:

- `organization_members`;
- `licenses`;
- `customers`;
- `consumer_units`;
- `energy_contracts`;
- `documents`.

Additional historical schema relationships also exist.

Organization membership is now an authorization authority.

An Organization that is soft-deleted is unavailable to normal organization
authentication context resolution.

Organization deletion therefore has access-control consequences in addition
to data lifecycle consequences.

## Rejected strategy — automatic cascade

P2.2d does not authorize automatic cascading deactivation or mutation of
Organization dependencies.

The current domains do not expose one uniform lifecycle contract that would
make such a cascade deterministic.

Organization memberships have an explicit active/inactive lifecycle with
their own authorization, audit and compensation behavior.

Licenses have a separate effective-license lifecycle.

Customers, consumer units, contracts and documents have independent domain
contracts.

Automatically mutating those domains as a side effect of Organization Delete
would combine separately authorized business operations and create new
cross-domain mutation semantics.

That strategy is rejected for P2.2d.

## Accepted strategy — fail-closed dependency block

Organization Delete must fail closed when known Organization dependencies
exist.

Before writing `organizations.deleted_at`, the backend must check the
Organization identifier against these current dependency tables:

- `organization_members`;
- `licenses`;
- `customers`;
- `consumer_units`;
- `energy_contracts`;
- `documents`.

The dependency guard is based on existence, not inferred business activity.

P2.2d does not attempt to decide whether an existing dependent row is
historical, inactive, expired or otherwise safe to cascade.

If any checked dependency exists, Organization Delete must be rejected before
the Organization mutation occurs.

No dependency row may be mutated by the guard.

## Failure semantics

Dependency resolution is part of the authorization-safe mutation boundary.

If a dependency query fails, Organization Delete must fail closed.

A query failure must not be interpreted as absence of dependencies.

The Organization soft-delete must not execute unless every dependency check
completed successfully and found no blocking row.

## Concurrency boundary

The existing Organization soft-delete concurrency boundary remains required.

The Delete mutation must continue to target:

- the selected Organization identifier;
- only an Organization whose `deleted_at` remains null.

The existing persistent audit and guarded compensation behavior must remain
intact.

P2.2d must not weaken those guarantees while adding the dependency guard.

## Error contract

A blocked Organization Delete is a domain conflict.

The backend should expose a conflict response rather than pretending that the
Organization was deleted.

The response must not expose dependent row contents.

It may identify that the Organization has dependencies that must be resolved
before deletion.

## Frontend contract

The frontend Delete capability must not be implemented until the backend
dependency guard and its tests pass.

After the backend safety boundary is established, the frontend may expose
Organization Delete only when the current platform context contains the
Organization Delete permission.

Frontend visibility remains presentation authorization only.

Backend authorization and dependency validation remain authoritative.

The frontend must require an explicit destructive confirmation before issuing
the Delete request.

## Production validation boundary

Production validation must not target an operational Organization.

The Organization created specifically for P2.2b and updated by P2.2c is the
intended candidate for the eventual allowed-path Delete validation, provided
the dependency guard confirms that it has no blocking dependencies.

The validation must never remove dependencies merely to make the Delete
succeed.

A successful production validation must prove that:

- the target is uniquely identified;
- the target has no blocking dependencies;
- the Delete permission is present;
- exactly one Delete request is issued;
- the Organization disappears from normal list and detail read contracts;
- no hard-delete is performed;
- no unrelated Organization is modified.

## Scope boundary

This decision does not authorize:

- hard-delete of Organizations;
- automatic dependency cascade;
- automatic membership deactivation;
- automatic license deactivation;
- deletion of customers;
- deletion of consumer units;
- deletion of contracts;
- deletion of documents;
- restoration of soft-deleted Organizations;
- P2.3 User Management implementation.

## Decision

P2.2d adopts fail-closed dependency blocking.

The backend dependency guard must be implemented and validated before
Organization Delete is exposed through the Administration frontend.

The existing soft-delete, persistent audit and compensation contracts remain
the mutation architecture.

P2.2 — Organizations remains open.

P2.3 — User Management remains unauthorized.

## Publication state

This decision is pending review, commit and publication to `origin/main`.

P2.2d implementation must not begin until this decision is published.
